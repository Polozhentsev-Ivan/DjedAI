# DjedAI

Локальная аналитическая платформа: пользователь загружает CSV или подключает PostgreSQL/ClickHouse, задаёт вопросы на русском языке и получает ответы, графики и сохраняемые дашборды. Агент выполняет расчёты через инструменты; исходные данные и результаты вычислений сохраняются.

**Текущий этап — интеграция CP1 (#144):** локальные CSV, каталог, текстовый чат с внешней моделью и сохранённые результаты. Production UI и API запускаются через Compose; дальнейшие этапы добавят внешние БД, графики, дашборды и полную многопользовательскую авторизацию.

## С чего начать

1. Прочитать [соглашение команды](CONTRIBUTING.md).
2. Посмотреть [руководство по структуре и служебным файлам](docs/repository-guide.md).
3. Изучить [техническую спецификацию](docs/specification.md) и [пояснения к исходным материалам](docs/README.md).
4. Выбрать [issue](https://github.com/Polozhentsev-Ivan/DjedAI/issues), назначить себя исполнителем и создать ветку от актуальной `main`.

```sh
git switch main
git pull --ff-only
git switch -c feat/53-csv-import
```

Участники с доступом на запись могут работать в ветках общего репозитория. При работе через fork PR также направляется в `main` исходного репозитория. Объединение — после ревью по соглашению команды.

## Локальная конфигурация

Безопасный образец — [.env.example](.env.example). Для локальных значений создайте `.env`:

```powershell
Copy-Item .env.example .env
```

В Linux/macOS: `cp .env.example .env`. Файл `.env` исключён из Git.

В `.env` заполните `MODEL_API_KEY` ключом DeepInfra. Профиль по умолчанию — `https://api.deepinfra.com/v1/openai`, модель `Qwen/Qwen3.6-35B-A3B` (35B суммарных параметров, открытые веса). Инференс выполняет провайдер; локальная GPU и загрузка весов не нужны. Без ключа авторизованный API данных и истории работает, а обращение к модели завершится понятной ошибкой.

Backend читает `.env` через `pydantic-settings`, агент — `MODEL_*` при создании клиента. Общие лимиты определены в `djedai.config.LimitSettings`. Хранилище, сессия, API/SSE и профиль модели согласованы в [PL-1 / #47](docs/decisions/47-contracts-and-runtime.md); [замеры модели](docs/model-profile-pl1.md) и [прогон на 500 000 строк](docs/cp1-smoke-run.md#повтор-на-модели-до-80b) сохранены в протоколах.

## Запуск CP1 через Compose

Общий лимит ответа агента, сетевые повторы и отмена запроса описаны в
[инструкции по времени выполнения](docs/agent-deadlines.md). По умолчанию один
вопрос ограничен 120 секундами, отдельная сетевая попытка — 60 секундами.

Нужны Docker с работающим Linux engine и Docker Compose v2. Команды выполняются из корня Git-репозитория (`repo/`), после создания `.env` по инструкции выше:

```sh
docker compose up --build -d --wait
```

Откройте [http://localhost:8080](http://localhost:8080). Compose собирает Python backend и React через `npm ci`/production build; nginx обслуживает UI и проксирует `/api` на backend. Mocks отключены. Вложенный адрес каталога или чата можно открывать напрямую и обновлять. Порт можно изменить переменной `DJEDAI_PORT` в `.env`. Публикуется только интерфейс на `127.0.0.1`; API доступен через тот же origin.

При каждом старте backend применяет Alembic-миграции. Все API датасетов, подключений, чатов, результатов и SSE требуют Bearer-сессии; `CP1_LOCAL_MODE` не даёт обхода авторизации. Compose отключает прежний bootstrap. Регистрация и вход работают через формы `/register` и `/login`; после создания аккаунта клиент явно выполняет вход. Сессия проверяется при reload, выход закрывает потоки и очищает прежний workspace. Подробности — [AUTH-4 / #104](docs/decisions/104-browser-auth.md). Старые данные CP1 сохраняются за прежним владельцем и автоматически новым аккаунтам не передаются.

SQLite (`/app/var/app.db`), исходные CSV, DuckDB/каталог (`/app/var/data/datasets`) и Parquet результатов (`/app/var/data/results`) находятся в именованном томе `app-data`. Compose закрепляет эти пути внутри контейнера, независимо от локальных путей в `.env`. Секреты `MODEL_*` передаются только backend; Docker build context исключает `.env`, локальные данные и отчёты. В клиентскую сборку входят только публичные параметры.

После регистрации или входа через интерфейс проверяется основной путь:

1. На странице «Источники» загрузите один или несколько CSV, дождитесь готовности и откройте каталог с таблицами и колонками.
2. Выберите датасет, создайте чат и задайте вопрос с независимо известным ответом, например число строк или сумму числового столбца. Проверьте текст и сохранённый результат с SQL/строками.
3. Выполните `docker compose restart`, обновите адрес чата и снова откройте каталог, историю и тот же `result_id`.

```sh
docker compose ps
docker compose logs --tail=100 backend frontend
docker compose down
docker compose up -d --wait
```

`restart` и обычный `down` сохраняют том. Ключ `docker compose down -v` удаляет данные приложения; для повторного открытия используйте обычный `down`. После изменения `.env` примените `docker compose up -d --force-recreate --wait`; после изменений исходников — исходную команду с `--build`.

Состав образов, proxy и способы проверки streaming/upload описаны в [infra/README.md](infra/README.md). PostgreSQL подключается через защищённый `POST /api/datasets/connect`; для сохранения DSN нужен серверный `SOURCE_ENCRYPTION_KEY`. Управление ключом, ограничения SQL и границы будущих функций описаны в [AUTH-3 / #103](docs/decisions/103-owner-isolation.md). ClickHouse, demo-профили и финальная конфигурация #99 остаются последующими задачами.

## Интерфейс

```sh
fnm use          # Node из .nvmrc; можно nvm use
cd frontend
npm ci
npm run dev      # http://localhost:5173, proxy /api на backend
```

Для демонстрационного mock-API задайте `VITE_API_MOCKS=true` в `frontend/.env.local`; по умолчанию запросы идут к backend. Сценарии mock-API, работа с настоящим backend, команды проверок и устройство приложения описаны в [frontend/README.md](frontend/README.md).

## Разработка и качество

Python-окружением управляем через uv: `uv sync --locked`, команды — через `uv run --locked …`. Прямые зависимости фиксируем через `==`, полный набор — в `uv.lock`. Frontend использует Vite и npm с точными версиями и `package-lock.json`. Минимум покрытия — 80% строк собственного Python-кода и отдельно 80% строк собственного TS/TSX-кода frontend; дополнительно обязательны содержательные проверки критичных сценариев. Правила коммитов, PR, тестирования и ревью описаны в [CONTRIBUTING.md](CONTRIBUTING.md).

Даты контрольных точек: **19 октября, 26 октября и 30 октября 2026 года**. Этапы и критерии конкретной работы смотрим в соответствующей issue.
