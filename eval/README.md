# Golden v1 для сценариев 1–2

`questions.yaml` содержит 16 эталонных вопросов: 5 для знакомства с данными, 6 по их содержанию и 5 неоднозначных/ошибочных запросов. Это результат #79: проверяемые ожидания для будущего eval агента. Проверка файла и эталонных чисел не запускает LLM и не является оценкой качества текущего агента.

Нумерация и смысл сценариев взяты из [README HK_Datasets на закреплённой ревизии](https://gitverse.ru/api/repos/kban/HK_Datasets/raw/commit/716fbbcdc3dfa2a63dba1cf835fcc780c5e91a1d/README.md), раздел «Сценарии (Вопросы для Агента)». Примеры «Что передо мной?», вопросов о периоде, значениях поля и одинаковом идентификаторе адаптированы к фоновым заданиям. Сценарий 3 в источнике — группировки и аномалии, 4 — визуализация, 5 — дашборд, 6 — контекст диалога, 7–10 — временные закономерности, сегменты, корреляции/лаги и экстраполяция. Они ещё не покрыты этим набором; наличие фильтра или частот в сценарии 2 не означает приёмку остальных сценариев.

## Источник и границы данных

Manifest `datasets/hk_background_jobs.json` фиксирует полный `08_Фоновые_задания.csv` из [HK_Datasets](https://gitverse.ru/kban/HK_Datasets), ревизию `716fbbcdc3dfa2a63dba1cf835fcc780c5e91a1d`, URL, размер 122084672 байта, SHA-256 и Git blob SHA-1. В файле 500000 строк и 15 полей. Используется весь CSV, без сэмплирования. Сам CSV и сгенерированные отчёты хранятся вне репозитория; URL загрузки закреплён на коммит, а не на изменяемую ветку.

Одна строка — отдельная попытка фонового задания. Код запуска обозначает попытку, код цепочки объединяет первоначальный запуск и повторные попытки; название задания — ещё одна самостоятельная единица. Временные поля подписаны МСК, то есть UTC+03:00. Нули обработанных записей участвуют в статистике, пустые коды ошибок не входят в частоты непустых кодов. Пустой код не доказывает успешность: есть также отменённые попытки. Выручки и таблицы заказов в выбранном датасете нет.

`binding` связывает исходные заголовки с нормализованными именами SQL. Пользовательское представление — `"08_fonovye_zadaniya"`; кавычки нужны из-за цифры в начале имени. `raw_08_fonovye_zadaniya` и служебные таблицы не считаются отдельными бизнес-таблицами. Дополнительный источник или переименование при загрузке требуют явного нового binding, а не автоматического выбора похожей таблицы.

В manifest определены популяции: все попытки, непустые значения «Обработано записей» и все попытки production. Они задают фильтры и смысл знаменателей. Например, процент ошибок production относится к попыткам; отменённые входят в знаменатель, повторные попытки учитываются отдельно. Суммы обработанных записей по попыткам нельзя выдавать за уникальную работу всей цепочки.

## Формат вопроса

Корень `questions.yaml` — список, как в §8 спецификации. `id` стабилен; `scenario` равен `1`, `2` или `edge`; `dataset` ссылается на manifest. Вопросы независимы и по умолчанию выполняются без истории предыдущего вопроса.

`expect.outcome` задаёт ответ или уточнение. Для обычного ответа:

- `tools_any` — допустимые релевантные инструменты. Достаточно корректного плана с одним или несколькими инструментами из списка; точная последовательность и SQL не закреплены. Наличие случайного вызова из списка само по себе не означает успех.
- `population` — ключ определения популяции в manifest.
- `facts` — буквальные эталонные значения с ключом, правилом сравнения и единицей. Количество записей, попыток и цепочек проверяется в их собственных единицах.
- `must_explain` и `must_not_claim` — смысловые требования для проверки человеком и будущим runner, не дословный шаблон ответа.
- `answer_contains_value.from_result` — числа ответа должны происходить из реально полученных результатов выбранного датасета. Сам по себе этот флаг не доказывает правильность числа: его также сверяют с независимым эталоном.

У каждого обычного вопроса есть минимум один машинно проверяемый факт и смысловая рубрика. `dataset.columns` задаёт полный набор исходных названий. Эквивалентные нормализованные названия можно сопоставлять через `binding`, но пропущенное поле или добавленное несуществующее поле не считается правильным.

Для edge вместо числовых фактов заданы `intent`, блок `clarification`, причина уточнения и минимум два содержательных примера вариантов. Формулировки можно менять, если сохранён смысл выбора. Пустой `tools_any` означает отсутствие необходимого аналитического вызова; безопасный осмотр через `describe_dataset` допустим. `tools_forbidden` не позволяет вычислить ответ по угаданной метрике, неподтверждённому источнику или выполнить запрос изменения данных. После уточнения выбранный расчёт начинается только после ответа пользователя.

## Проверка эталонов без модели

Эталонные числа вычислены независимым проходом полного исходного CSV через Python `csv` и стандартные числовые операции, без импорта `djedai`, вызова production-инструментов, DuckDB или LLM. Проверка подтверждает идентичность исходного файла, полноту популяций и значения, записанные в YAML. Она не проверяет ответы, траектории инструментария или уточнения реальной модели.

Из корня репозитория, с заранее полученным CSV вне Git:

```powershell
uv run --locked python scripts/verify_golden.py --data-file ../datasets/08_Фоновые_задания.csv --output ../artifacts/issue-79/golden-report.json
```

Если локального CSV нет, скачивание нужно включить явно. Используется закреплённый URL и обязательная проверка хэшей:

```powershell
uv run --locked python scripts/verify_golden.py --data-file ../datasets/08_Фоновые_задания.csv --download --output ../artifacts/issue-79/golden-report.json
```

Проверка только структуры YAML/manifest, без CSV, сети и расчёта значений:

```powershell
uv run --locked python scripts/verify_golden.py --validate-only
```

Успешный `--validate-only` не означает подтверждения эталонов по полному CSV. Для воспроизведения нужен обычный запуск с исходным файлом. Сгенерированный JSON-отчёт не добавляют в Git.

## Правила будущего scoring

`exact` применяется к целым счётчикам, минимумам/максимумам, медиане этого набора и временным границам. Даты сравниваются по моменту с точностью до секунды с учётом МСК, а не по дословному форматированию. `exact_unordered` означает полный набор значений или пар значение/частота: порядок строк неважен, пропущенная категория и лишняя категория — ошибки. Для `top3` пустые коды исключены; на границе текущей тройки нет равенства частот.

`approx` с абсолютным допуском 0.005 допускает округление среднего и процента до сотых. Эталон хранит значение до округления. Процент хранится в шкале 0–100; доля 0–1 требует явного перевода единиц. Значения 0, 0.00, нулевой процент и пропуск — разные понятия.

Для будущих top-N с равными частотами #80/#81 должны явно задать вторичный порядок либо принимать все допустимые перестановки и варианты на границе ties. Нельзя закреплять случайный порядок SQL-движка. Для обзора используется включение обязательных фактов, а не exact совпадение всего текста. Для уточнения проверяются отсутствующий выбор, варианты и отсутствие угаданного расчёта, а не одно слово «уточните».

Проверки инструмента, числа, единицы/популяции, текста ответа и provenance нужно отражать раздельно. Альтернативный корректный `run_sql` допустим вместо описательного инструмента, если он работает с выбранными пользовательскими данными и даёт полный ответ. Нельзя использовать raw-копию как дополнительную независимую таблицу, чужой dataset, данные тестовой заглушки или заранее сохранённый эталонный ответ.

В будущем реальном прогоне агенту передают обычный `question` и штатный каталог выбранного датасета. `expect`, oracle, готовые SQL, подсказки правильного плана и правильные ответы не передаются в промпт и не внедряются в инструментарий. Сравнение выполняется после ответа. Факты, которые уже входят в штатный каталог, остаются нормальным контекстом приложения.
