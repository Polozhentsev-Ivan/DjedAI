## Источник, единицы и границы

Используется полный `08_Фоновые_задания.csv`: 500000 строк, 15 полей, 122084672 байта. Manifest `datasets/hk_background_jobs.json` фиксирует ревизию `716fbbcdc3dfa2a63dba1cf835fcc780c5e91a1d`, URL, SHA-256 и Git blob SHA-1, SQL binding и популяции. CSV и сгенерированные отчёты остаются вне checkout.

Одна строка — попытка фонового задания, код цепочки объединяет несколько попыток. Повтор цепочки не является полным дублем. Нули участвуют в статистике; пустой код ошибки не доказывает успех, поскольку есть отменённые попытки. Денежных показателей и других пользовательских таблиц здесь нет. Месячные и квартальные группировки используют начало попытки в МСК (UTC+03:00); raw-копии и служебные таблицы не являются бизнес-таблицами.

Все сценарии адаптированы к этому источнику. Они не подтверждают межтабличные JOIN, подключения БД или работоспособность конкретной функции. `synthetic_expectations.json` сохраняет отдельные синтетические эталоны #48.

## Формат и будущая оценка

Корень YAML — список. У вопроса есть стабильный `id`, `scenario` (1–10 или `edge`), `dataset`, `question`, `expect` и при необходимости `context`.

- `facts` содержат буквальный проверенный эталон, правило сравнения и единицу; `population` определяет строки, фильтры и знаменатели. Результаты инструмента, числа в ответе и смысл текста оцениваются раздельно.
- `tools_any` перечисляет допустимые зарегистрированные инструменты. Корректный альтернативный SQL допустим; точная строка SQL и число вызовов не закреплены. Вызов случайного подходящего инструмента не заменяет правильных результатов.
- `tools_planned` отдельно перечисляет дополнительные допустимые инструменты из спецификации, ещё не зарегистрированные на момент подготовки набора; `manifest.planned_tools` связывает их с issues. Это альтернативы инструментам из `tools_any`: корректный SQL допустим вместо специализированной функции. `requirements` отмечает нужные возможности (графики, дашборды, память и расширенная аналитика). Это требования к выполнению кейса, а не отметки его успеха. Runner должен проверять фактическую готовность на своей ревизии и явно различать fail, skip и blocked; исторический статус инструмента не является причиной блокировки, если нужный расчёт уже доступен.
- `must_explain` и `must_not_claim` задают смысловую рубрику. Дословный шаблон ответа не требуется. `answer_contains_value.from_result` требует происхождения чисел из реального результата; одно происхождение ещё не доказывает правильность эталона.
- `outcome: clarify` требует содержательного уточнения и вариантов до выбора расчёта; безопасный осмотр каталога допустим. `reject` требует понятного отказа без аналитических/опасных вызовов.
- `input_error` проверяет границу приложения: UI не отправляет пустой вопрос, прямой API отвечает 422, модель не вызывается. Это не ошибка качества ответа LLM.

`exact` проверяет точное значение, `exact_unordered` — полное мультимножество строк без зависимости от порядка (включая кратность). `approx` задаёт абсолютный допуск в явно указанных единицах: например, 0.005 для округления до сотых и отдельный малый допуск для Pearson. Процент 0–100 не подменяется долей 0–1. Boolean не является числовым счётчиком. Для top-5 сервисов вторичный порядок при равенстве — название по возрастанию. Для временных рядов отображение должно сохранять хронологию, даже если сравнение набора строк допускает иной порядок.

### Контекст, графики и дашборды

`context.previous_cases` содержит только ID уже объявленных вопросов того же датасета; `same_chat: true` требует исполнения в одном чате. Для каждого оцениваемого кейса runner начинает отдельный чат, рекурсивно собирает зависимости в порядке объявления, удаляет повторные ID и реально исполняет эти вопросы. При сбое предпосылки продолжение блокируется с причиной. Подготовленные ответы ассистента, `expect`, SQL oracle и эталонные ID не подставляются в историю.

`reuse_result_from` требует реального результата указанного предыдущего хода. При смене вида графика новый SQL-вызов не обязателен. Это не разрешает подменять результат фикстурой.

`expect.chart` определяет допустимые типы ChartSpec, смысл и тип оси X, единицу Y, числовой `data_fact`, число точек и обязательную ссылку на сохранённый результат. Поля осей должны существовать в колонках этого результата. Полный ряд из 24 месяцев нельзя обрезать стандартным `limit=20`; сведения должны совпадать с независимым фактом.

`expect.dashboard` требует сохранённый дашборд и виджеты с проверяемыми метриками, допустимыми типами графиков и воспроизводимыми рецептами пересчёта. Widget ID в рубрике — смысловая метка, а не ожидаемый UUID. `dashboard_link` без реально сохранённого объекта и данных недостаточен. Refresh читает тот же источник; зависимости рецепта хранят `source_step_id`, а не старые `result_id`. На неизменном CSV числа после refresh сохраняются, ссылки результатов проверяются по фактическим вычислениям.

## Методы новых эталонов

Счётчики и группировки учитывают все попытки, включая повторные и отменённые; ошибки определяются статусом «Ошибка». Полный дубль сравнивает все исходные поля. Средняя длительность считается по строкам с обоими timestamp. Показатели по окружению имеют собственный знаменатель.

В дневном календаре от минимальной до максимальной даты включены и дни без запусков (ноль). Среднее по номеру месяца/дню недели делится на все соответствующие календарные дни в этом диапазоне. День недели: 0 — понедельник, 6 — воскресенье. Максимум при равенстве выбирается по меньшему номеру. Небольшая разница средних на двух годах описывает наблюдения и не доказывает устойчивую сезонность.

Pearson между счётчиками использует попарно непустые значения за попытку; дневной Pearson даёт одинаковый вес каждому дню. Нулевая дисперсия означает неопределённый коэффициент, а не 0. Для лага L сопоставляются attempts[t] и errors[t+L], то есть положительный лаг означает, что X предшествует Y. Проверяется диапазон −7…7 только на пересечении дат (без циклического сдвига и заполнения краёв); выбирается максимальный |r|, при равенстве — меньший |L|, затем меньший L. Корреляция не доказывает причинность; число ошибок является частью числа попыток.

Прогнозные кейсы задают метод словами в самом вопросе. Семь будущих дней повторяют последние семь календарных значений в прежнем порядке (seasonal naive, период 7); горизонт начинается после максимальной даты источника. Сценарий +10% умножает каждое ожидание на 1.1 без округления до целых. Backtest откладывает последние семь дней и прогнозирует их только по предшествующей неделе; MAE сравнивает прогноз с отложенными наблюдениями. Фактические holdout-значения не используются для обучения. Это проверяемые условные расчёты, без утверждения известного будущего или откалиброванного доверительного интервала.

## Воспроизведение без модели

`scripts/verify_golden.py` проверяет структуру и независимо пересчитывает числовые факты через Python csv/Counter/Decimal, без импорта приложения, DuckDB и LLM. Все минимумы групп, контекст, визуальные рубрики и ссылки фактов валидируются автоматически.

```powershell
uv run --locked python scripts/verify_golden.py --validate-only
uv run --locked python scripts/verify_golden.py --data-file ../smoke-cp1/artifacts/hk-datasets/08_Фоновые_задания.csv --output ../artifacts/issue-80/full-source-check.json
uv run --locked pytest tests/unit/test_golden_references.py tests/unit/test_golden_scenarios.py -q
```

Отсутствующий файл можно явно скачать с закреплённого URL, добавив `--download`; проверяются размер и оба хеша, существующий кэш не заменяется. Другой путь к полному CSV разрешён. Для `--validate-only` не нужны CSV, сеть или модель; результат `structure_valid` сопровождается `oracle_verified=false`.

Обычный запуск подтверждает весь исходный файл и значения, а не качество агента. В JSON отражаются число вопросов и проверки каждого факта с единицей/популяцией; `agent_evaluation=not_run` сохраняется при любом результате. Независимый повторный oracle и отчёты разработки хранятся вне Git в `artifacts/issue-80/`.

## Прогон агента

`scripts/eval_runner.py` исполняет вопросы через настоящий граф агента на закреплённом CSV. Датасет один раз загружается штатным конвейером в DuckDB; граф получает реальный каталог и диспетчер инструментов, поэтому SQL выполняется по golden-таблице, а не по mock-базе.

```sh
uv run --locked python scripts/eval_runner.py \
  --data-file ../smoke-cp1/artifacts/hk-datasets/08_Фоновые_задания.csv \
  --output ../artifacts/issue-81/eval-report.json \
  --workers 2
```

`--data-file` обязателен; размер и SHA-256 сверяются с manifest. Если файла ещё нет, добавьте `--download`. Отчёт версии 2 содержит `summary` (`passed`, `failed`, `skipped`, `blocked`, `pending`) и по каждому вопросу статус, длительность, `thread_id`, план с SQL/аргументами, полные `tool_results`, `answer_blocks`, intent и проверки фактов. `answer` включает текст уточнений и отказов, а не только блоки `text`. Старые основные поля сохраняются; потребитель должен учитывать `schema_version`.

JSON записывается атомарно до начала вопросов и после каждого результата. Пока прогон идёт, `status=running`, у ожидающих вопросов `status=pending`; `summary.total` — число вопросов, взятых в работу, без skipped. У завершённого отчёта `status=completed`, `pending=0`. Прерванный после запуска отчёт помечается `interrupted`; он не выдаётся за полный результат.

`skipped` получают неподдерживаемые требования и `input_error`; `blocked` — невыполненная или упавшая предпосылка из `context.previous_cases` либо вопрос к другому датасету. Дубликаты ID отвергаются до инициализации модели: разные кейсы не могут делить checkpoint. Пропущенный и заблокированный вопрос не считается успешным.

Список `capabilities` строится по фактическому реестру инструментов. Runner принимает зарегистрированные альтернативы из `tools_any` и `tools_planned`: например, `time_aggregate` допустим для месячных группировок. Требования `seasonality` и `segments` включаются при наличии соответствующих инструментов; возможности `charts`, `dashboards`, `correlation` и `forecast` выполняются и проверяются по содержанию. Снимок `tools_planned` в golden не объявляет текущий реестр неизменным и не означает автоматический пропуск уже реализованной функции.

Контекстные вопросы выполняются в одном чате с реальной историей: зависимости разрешаются рекурсивно, исполняются до целевого вопроса и при сбое блокируют продолжение. Каждый предварительный ход сохраняется в `context_results`. `duration_seconds` измеряет целевой ход, `total_duration_seconds` включает контекст. Каждый ход использует штатный `AGENT_TURN_TIMEOUT_SECONDS` (по умолчанию 120 с), попытки модели — штатные таймауты и retry. Диагностика стадий/попыток и последний checkpoint сохраняются также при таймауте; ключ клиента и сырой ответ провайдера не сериализуются.

Терминальные ошибки API, верификатора и инструментов отбрасывают результат до проверки фактов и intent. Проверка intent остаётся строгой: `off_topic` вместо ожидаемого `invalid` — ошибка классификации. Отдельные `safety_checks` показывают запрещённые запланированные/выполненные вызовы, поэтому такой провал не смешивается с выполнением опасного SQL. Запрет учитывает и новые инструменты реестра; правильный intent не скрывает запрещённый вызов.

Эталон и ответ проверяются раздельно. Каждый факт сверяется по `comparison` (`exact`, `exact_unordered`, `approx` с допуском) только с результатами инструментов: текст ответа не является доказательством, поэтому правильный SQL не маскирует неверное число в ответе, а верное число в тексте не заменяет отсутствующий результат. Числовые ячейки коллекций сравниваются по значению, поэтому `CAST(COUNT(*) AS DOUBLE)` даёт `454882.0`, равное эталонному `454882`; при сверке результата сохраняются пары категория–значение, порядок (где он задан) и кратность строк, поэтому перепутанные счётчики и substring-совпадения не проходят.

Коллекции могут быть проекциями объединённой SQL-таблицы: из «квартал, попытки, ошибки» извлекаются две пары, при этом все строки и их связи должны совпасть. Полные коллекции не принимают лишние строки. Только явно названные факты `*.topN` могут выбрать N лидеров из большего частотного результата, без NULL-категории и с проверкой ранга. Поиск проекции ограничен, сочетания значений ячеек не материализуются.

Для `july.change_percent` и `production.error_percent` готовая процентная ячейка SQL необязательна: checker может вычислить процент по заданной формуле, предварительно подтвердив соответствующие `july.counts` либо оба счётчика production. Нулевой знаменатель и неподтверждённый источник не допускаются. Формула, ключи источников и вычисленное значение сохраняются в `fact_checks.derivation`. При таком выводе отдельно требуется правильный процент в ответе с учётом округления: случайное совпадение процента с числом строк SQL не оправдывает ошибку. Произвольные отношения ячеек для других эталонных фактов не перебираются.

Месячные и квартальные бакеты сопоставляются с `YYYY-MM`/`YYYY-QN` в МСК; произвольная дата внутри месяца не принимается за начало бакета. Для `dataset.columns` используются соответствия исходных и SQL-имён из фактически загруженного каталога; совпадения числа колонок недостаточно. `empty` с явными нулевыми фактами допустим, пустой результат сам по себе не придумывает ноль. Единственная загруженная таблица позволяет вывести отсутствие межтабличных связей.

Отдельно проверяются числа самого ответа при `answer_contains_value.from_result`: каждое число должно происходить из результата инструмента. Допускаются округление результата, масштаб «тыс.»/«млн», процент или доля с явной единицей/контекстом, выведенные из чисел результата, и константы, заданные в самом вопросе (например, порог 3600 секунд). Случайное отношение двух ячеек не оправдывает неверный счётчик строк. Число без источника делает кейс `failed`, даже если эталон подтверждён SQL. Даты, годы, календарные кварталы, номера пунктов и числовые префиксы SQL-идентификаторов не считаются измеренными значениями. Число в backticks остаётся проверяемым, если это числовое значение, а не идентификатор. Обычные утверждения «2024 строки» или «59 запусков» по-прежнему требуют подтверждения.

Отчёт разделяет две оси:

- `automated_status` (`passed`/`failed`) — данные, инструменты, графики, дашборды, числа в ответе.
- `semantic_status` (`passed`/`partial`/`not_evaluated`/`failed`) и список `semantic_rubrics`, где каждая рубрика `must_explain`, `must_not_claim`, `clarification.*` имеет свой статус.

Итоговый `status`: `failed`, если упала любая ось; `passed`, только если все рубрики подтверждены; иначе `needs_review` — автоматика прошла, но смысл должен оценить человек. `needs_review` не засчитывается как принятый ответ и не блокирует зависимые вопросы: их блокирует только `automated_status=failed`. Сводка `summary` считает обе оси и рубрики отдельно.

Счёт читается по двум числам: `automated_passed` и `needs_review`. `passed` при неоценённых рубриках почти не будет, поэтому его малое значение не означает плохой результат. Старый счёт вроде 15 из 22 получен по другим правилам и с новым напрямую не сравнивается.

Кодом оцениваются только вещи со структурным или точно проверяемым свидетельством: подмена прогноза фактом holdout, вывод об объёме данных из результата с `LIMIT`, число цепочек или кодов, названное строками, и несоответствие названия дня недели номеру. Всё остальное получает `not_evaluated`, потому что поиск ключевых слов не отличает «это выручка» от «это не выручка». Значения больших чисел из эталона также должны попасть в текст ответа, если он не опирается на таблицу, график или дашборд: подтверждения результатом инструмента недостаточно.

Порядок строк при `comparison: exact` важен только для календарных рядов и рейтингов (`top*` или слово «порядок» в единице); категории с метками сопоставляются по метке.

Эталон графика (`chart.data_fact`) сверяется только с колонками, которые график рисует: X, цвет и Y. Верные числа в соседней колонке результата проверку не проходят. Для графиков виджетов дашборда такой привязки нет: это отмечено как `widget_chart_axes` в `not_evaluated`.

Для дашбордов проверяются виджеты, их факты и пересчёт рецептов инструментами приложения с новыми `result_id` и теми же значениями. У прогонщика нет БД приложения, поэтому перезапуск и чужой владелец перечислены в `dashboard_checks.not_evaluated`; их проверяют `tests/integration/test_dashboard_chat.py` и `tests/integration/test_owner_isolation.py`.

Отдельная CI-проверка измеряет минимум 80% покрытия именно runner и сравнения значений, помимо покрытия приложения:

```sh
uv run --locked pytest tests/unit/test_eval_runner.py tests/unit/test_eval_validation.py tests/integration/test_eval_runner_runtime.py --cov=scripts.eval_runner --cov=eval_values --cov-report=term-missing --cov-fail-under=80
```

В модель передаются только пользовательские вопросы и штатный каталог. Golden, oracle и готовые ответы остаются на стороне оценки. Наличие ожидаемого графика, дашборда или прогноза не означает готовность соответствующей функции.

## Вопросы организаторов

`organizer_questions.yaml` содержит шесть вопросов из `TestCases.md`, каждый на своём датасете, и эталоны, посчитанные напрямую из CSV. Manifest каждого вопроса лежит в `datasets/organizer/q<N>.json`. Запуск по одному вопросу, файл датасета должен совпасть с хешем manifest:

```bash
.venv/bin/python scripts/eval_runner.py --questions eval/organizer_questions.yaml --manifest eval/datasets/organizer/q6.json --data-file artifacts/hk-datasets/08_Фоновые_задания.csv --workers 1 --output <файл>
```

Вопросы других датасетов в таком запуске получают `skipped`. Неверный ответ получает `failed`: эталон сверяется с результатами инструментов. В вопросах 3 и 4 допуск покрывает `quantile_cont` и `quantile_disc`.
