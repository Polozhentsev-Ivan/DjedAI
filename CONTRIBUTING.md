# DjedAI — соглашение о совместной разработке

Памятка для всех участников команды. Она определяет порядок работы с кодом; функциональный объём, архитектуру и критерии задач берём из технической спецификации проекта и согласованного плана issues.

## 1. Задача → ветка → PR

- Перед началом берём issue в работу и назначаем себя исполнителем. Владелец зоны ответственности помогает с профильными решениями; взять задачу может любой участник.
- Ветка создаётся от актуальной `main`: `feat/53-csv-import`, `fix/76-number-verification`, `docs/99-local-start`.
- Один PR решает одну понятную задачу. Связанные изменения кода, тестов и документации входят в тот же PR; посторонний рефакторинг выносим отдельно.
- В `main` изменения попадают через PR после проверки и ревью. Для объединения используем squash merge; итоговый коммит получает название PR.
- Изменение общего контракта заранее обсуждаем с владельцем и потребителями формата. Обновляем схему, примеры и затронутые интеграции в рамках согласованного изменения.

## 2. Коммиты

Используем формат [Conventional Commits](https://www.conventionalcommits.org/en/v1.0.0/):

```text
type(scope): краткое описание действия (#номер-issue)
```

`type`, `scope` и краткое описание действия в заголовке пишем по-английски. Развёрнутое описание в теле коммита — по-русски. Номер issue указываем, если изменение относится к задаче. Коды вроде `B1-1` остаются в названиях issues; дублировать их в каждом коммите не требуется.

| Тип | Когда использовать |
|---|---|
| `feat` | Новая возможность |
| `fix` | Исправление ошибки |
| `refactor` | Изменение устройства кода без изменения поведения |
| `test` | Добавление или исправление тестов |
| `docs` | Документация |
| `build` | Зависимости, сборка, контейнеры |
| `ci` | Автоматические проверки |
| `chore` | Прочие технические изменения |

Зоны: `data`, `analytics`, `agent`, `ui`, `backend`, `auth`, `contracts`, `infra`, `deps`. Если общей зоны нет, `scope` можно опустить.

```text
feat(data): support multiple CSV uploads (#53)
fix(agent): remove unverified numbers from answers (#76)
test(auth): check access to another user's result (#103)
build(deps): update the pinned DuckDB version
```

Коммит должен быть логически цельным. Из названия должно быть понятно изменение; сообщения `fix`, `update` и `готово` без пояснения не используем. Кодировку файлов сохраняем UTF-8.

## 3. Pull request и ревью

Название PR оформляем как коммит: `feat(data): support multiple CSV uploads (#53)`. Описание PR пишем по-русски.

Короткий шаблон описания:

```markdown
## Что изменилось
Какую проблему решает PR и какое поведение получилось.

## Связанные задачи
Closes #53

## Проверка
- Выполненные команды и их результат.
- Покрытие тестами и существенные проверенные случаи.
- Ручной сценарий или скриншот для изменений UI.

## Ограничения
Незавершённые части, известные проблемы или «нет».
```

- `Closes #…` ставим, когда PR полностью выполняет критерии issue. Для раннего этапа или частичного результата пишем `Refs #…` и перечисляем, что готово и что осталось.
- Незавершённую работу можно показывать через Draft PR. Перед запросом ревью автор просматривает собственный diff и запускает проверки.
- Итоговый ревьюер — `@Polozhentsev-Ivan`; профильные вопросы и общие контракты проверяем с владельцами затронутых зон. Автор не принимает собственный PR: изменения самого итогового ревьюера проверяет другой участник, знакомый с затронутой частью.
- До merge устраняем замечания и падения проверок. В PR сохраняем команды, результаты и ограничения, чтобы проверку мог повторить другой участник.

## 4. Python и зависимости: используем uv

Окружением, зависимостями и запуском Python-команд управляем через `uv`. Зависимости проекта описываем в `pyproject.toml`, полный разрешённый набор фиксируем в `uv.lock`. Оба файла храним в Git; lock-файл обновляем через uv. Это обеспечивает установку согласованных версий на разных машинах. [Документация uv](https://docs.astral.sh/uv/guides/projects/).

- Все прямые зависимости, включая инструменты разработки, тестирования и optional-группы, имеют точную версию через `==`. Записи без версии, `>=`, `~=` и `*` для библиотек не используем.
- Транзитивные зависимости имеют точные версии в `uv.lock`; перечислять каждую из них вручную в прямых зависимостях не нужно.
- Зависимость из Git фиксируем полным commit SHA. Внешняя изменяемая ветка вместо версии не подходит.
- Если используется сборка Python-пакета, библиотеки в `build-system.requires` также фиксируем через `==`.
- Зависимости добавляем и обновляем через uv. Изменённые `pyproject.toml` и `uv.lock` включаем в один PR; отдельные списки установленных вручную пакетов не поддерживаем.
- Обновление библиотек делаем осознанно: в PR указываем старую и новую версии, причину и результаты проверок совместимости. Не обновляем весь набор заодно с несвязанной задачей.
- Точную версию Python, включая patch, фиксируем в `.python-version`; совместимость в `requires-python` согласуем с ней. Версию uv также фиксируем в инструкции установки и CI. Локальный запуск, CI и соответствующий контейнер используют согласованные версии.

Шаблоны добавления зависимостей — буквенные номера нужно заменить выбранными версиями:

```text
uv add "fastapi==X.Y.Z"
uv add --dev "pytest==X.Y.Z" "pytest-cov==X.Y.Z" "ruff==X.Y.Z"
```

Конкретные номера выбираем при создании окружения с учётом совместимости стека и оборудования для модели, затем записываем в файлы проекта. Эти примеры задают синтаксис, а не назначают версии библиотек.

После получения изменений:

```sh
uv sync --locked
```

Проектные команды запускаем через `uv run --locked …`. В CI также используем `--locked`: рассинхронизация `pyproject.toml` и lock-файла должна завершать проверку ошибкой, а не менять зависимости во время прогона. [Режимы синхронизации uv](https://docs.astral.sh/uv/concepts/projects/sync/).

## 5. Тестирование и покрытие

Новая и изменённая логика сопровождается автоматическими тестами в том же PR. Исправление ошибки включает регрессионный тест, который обнаруживает исходный дефект.

**Минимум — 80% покрытия строк собственного Python-кода приложения.** Добавляем проверки вместе с кодом с начала проекта. Ключевые сценарии правильности вычислений, доступа к данным и сохранения результатов проверяем независимо от общего процента.

- Измеряем весь собственный код приложения, включая модули, которые тесты не импортировали. Список пакетов или каталогов задаём в `tool.coverage.run.source` внутри `pyproject.toml`. Такая настройка позволяет учитывать неизмеренные файлы. [Настройка источников coverage.py](https://coverage.readthedocs.io/en/latest/source.html).
- Тесты, фикстуры, сторонний и сгенерированный код не входят в покрытие приложения. Исключения для собственного кода должны иметь конкретное объяснение в PR; исключать сложную логику ради процента нельзя.
- Проверяем обычный результат, существенные ошибки, пустые данные и граничные значения. Для кода с ветвлениями проверяем разные исходы, а не только успешный путь.
- Эталонные значения рассчитываем независимо от проверяемой функции. Наличие теста без содержательных утверждений о результате не считается проверкой поведения.
- Фикстуры небольшие и воспроизводимые; случайность имеет фиксированный seed. Тесты используют временные каталоги и отдельные тестовые БД и не зависят от порядка запуска.

### Какие проверки нужны

| Уровень | Что проверяем |
|---|---|
| Unit | Преобразование данных, расчёты, валидацию, состояние агента, форматирование и ошибки отдельных компонентов |
| Integration | Реальное взаимодействие с DuckDB/БД, API, миграциями, хранилищем, SSE и контрактами — в затронутых изменением частях |
| Сквозные проверки и eval | Пользовательский сценарий от входа и источника данных до ответа, графика или дашборда; качество агента на эталонных вопросах |

Быстрые unit-тесты не требуют GPU, работающей LLM или внешней сети. Модель в них заменяем управляемым fake/stub-ответом, чтобы проверять логику. Это не заменяет проверку реальной интеграции с моделью и оценку качества ответов.

Интеграционные тесты и прогоны с моделью помечаем отдельно (`integration`, `llm`) и описываем их окружение и команды. Перед merge запускаем проверки, затронутые PR; полный eval выполняем на чекпоинтах и при изменениях модели, промптов или поведения агента. Невыполненная проверка указывается в PR с причиной и не считается успешной.

Для проекта особенно важны:

- CSV: кодировки, разделители, пропуски, даты и сохранность ID с ведущими нулями.
- Аналитика: известные правильные значения, единицы, границы периодов, дубли, аномалии и ошибки параметров.
- SQL: запрет записи и обходов через файлы/сеть, лимиты и ограничение разрешённым датасетом.
- Авторизация: регистрация и сессии, два пользователя, чужие ID/списки/результаты/SSE, смена аккаунта и состояние UI.
- Агент: уточнения, ограниченные повторы, память, подтверждение чисел результатами инструментов.
- Хранение и дашборды: сохранность после перезапуска, воспроизводимое обновление и частичный сбой виджета.

## 6. Команды перед PR

Инструменты разработки — `ruff`, `pytest` и `pytest-cov`; их точные версии находятся в dev-зависимостях. Конфигурацию храним в `pyproject.toml`.

После создания каркаса проекта, dev-группы и настройки `coverage.source` одинаковый базовый прогон локально и в CI выглядит так:

```sh
uv sync --locked
uv run --locked ruff check .
uv run --locked ruff format --check .
uv run --locked pytest -m "not integration and not llm" --cov --cov-config=pyproject.toml --cov-report=term-missing --cov-report=xml --cov-fail-under=80
```

Это проверка покрытия строк; измерение ветвей можно запускать дополнительно. `--cov` без имени берёт источники из конфигурации, а `--cov-fail-under=80` завершает прогон ошибкой ниже порога. Маркеры `integration` и `llm` регистрируем в настройках pytest. [Параметры pytest-cov](https://pytest-cov.readthedocs.io/en/latest/config.html).

Если PR затрагивает БД, API или модель, дополнительно выполняем соответствующий интеграционный/LLM-прогон и указываем команду в PR. Документационные изменения проверяем чтением примеров и ссылок; искусственные тесты ради документации не нужны.

CI должен проверять согласованность lock-файла, линтер, форматирование, быстрые тесты и порог покрытия. Конкретные команды запуска сервисов и интеграционных проверок добавляем в README вместе с реализацией.

## 7. Технологические договорённости

- Стек берём из спецификации: DuckDB, согласованные библиотеки обработки и статистики, sqlglot, LangGraph, Pydantic v2, FastAPI/SSE, локальная модель и Compose. Открытые решения вроде Streamlit/Taipy и выбора БД приложения согласуем командой; эта памятка не выбирает их заново.
- Общие схемы используем из пакета `contracts`, без независимых копий между компонентами. Новым и изменённым общим функциям задаём аннотации типов.
- Форматирование и стиль проверяет Ruff; параметры едины для команды. Комментарии объясняют причины решений, а публичные интерфейсы — вход, выход и существенные ошибки.
- Параметры окружения, адреса, лимиты и настройки модели выносим в конфигурацию. `.env.example` содержит имена и безопасные примеры; реальные секреты и пользовательские данные не коммитим.
- Для внешних Docker-образов фиксируем точные версии, для воспроизводимых сборок — digest. Для модели фиксируем идентификатор весов, revision и параметры запуска. Плавающий `latest` не используем как версию проекта.
- Сохраняем принципы проекта: сырые данные неизменны; числа ответа приходят из инструментов; графики получают данные по `result_id`; результаты вычислений сохраняются; доступ ограничен владельцем; основной сценарий работает локально.

- [ ] Пройдены базовые и затронутые интеграционные проверки; результаты и ограничения записаны в PR.
- [ ] Зависимости зафиксированы, lock-файл согласован; изменённые контракты и инструкции обновлены.
- [ ] Автор просмотрел diff и запросил ревью `@Polozhentsev-Ivan` и профильных участников, если требуется; для PR самого итогового ревьюера приглашён другой участник.
