# Production browser journey — #175

Ручная воспроизводимая проверка связи UI, API, графа, SQL и хранения.
Скрипт запускает production React/nginx и backend в отдельном Compose-проекте,
настоящую PostgreSQL и управляемый HTTP endpoint модели. API приложения не
подменяется, MSW не используется. Это transport-регрессия, а не оценка качества
живой LLM и не запись шести вопросов организаторов.

## Запуск

Нужны Linux/WSL, Bash, Git, Docker Engine/Compose v2, Node и npm из
[frontend/package.json](../frontend/package.json). Из корня checkout:

```sh
npm --prefix frontend ci
cd frontend
npx playwright install --with-deps chromium
cd ..
bash scripts/test-journey.sh /absolute/path/outside-checkout/journey-run
```

Используйте новый каталог для каждого запуска: существующий `journey-report.json`
скрипт не перезаписывает. Сборка требует доступа к реестрам/пакетам; PostgreSQL
адаптер может скачать расширение DuckDB при первом подключении.

Скрипт не включает локальный CI. Он принудительно использует `.env.example`,
новое имя проекта `djedai-journey-*`, динамические loopback-порты и собственный
том. Пароли аккаунтов и ключ шифрования генерируются на запуск. PostgreSQL
не публикует порт на хост; тестовые DSN/пароли из fixtures действуют только
в одноразовой БД. Модельный endpoint находится внутри тестового стенда.

После успеха или ошибки `trap` сохраняет Compose-лог и удаляет только этот
проект с его томами. Рабочая `.env` и рабочее приложение не используются.
Не запускайте отдельные фазы браузерного скрипта против пользовательской установки:
изменение источника и проверка сбоя рассчитаны на одноразовые fixtures.

## Данные и независимые ожидания

[orders.csv](../tests/fixtures/journey/orders.csv) содержит четыре заказа:
три январских на 12, 30 и 8 и один февральский на 900. Одна строка — заказ.
В январе категории A/B дают 42/8, регионы North/South — 20/30. Февральские
900 намеренно не входят в результат: потеря периода в продолжении обнаруживается.
[targets.csv](../tests/fixtures/journey/targets.csv) независимо задаёт план North/South
100/200. Эти буквальные ожидания в браузерном тесте не вычисляются SQL приложения
и не передаются модельной фикстуре.

PostgreSQL загружается из тех же файлов при инициализации. Через UI выбираются
`public.orders` и `public.targets`; `orders` — представление над `order_rows`.
После сохранения
дашбордов runner увеличивает первый заказ на 10: повторное открытие должно
показать прежний снимок, а явный refresh — новые 30/30 по регионам.
Для другого пользователя загружается собственный CSV с первым заказом 112:
его категории должны дать 142/8, а ресурсы первого пользователя недоступны.

## Что проверяется

1. Регистрация/вход через UI, загрузка обоих CSV и подключение PostgreSQL через
   форму, готовность каталога и создание чата для нужного датасета.
2. Вопрос о сумме `amount` по `category` за январь 2025: точные строки результата,
   выбранные оси, настоящий SQL, `result_id`, происхождение и завершение verify.
3. «А теперь то же самое по регионам»: тот же чат, сохранённый январский период,
   новый результат 20/30. Модельная фикстура отказывает, если runtime не передал
   историю и результат текущего чата.
4. Смена вида на линейный: прежний `result_id`, без нового вызова инструмента.
   «Как посчитано» открывается в браузере. Два графика — факт и независимый план —
   сохраняются через UI в один дашборд, читаются по прямому URL и после reload.
5. Разрыв SSE через reload при удержанном модельном запросе: причина прерывания
   сохраняется, POST не повторяется, новый вопрос успешно обрабатывается.
6. Выход/смена аккаунта: старый токен отозван, личные списки пусты, чужие dataset,
   chat, dashboard и result ID/refresh отвечают 404, собственный расчёт использует
   данные второго пользователя. Чужой дашборд не отображается в UI.
7. После изменения PostgreSQL все сервисы перезапускаются с прежними томами.
   Сохранённые определения совпадают; refresh без активного хода и без вызова LLM
   выдаёт новые `result_id` и правильные числа для CSV и PostgreSQL.
8. В одноразовой PostgreSQL первый `amount` становится отрицательным. Тестовое
   представление `orders` для этого значения выполняет невалидный CAST;
   схема источника остаётся прежней. Refresh должен показать ошибку фактического
   виджета без старого графика; соседний план остаётся успешным и получает новый
   результат. API при этом не подменяется. Изменение самой схемы проверяло бы
   другой случай: общий отказ `catalog_stale`, а не частичный сбой вычисления.

Числа проверяются по сохранённым данным, на которые ссылаются таблицы/графики.
Текст управляемой модели не содержит самостоятельных числовых выводов;
прохождение verify здесь не доказывает способность живой модели формулировать
или проверять произвольные числовые утверждения.

## Отчёт и границы приёмки

`journey-report.json` фиксирует полный SHA, признак незакоммиченных изменений,
scope, завершённые проверки, сохранённые и обновлённые дашборды. Фазы последовательно
дают `prepared`, `restart_verified` и только после проверки частичного сбоя —
`passed`. Ошибка даёт `failed`, её фазу, текст страницы и screenshot; ненулевой
exit code команды, включая сбой очистки, не считается успешным запуском.
Рядом сохраняются `application-sha.txt`, `worktree-status.txt`, `compose-run.txt`,
`compose.log` и PNG ключевых экранов. Отчёт не хранит токены сессий или пароль аккаунта.

Выполнение этого сценария закрывает автоматизацию transport-пути #175.
Протокол на реально объединённом SHA и включение в итоговую регрессию #51
выполняются после ревью/merge; текущая ветка сама по себе не является принятой
финальной сборкой. Качество/скорость живой модели и её смысловые ответы
проверяются отдельно [eval-прогоном](../eval/README.md), а сценарии организаторов —
в #243/#244. ClickHouse, все типы графиков и полный UX-аудит этим сценарием не покрыты.
