# Время выполнения и отмена хода агента (#158)

Один явно отправленный вопрос получает общий монотонный deadline. Он создаётся
после проверки доступа и создания runtime, перед запуском рабочего потока чата.
Загрузка контекста, граф, инструменты, сетевые попытки, паузы и повторные
plan/compose используют оставшееся время этого же бюджета. Получение HTTP-ответа
не сбрасывает deadline; медленная передача по одному байту его не продлевает.

## Настройки

Переменные из `.env.example` читаются общей `LimitSettings`. Изменение требует
пересоздания backend: `docker compose up -d --force-recreate --wait`.

| Переменная | По умолчанию | Допустимо | Значение |
| --- | --- | --- | --- |
| `AGENT_TURN_TIMEOUT_SECONDS` | 120 | `0 < x <= 600` | Весь ход агента, секунды |
| `MODEL_TIMEOUT_SECONDS` | 60 | `0 < x <= 600` | Одна HTTP-попытка, секунды; дополнительно ограничена остатком хода |
| `MODEL_MAX_RETRIES` | 1 | целое `0..3` | Дополнительные сетевые попытки одного модельного вызова |
| `MODEL_RETRY_DELAY_SECONDS` | 0.5 | `0..10` | Начальная пауза, секунды; далее удвоение на каждом повторе |

Пустое значение использует default; неверные границы, NaN и бесконечность
отклоняются конфигурацией. Нулевое число повторов отключает их. Меньший таймаут
попытки позволяет повторить временный сбой внутри общего бюджета; больший
никогда не продлевает ход. Лимит инструмента `TOOL_TIMEOUT_SECONDS` также
ограничен остатком хода. Значения длительности могут быть дробными.

120 секунд сохраняют возможность успешного пути, измеренного примерно за 104 с
на текущем профиле модели, и обрывают воспроизведённое ожидание 193,8 с. Это
эксплуатационный компромисс: более медленный успешный путь тоже может быть
прерван. 60 секунд оставлены для одной попытки; один повтор вместо прежних двух
снижает число бесполезных запросов, но позволяет восстановиться после
кратковременного сбоя. Верхняя граница 600 с защищает от случайного многоминутного
наращивания лимитов и согласована с текущим nginx read timeout. Из-за накладных
расходов для пользовательского запуска общий бюджет лучше держать ниже 600 с.
Эти настройки ограничивают ожидание, но не ускоряют генерацию модели.

## Повторы и ошибки

Внутренние повторы OpenAI SDK отключены (`max_retries=0`). Одна прикладная политика
повторяет сетевые сбои/таймауты и HTTP 408, 429, 500, 502, 503, 504. HTTP 401/403,
прочие постоянные ошибки, неверный URL и пустой/непригодный ключ не получают
сетевых повторов. Ошибочный JSON и нарушение схемы также не повторяются клиентом.
Существующие циклы исправления plan/compose ограничены исходным deadline.

Статус и заголовки HTTP-ошибки обрабатываются сразу после получения. Тело ошибки
не загружается: медленная передача 401/403 не превращает постоянную ошибку в
повторяемый timeout, а 429/503 сохраняют Retry-After. Успешный ответ по-прежнему
полностью читается в пределах таймаута попытки и общего бюджета.

`retry-after-ms`, `Retry-After` в секундах или HTTP-дате имеют приоритет над
экспоненциальной паузой. Если указанная пауза исчерпывает остаток бюджета,
дополнительная попытка не начинается и возвращается ошибка провайдера. Некорректный
заголовок использует обычную паузу. После исчерпания общего бюджета поток получает
ровно один терминальный `event: error` с `code: "turn_timeout"` и русским текстом.
`done` после него не отправляется. Черновик из compose не публикуется и не
сохраняется сообщением assistant, если verify не успел завершиться.

Числа по-прежнему проверяются через verify. Ошибка самого провайдера на verify
удаляет неподтверждённый текст по существующему правилу; deadline его не ослабляет.
Клиент не повторяет POST автоматически. Новый вопрос требует явного действия и
получает собственный бюджет; поздние события прежнего хода ему не передаются.

## Отмена и освобождение ресурсов

«Остановить» в браузере сначала сохраняет отмену конкретного вопроса через
`POST /api/chats/{chat_id}/messages/{message_id}/cancel`, затем прерывает fetch.
При ожидании первого подтверждения приёма вопроса или ответа отмены действует
ограничение ожидания 5 с. Разрыв соединения или отзыв сессии
закрывает SSE и выставляет флаг отмены. Сетевой транспорт проверяет его и время
не реже чем раз в 50 мс; активный async HTTP-запрос отменяется с закрытием
ответа/сокета. Ожидание сетевой очистки ограничено одной секундой. Ответ API
дополнительно ждёт завершения рабочего потока не более одной секунды.
Проверка отзыва сессии выполняется существующим SSE guard с интервалом 200 мс.

В тестах локального управляемого сервера предусмотрен допуск: до 1,5 с для
завершения сетевого вызова и до 2,5 с сверх бюджета для завершения API-ответа.
Это допуск на планирование и очистку ресурсов, а не дополнительные попытки.
DuckDB получает `interrupt()` при отмене или deadline; таймер останавливается
до повторного использования соединения. Рабочий поток владеет своей сессией и
соединением и закрывает их в `finally`.

Сохраняемые исходы, коды ошибок и восстановление после перезагрузки описаны
в [chat-turns.md](chat-turns.md). Они используют бюджет и транспорт #158;
политика сетевых повторов и значения лимитов не изменены.

Запись assistant в файловую SQLite выполняется отдельной короткой транзакцией:
после flush ещё раз проверяется активность хода перед commit. Блокировки записи
и commit обрабатываются без внутреннего ожидания SQLite, с откатом и паузами
в пределах бюджета. Отмена или deadline прекращают эти попытки; освобождение
блокировки позже не приводит к сохранению прежнего ответа. Таймаут соединения
SQLite восстанавливается до возвращения соединения в пул.

Системный DNS resolver может завершить фоновую работу позже: чат не ждёт его,
HTTP-соединение после отмены не создаётся. Синхронное чтение файлов или
произвольный сторонний Python-инструмент нельзя принудительно остановить внутри
потока. SSE всё равно прекращается по deadline; результат проверяется перед
следующим этапом/публикацией, а ресурсы такого расширения закрываются при возврате.
Новые инструменты должны учитывать `current_budget()` и отмену при длительной работе.
Проверка авторизации и создание runtime до запуска хода не входят в этот бюджет.

## Воспроизводимая проверка

Без ключа, GPU и внешнего inference:

```sh
uv run --locked pytest tests/unit/agent/test_deadline.py tests/unit/backend/test_chats.py -q
```

Тесты используют настоящий SDK и локальный HTTP-сервер: зависание до заголовков,
медленный body, timeout → success, 429/5xx/401/403, длинный Retry-After, остановка
во время запроса/паузы, повтор plan/compose, прерывание DuckDB. Живой API проверяет
разрыв TCP, logout во время запроса, последующий вход и новый вопрос. Отдельный
сценарий останавливает настоящий граф на verify и проверяет отсутствие черновика
в SSE и истории.

Локальный прогон 23.10.2026 на собранных production-образах backend/frontend,
через nginx и отдельный том, с управляемой моделью и бюджетом 2 с:

| Сценарий | Время HTTP-запроса целиком | Результат |
| --- | --- | --- |
| Модель не отправляет ответ | 2,272 с | Один `turn_timeout`, модельное соединение закрыто |
| Модель зависает на verify | 2,242 с | Один `turn_timeout`, черновика в SSE/истории нет |
| Следующий вопрос, 429 → success | 0,386 с | Один повтор, полный путь с verify и `done` |

Модель получила 10 попыток суммарно, два зависших соединения закрылись. В истории
остались три вопроса и только один подтверждённый ответ. Это проверка управления
временем и восстановления, без внешнего inference и оценки качества модели.
Повтор после интеграции #157: журнал содержит ровно 10 попыток и исходы
`timeout`, `timeout`, `success`; обе прерванные попытки имеют тип `TIMEOUT`.

Регрессионные проверки ревью дополнительно удерживают блокировку записи и
читающую транзакцию SQLite до завершения хода. Рабочий поток закрывается ещё
при удерживаемой блокировке, assistant отсутствует после её освобождения,
следующий вопрос сохраняет единственный новый ответ. Проверяется также отзыв
хода после INSERT до commit, откат и восстановление таймаута соединения.
Для медленных тел 401/403 и 429 с Retry-After 600 с остаётся одна попытка;
503 с коротким Retry-After восстанавливается через разрешённый повтор.

Журнал #157 записывает фактические попытки этой политики; внутренние повторы SDK
остаются отключены. Исключения deadline и отмены сохраняются как TIMEOUT/CANCELLED
на попытке, модельном вызове, этапе и ходе, а не как неизвестная ошибка.
