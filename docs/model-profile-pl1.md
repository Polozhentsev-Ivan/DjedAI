# PL-1: профиль модели и реальные замеры

Дата: **20 октября 2026 года**. Обновлено: **26 октября 2026 года** (#159).
Решение: **DeepInfra / Qwen3.6-35B-A3B**.
Пользователь разрешил внешний инференс с открытыми весами до 80B суммарных
параметров. У выбранных [официальных весов](https://huggingface.co/Qwen/Qwen3.6-35B-A3B)
35B параметров, 3B активных и лицензия Apache-2.0. DeepInfra указывает
[FP8 и контекст 262 144 токена](https://deepinfra.com/Qwen/Qwen3.6-35B-A3B).
235B-модель предыдущего smoke-прогона исключена из нового профиля.

## Конфигурация

| Параметр | Значение |
| --- | --- |
| Endpoint | `https://api.deepinfra.com/v1/openai` |
| MODEL_NAME | `Qwen/Qwen3.6-35B-A3B` |
| Ответ | strict JSON Schema, temperature=0.1, max_tokens=2048 |
| Reasoning | По стадиям: `MODEL_REASONING_UNDERSTAND`, `_PLAN`, `_VISUALIZE`, `_COMPOSE`, `_VERIFY`; сейчас везде `provider_default`, параметр провайдеру не передаётся |
| Поддержка reasoning | Подтверждена для DeepInfra Qwen3.6-35B-A3B 25.10.2026; в шаблоне `MODEL_REASONING_SUPPORTED=false` как защита при смене модели/endpoint; ненулевой режим при `false` останавливает запуск, а не игнорируется |
| Timeout | 60 с на попытку; до двух SDK-повторов транспортных ошибок |
| Контекст приложения | Бюджет 8192 токена, включая резерв ответа 2048; сокращение входа/истории относится к #77 |
| Серверные веса/runtime | Стабильный API ID; SHA обслуживаемых весов, сборка runtime и GPU/VRAM провайдером не раскрыты |
| Локальное оборудование | RTX 4070 Laptop, 8188 MiB VRAM; веса локально не размещались |
| Среда клиента | Windows, Python 3.13.16, зависимости `uv.lock` |

Это управляемый профиль, а не воспроизводимая локальная сборка весов. Для смены
ID или провайдера повторяются описанные ниже замеры. Полное окно 262 144 не
проверялось; успешная контекстная проба содержала **3964 входных токена** по
usage API. Бюджет 8192 — решение для реализации памяти, не заявление о
проверке каждого размера входа до этой границы.

## Reasoning по стадиям (#159)

Режим reasoning задаётся отдельно для пяти модельных стадий. Допустимые
значения: `provider_default`, `none`, `low`, `medium`, `high`.
`provider_default` не добавляет `reasoning_effort` в запрос и сохраняет прежнее
поведение провайдера/модели; остальные значения передаются как
`extra_body={"reasoning_effort": ...}` в OpenAI-совместимом Chat Completions.
Фактически отправленное значение и исходная настройка попадают в диагностику
(`reasoning_effort`, `reasoning_setting`).

На 25 октября 2026 года поддержка `reasoning_effort` для
`Qwen/Qwen3.6-35B-A3B` через DeepInfra подтверждена на выбранном endpoint:
минимальные запросы с `none` и `high` вернули HTTP 200, а `high` при
достаточном лимите выдал reasoning-контент и обычный ответ. Это проверка
конкретной пары «модель + endpoint», а не свойство любого
OpenAI-совместимого API. Шаблон `.env.example` сохраняет
`MODEL_REASONING_SUPPORTED=false` как безопасное значение для копирования:
поддержка зависит от модели и может измениться при смене ID или провайдера.
Перед использованием `none`/`low`/`medium`/`high` флаг включают явно; в
замере ниже это делал `--reasoning-supported`. При `false` такой профиль
останавливает запуск, а не игнорируется. DeepInfra по-прежнему предупреждает,
что модель без reasoning может молча проигнорировать параметр, поэтому
подтверждение относится только к проверенной паре. Ответ провайдера с отказом
возвращается как ошибка модели; повтор с `provider_default` и автоматическая
подмена профиля не выполняются.

Текущий рабочий профиль не изменён: все пять стадий остаются
`provider_default`. Консервативный кандидат для проверки ускорения:

| Стадия | `proposed` | Почему |
| --- | --- | --- |
| understand | `none` | классификация intent и выбор уточнения |
| visualize | `none` | выбор представления по уже готовым данным |
| plan | `provider_default` | SQL, JOIN, фильтры и выбор метрики |
| compose | `provider_default` | формулировка чисел и единиц |
| verify | `provider_default` | проверка чисел перед публикацией не отключается |

Кандидат не включается по умолчанию и не считается безопасным, пока реальное
сравнение не покажет отсутствие регрессий. Сложные вопросы и проверка чисел
сохраняют reasoning.

## Метод

[benchmark_model_profiles.py](../scripts/benchmark_model_profiles.py) — текущая
версия harness для #159. Она отправляет 15 стадийных случаев и одну контекстную
пробу (16 случаев; при трёх повторах — 46 стадийных запросов), а также 8 полных
ходов по три повтора каждого (24 хода) по одному и тому же фиксированному
синтетическому датасету. Стадийные случаи покрывают understand (COUNT и
неоднозначные продажи), plan (COUNT, SUM по регионам, фильтр+JOIN,
отсутствующие возвраты, валюты, процент), compose (COUNT, валюты, процент,
отсутствие данных), verify (валидный и заведомо неверный черновик) и
visualize. Полные ходы повторяют эти вопросы через граф, включая execute,
compose и verify. Контекстная проба выполняется один раз на профиль.

Данные полностью искусственные: 4 заказа, клиенты, пустая таблица `refunds` и
таблица `sales` с двумя метриками без выбранной по умолчанию. Ожидания
(`4`, суммы по регионам/валютам, 50%, отсутствие данных) вычислены вручную по
этим строкам, а не взяты из проверяемого SQL. SQL исполняется штатным реестром
инструментов в отдельной DuckDB; для неоднозначности нужны `intent=ambiguous`
и непустой clarification; для графика — непустой ChartSpec с result_id и осями.
Ошибки инструмента и неисполняемые планы не обрывают серию.

Отчёт разделяет:
- `stage_latency_seconds` — время отдельного стадийного запроса;
- `turn_latency_seconds` — общее время полного хода;
- `turn_stage_latency_seconds` — длительности стадий внутри полного хода;
- токены каждого `model_call` из usage провайдера (`null`, если usage не пришёл).

Время стадии никогда не выдаётся за время ответа. p95 считается ближайшим
верхним порядковым значением по всем стадийным запросам серии, без
интерполяции; три повтора относятся к каждому случаю отдельно. Сравнение
профилей помечает семантические и schema-регрессии, а исходные ошибки baseline
перечисляет отдельно; `safe_to_enable=false` запрещает включать ускоренный режим.

```sh
# Сравнение baseline (все стадии provider_default) и proposed
# (understand/visualize = none, остальные provider_default).
# Флаг --reasoning-supported обязателен: без него клиент откажется запускаться
# с ненулевым режимом, а не проигнорирует его.
uv run --locked python scripts/benchmark_model_profiles.py \
  --model Qwen/Qwen3.6-35B-A3B \
  --base-url https://api.deepinfra.com/v1/openai \
  --env-file .env.deepinfra \
  --reasoning-profile baseline --reasoning-profile proposed \
  --reasoning-supported \
  --repeats 3 --turn-repeats 3 --context-lines 200 \
  --timeout 60 --max-output-tokens 2048 \
  --output artifacts/model-profiles/task10-comparison.json
```

Ключ читается из окружения или указанного `--env-file`
(`DEEPINFRA_API_KEY`, иначе `MODEL_API_KEY`). В примере используется локальный
`.env.deepinfra`; шаблон `.env.*` в `.gitignore` не даёт закоммитить ключ.
В реальной серии 25 октября применялся отдельный локальный env-файл с ключом
DeepInfra, также не входящий в Git. Команда сохраняет JSON в локальный `artifacts/model-profiles/`; ключ и
реальные данные в отчёт не попадают. Проверки CLI и оценщика работают без
внешнего API.

Серия 20 октября ниже использовала **прежнюю, более короткую версию** harness
(6 запросов и контекстная проба). Её числа нельзя смешивать с текущими 16+8
случаями или считать сравнением режимов reasoning.

## Сравнение режимов reasoning (#159)

Цель — прогнать `baseline` и `proposed` на одном датасете и одних вопросах,
по три повтора стадийных случаев и по три повтора каждого полного хода, и
сравнить schema, смысл, SQL, итоговые числа, токены и время. Команда приведена
в разделе «Метод». `verify` остаётся включённым в обоих профилях.

Реальная серия выполнена **25 октября 2026 года** через DeepInfra; начало
`2026-10-25T20:28:15Z`. Локальный отчёт:
`artifacts/model-profiles/task10-comparison.json` (в Git не входит). На каждый
профиль пришлось 70 проверок: 46 стадийных запросов (15 случаев по три повтора
плюс одна контекстная проба) и 24 полных хода (8 случаев по три повтора).

schema-регрессии на графиках. Это прямое нарушение правила «не включать
ускоренный режим при ухудшении ранее успешных сценариев».

### Качество по случаям

Тринадцать из пятнадцати стадийных сценариев прошли 3/3 по схеме и 3/3 по
смыслу в обоих профилях: understand с неоднозначностью; plan COUNT, SUM по
регионам, фильтр+JOIN, отсутствующие возвраты, валюты и процент; compose
COUNT, валюты, процент и отсутствие данных; verify валидного и неверного
черновика. Контекстная проба прошла 1/1 в обоих профилях. Исключения:

\* Для неоднозначного вопроса SQL не исполняется, а итоговых чисел нет по
замыслу: агент должен вернуть `intent=ambiguous` и непустой clarification.
Оба профиля сделали это 3/3.

Причина семантической регрессии `understand_count`: proposed в двух повторах
из трёх классифицировал «Сколько строк в таблице orders?» как
`data_overview`, а в одном из них ещё и не извлёк таблицу `orders`. Схема при
этом оставалась валидной, то есть schema-валидность не заменяет проверку
смысла. В baseline все три ответа были `data_question` с таблицей `orders`.

Schema-регрессии графиков вызваны `OUTPUT_LIMIT`: в proposed два запроса
visualize упёрлись в лимит 2048 выходных токенов (стадийный
`visualize_region`, повтор 2, и `turn_chart`, повтор 2), тогда как в baseline
схема этих случаев была валидной 3/3. Дополнительно `turn_chart` в proposed
дал пустые итоговые числа в повторе 1. Это не принято как допустимая плата за
скорость.

У baseline тоже есть исходные ошибки графиков, и они не приписаны proposed:
`visualize_region` — 1/3 по смыслу (в двух ответах пустые `x`/`y`);
`turn_chart` — 2/3 по смыслу (в одном повторе SQL-результат не совпал с
ожидаемым при верных итоговых числах). Поэтому графики остаются известным
ограничением качества, а не доказанно исправным сценарием. Отдельного
исправления графиков #159 не содержит.

### Решение и проверка harness

Рабочий профиль остаётся прежним: все пять стадий `provider_default`,
`proposed` — только кандидат для будущего замера. `verify` не отключается,
typed JSON Schema, проверка чисел перед публикацией и запрет выдуманных
результатов сохранены. Сложные вопросы и проверка чисел продолжают работать
с reasoning по умолчанию.

Без внешнего API проверен сам harness:
`uv run --locked pytest -q tests/unit/agent/test_model_benchmark.py` — **14 passed**.
Тесты подтверждают 16 стадийных (15 сценариев + контекстная проба) и 8 полных
случаев, независимые числовые ожидания, раздельное время стадии/полного хода,
учёт токенов, отличие schema-валидности от семантической корректности,
обработку исходных ошибок baseline и запрет включения профиля при регрессии.
Это проверка измерителя, а не качества Qwen3.6-35B-A3B.

Ограничения #159:
- серия выполнена на одном провайдере и endpoint 25.10.2026, по три повтора;
  latency управляемого API изменчива, p95 — описательная статистика, не SLA;
- синтетический датасет из 4 строк проверяет числа и SQL, но не заменяет
  полный eval #81 и продуктовые сценарии;
- контекстная проба выполнена один раз на профиль, максимальный prompt около
  11,4 тыс. токенов; полное окно 262 144 не проверялось;
- провайдер не отдаёт `reasoning_tokens`, поэтому расход reasoning не измерен;
- поддержка `reasoning_effort` подтверждена только для пары
  `Qwen/Qwen3.6-35B-A3B` + DeepInfra; при смене модели или endpoint флаг
  `MODEL_REASONING_SUPPORTED` и профиль проверяются заново;
- baseline-ошибки графиков остаются; ускоренный профиль не включается, пока
  они не разобраны и повторный замер не покажет отсутствие регрессий.

| Qwen3-32B | 18/19 | 18/19 | 15,776 | 77,069 |

У обеих большая контекстная проба завершилась транспортной ошибкой API.
Дополнительный запрос с 400 таблицами получил ReadTimeout около 60 с;
малые пробы с 50 и 200 таблицами прошли. Причина на стороне сети/endpoint
не локализована, поэтому большой контекст не считается подтверждённым.
В серии 20 октября инструкция явно отличает численный вопрос от общего обзора,
а проба ограничена 200 таблицами; сравнивать две серии как неизменный benchmark
или обещать скорость по одному прогону нельзя. Задержки управляемого API меняются.

35B-профиль выбран как разрешённый по размеру, с валидным JSON и реальным
сквозным SQL-прогоном. Доля невалидных схем в серии 20 октября ниже порога 20%
из PL-1. Это минимальная проверка выбора, а не полный eval и не SLA 30 с на ход:
лимит 30 с относится к одному инструменту, вызовы модели имеют отдельный timeout.

## Сквозная проверка 500 000 строк

После выбора выполнен [повтор CP1 smoke](cp1-smoke-run.md#повтор-на-модели-до-80b)
с лимитом генерации 2048 и timeout 60. COUNT всей таблицы, независимый CSV-парсер
и текст ответа дали 500000. SQLite, Parquet и DuckDB прочитаны новым процессом.
Прогон подтверждает минимальный путь без UI; issue #106 остаётся открытой.
