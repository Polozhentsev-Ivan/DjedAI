## 0. Что мы делаем — одним абзацем

Локальная платформа, в которую загружают сырые CSV (или подключают Postgres/ClickHouse), а дальше пользователь в чате на естественном языке спрашивает о данных и получает ответ текстом, графиком или сохраняемым дашбордом. Внутри: конвейер приёма и профилирования данных → каталог → LLM-агент (LangGraph), который **не считает сам**, а вызывает SQL и фиксированные аналитические функции → результаты сохраняются с id → фронт рендерит графики по декларативным спекам.

### Ключевые принципы (не обсуждаются без веской причины)

1. **LLM не производит чисел.** Каждая цифра в ответе пришла из результата инструмента (`facts` или `data`). Проверяется узлом-верификатором.
2. **LLM не кладёт данные в графики.** Спека графика ссылается на `result_id`, данные фронт берёт с бэкенда.
3. **Всё, что посчитано, сохранено.** Любой вызов инструмента → запись в хранилище результатов с параметрами и SQL. Отсюда «как посчитано», дашборды и контекст диалога.
4. **Исходные данные неизменны.** Сырые таблицы хранятся как есть; типизация и очистка — через view + лог трансформаций.
5. **Уточнить лучше, чем угадать.** На неоднозначный/некорректный вопрос — уточняющий вопрос с вариантами, отказ — в крайнем случае.
6. **Приложение локально.** Backend, UI и хранилища локальные; для инференса разрешён управляемый API открытой модели до 80B суммарных параметров (решение #47). Интернет — только белый список доменов, без поисковиков.

## 3. B1 — Data Layer (приём и профилирование)

**Ответственный:** **DE** — весь блок: движок загрузки CSV → DuckDB «на лету», разбор грязных CSV, вывод типов, связи по ID, профайлер, адаптеры БД, оптимизация SQL. Блок отдаёт наружу Python-интерфейс `DatasetService`: `ingest_csv(owner_id, sources)` и `connect_db(owner_id, dsn, tables)` возвращают `dataset_id` со статусом `processing`, `get_catalog(owner_id, dataset_id)` — готовый каталог. **BE** вызывает его из эндпоинтов загрузки (B5-3); сборка идёт в фоне. Сигнатуры, статусы и ошибки — [B1-10 / #62](decisions/62-data-interface.md).

### 3.1 Адаптер CSV

Вход: файл произвольного вида. Выход: таблица в DuckDB + запись в каталоге.

Шаги:
1. **Кодировка** — `charset-normalizer` (UTF-8, cp1251, UTF-16 и т.д.).
2. **Диалект** — разделитель (`, ; \t |`), кавычки, наличие заголовка (`csv.Sniffer` + эвристики; fallback — DuckDB `read_csv(auto_detect=true)`).
3. **Загрузка сырой таблицы** — `raw_<table>` все колонки как VARCHAR (ничего не теряем).
4. **Вывод типов по колонке** — пробуем по порядку: bool → int → float (вкл. `1 234,56`, `12,5%`, валюты) → date/datetime (несколько форматов, `dd.mm.yyyy`, ISO, unix ts) → category (низкая кардинальность) → text. Порог успешного парсинга — ≥ 95% непустых значений (`TYPE_PARSE_THRESHOLD`); защитные правила ID и неоднозначности применяются независимо от порога.
5. **Typed view** — `CREATE VIEW <table> AS SELECT TRY_CAST(...) ...` над raw.
6. **Нормализация имён колонок** — snake_case латиницей для SQL (`original_name` хранится в каталоге и показывается пользователю).
7. **Лог трансформаций** — каждое решение (какой формат даты, какой разделитель, сколько значений не распарсилось) пишется в `transformations`.

Крайние случаи для тестов: пустые строки в конце, BOM, разное число колонок в строках, дубли заголовков, колонка из одних пропусков, даты в двух форматах в одной колонке, ID с ведущими нулями (не превращать в int!).

### 3.2 Адаптер БД

- PostgreSQL: `ATTACH 'postgres://...' AS src (TYPE postgres, READ_ONLY)` → таблицы видны как `src.schema.table`.
- ClickHouse: выбранные таблицы копируются в DuckDB датасета через HTTP-интерфейс (`FORMAT Parquet`) под read-only пользователем, если их объём не больше порога (`CLICKHOUSE_MAX_ROWS`/`CLICKHOUSE_MAX_BYTES`); дальше — общий каталог и инструменты. Выбор по объёму — [решение #61](decisions/61-clickhouse.md), уточняет §7 решения #47.
- Типы берутся из БД, профайлер работает так же, как для CSV.

### 3.3 Профайлер

Для каждой колонки: тип, доля пропусков, число уникальных, уникальна ли, top-10 значений с частотами, min/max/mean/median/std для чисел, диапазон и гранулярность для дат, 5 примеров значений.

Для каждой таблицы: число строк, кандидаты в первичный ключ (уникальные non-null колонки, ID-подобные имена/паттерны), временные колонки, дубли строк (полные).

**Граф связей (ключевая фича):**
- Кандидаты — колонки с ролью `id` или высокой кардинальностью строкового/целого типа.
- Для пар колонок из разных таблиц с совместимым типом считаем на уникальных значениях `overlap = |A∩B| / |A|` — долю значений ссылки (`from`), найденных в ключе (`to`), — и Jaccard (на больших таблицах — на сэмпле / MinHash). Формула `/min(|A|,|B|)` даёт 1.0 для случайно вложенных диапазонов (`sale_id 1..4168` ⊇ `product_id 1..50`), поэтому `to` — уникальная сторона, а `/min` остаётся только для `N:M`.
- Связь, если `overlap ≥ 0.5` (`RELATION_MIN_OVERLAP`) при совпадении имён колонок; без него — только при почти полном покрытии и высоком Jaccard: `overlap ≥ 0.95` (`RELATION_UNNAMED_MIN_OVERLAP`) и `jaccard ≥ 0.5` (`RELATION_MIN_JACCARD`). Кардинальность (1:1, N:1, N:M) — по уникальности с каждой стороны; связь ориентирована от ссылки к ключу, поэтому `1:N` не выдаётся.
- Каждая связь проверяется JOIN-ом: число строк и суммы до и после; размножение строк и строки без пары понижают `confidence` и попадают в `warnings`.
- Выход — список `relations` в каталоге, LLM потом использует их для JOIN.

**LLM-обогащение (после статистики):**
- Описание каждой колонки на русском одним предложением по имени + примерам + статистике.
- Описание таблицы и общий `summary` датасета («Перед вами данные о продажах … за 2021–2024, 3 таблицы, связаны через client_id»).
- Делается батчем при загрузке, кэшируется в каталоге.

## 4. B2 — Analytics (инструменты)

**Ответственный:** **DA** (аналитические Python-инструменты). Логику сценариев (что считать «сезонностью», «аномалией», как формулировать `facts`) согласует с **PM/BA**; описания инструментов для LLM — с **MLE**.

### 4.1 Общие правила

- Все функции — чистые Python-функции, зарегистрированные в реестре: имя, pydantic-модель параметров, описание для LLM.
- Работают через DuckDB (агрегации в SQL), в pandas/polars тянут только уже агрегированное.
- Каждая возвращает `ToolResult` (4.3). Никаких «просто датафреймов».
- `facts` — короткие утверждения на русском **с уже подставленными числами**, которые LLM может цитировать.
- Таймаут на вызов — 30 с (`TOOL_TIMEOUT_SECONDS`), лимит строк в `data` — 5000 (остальное агрегировать/обрезать с флагом `truncated`).
- При ошибке — `status: "error"` с `error.suggestion` (например, «колонка `revnue` не найдена, похожие: `revenue`»).

### 4.2 Каталог инструментов

| Инструмент | Параметры (кратко) | Что делает | Сценарии |
|---|---|---|---|
| `describe_dataset` | — | обзор датасета из каталога: таблицы, объёмы, период, связи | 1 |
| `describe_column` | table, column | полный профиль колонки + описание | 2 |
| `value_counts` | table, column, top_n, filter? | частоты значений | 2, 4 |
| `run_sql` | sql | произвольный SELECT (read-only, через sqlglot, авто-LIMIT) | 2, 3, 4, 5, 8 |
| `time_aggregate` | table, time_col, measure, agg, freq (day/week/month/quarter/year), group_by? | ряд по времени | 3, 5, 7 |
| `find_duplicates` | table, columns? | полные и частичные дубли, примеры | 3 |
| `detect_anomalies` | table, time_col?, measure, method (iqr/zscore/stl-residual) | выбросы точечные и во временном ряду | 3 |
| `seasonality` | table, time_col, measure, period (7/12/…) | STL-декомпозиция, сила сезонности, пиковые периоды | 3, 7 |
| `segment_profile` | table, group_by[], measures[] | сводка по комбинациям признаков | 8 |
| `compare_segments` | table, segment_col, a, b, columns? | чем отличаются A и B: значимые различия (t-test / χ², effect size) | 8 |
| `correlation` | table, columns[], method | матрица корреляций | 9 |
| `lagged_correlation` | table, time_col, a, b, max_lag, freq | кросс-корреляция по лагам, лучший лаг, Granger (как «потенциальная», с оговоркой) | 9 |
| `forecast` | table, time_col, measure, horizon, freq | прогноз (ETS/ARIMA, опц. prophet) с интервалами | 10 |
| `what_if` **[stretch]** | table, driver, target, change | линейная/лог-лог регрессия, оценка эффекта изменения драйвера | 10 |

Cross-table функции принимают `table` как имя таблицы **или** результат `run_sql` (`source_result_id`) — тогда сначала JOIN делается SQL-ем, а функция работает по результату.

```jsonc
  "error": null,                                  // { code, message, suggestion }
  "created_at": "...",
  "duration_ms": 412
}
```

### 4.4 Безопасность `run_sql`

- Отдельное read-only соединение DuckDB.
- sqlglot: разрешён только `SELECT`/`WITH`; запрещены `ATTACH`, `COPY`, `INSTALL`, `PRAGMA`, функции чтения файлов.
- Если нет `LIMIT` — добавляется `LIMIT 5000`.
- Таймаут через `interrupt()`.
- Ошибка БД возвращается агенту текстом + подсказкой → агент может исправить запрос (макс. 2 ретрая).

## 5. B3 — Agent (LLM, LangGraph)

**Ответственный:** **MLE** — развёртывание и оптимизация локальной модели, промпты и граф, удержание контекста, цикл самоисправления SQL/вызовов, помощь BE в подключении агента к UI.

### 5.1 Граф

```
            ┌────────────┐
 message ──►│ load_ctx   │ каталог (сжатый) + история + реестр результатов чата
            └─────┬──────┘
            ┌─────▼──────┐   intent + ambiguity
            │ understand │──────────────┐
            └─────┬──────┘              │ ambiguous / invalid / off_topic
                  │ ok            ┌─────▼─────┐
                  │               │ clarify   │──► ответ-уточнение с вариантами (END)
            ┌─────▼──────┐        └───────────┘
            │ plan       │ какие инструменты, в каком порядке (≤ 5 шагов)
            └─────┬──────┘
            ┌─────▼──────┐ ◄──┐
            │ execute    │    │ ошибка инструмента → исправить параметры (≤ 2 ретрая)
            └─────┬──────┘ ───┘
            ┌─────▼──────┐
            │ visualize  │ нужен ли график; ChartSpec из chart_hint + вопроса
            └─────┬──────┘
            ┌─────▼──────┐
            │ compose    │ текст для бизнес-пользователя только из facts/data
            └─────┬──────┘
            ┌─────▼──────┐   детерминированно: число ∉ facts/data своего result_id,
            │ verify     │   чужая единица/период/популяция/знаменатель или
            └─────┬──────┘   неявная формула → перегенерация (2 раза) или ошибка
                 END → AssistantMessage
```

Сценарий «дашборд» — отдельная ветка после `understand`: агент планирует 3–8 виджетов собственным планом (не обычным планом на пять шагов), выполняет их, собирает `Dashboard`, сохраняет, отвечает ссылкой + превью.

### 5.2 Интенты (`understand`)

| intent | пример | дальше |
|---|---|---|
| `data_overview` | «Что передо мной?» | plan (часто 1 вызов `describe_dataset`) |
| `data_question` | «Какие значения встречаются чаще?» | plan |
| `visualize` | «Покажи, как это распределено» | plan + visualize обязательно |
| `modify_previous` | «А теперь в другом виде», «подробнее про второй пункт» | ссылка на `focus_result_ids`, без пересчёта если возможно |
| `dashboard` | «Создай дашборд с квартальной статистикой» | ветка дашборда |
| `hypothesis` | «Изменения C предшествуют росту D?» | plan со специальными функциями |
| `ambiguous` | «Покажи продажи» при 3 колонках-кандидатах | clarify с вариантами |
| `invalid` | колонки/сущности нет в данных | clarify: «такого поля нет, возможно вы имели в виду …» |
| `off_topic` | «Напиши стих» / вне данных | вежливый отказ + что система умеет |

Выход `understand` — JSON по схеме (guided decoding):

```jsonc
{ "intent": "data_question", "resolved_question": "Топ-10 значений колонки region в orders",
  "entities": { "tables": ["orders"], "columns": ["region"] },
  "references": ["r_15"],               // на какие прошлые результаты ссылается
  "clarification": null }               // { question, options: [..] } если нужно
```

### 5.4 Память (T7)

- Хранится на уровне чата (в БД B5).
- В промпт: последние 6–10 сообщений + краткое summary старых (генерится при превышении лимита).
- Каждое сообщение ассистента хранит `result_ids` → «второй пункт» разрешается через список блоков прошлого ответа.
- `focus_result_ids` обновляется каждым ходом.

### 5.5 Работа с моделью

- Все структурированные выходы — через guided decoding по JSON-схеме из pydantic.
- Температура 0–0.2 для `understand`/`plan`, 0.3–0.5 для `compose`.
- Промпты в `prompts/*.md` в репозитории, версионируются.
- Few-shot примеры для `plan` по каждому интенту.
- Если модель не тянет tool-calling в нативном формате — план как JSON-список вызовов, исполняет код.

## 6. B4 — Интерфейс

**Ответственные:** **BE** — реализация интерфейса и API; **DA** — участие в проверке понятности, текстов и сценариев; **MLE** — помогает связать агент с UI (стриминг шагов). Вайрфреймы и UX-проверка выполняются по B4-0/B4-9 и актуальному плану без отдельной PM-роли.

### 6.0 Выбор технологии — React + TypeScript

Утверждён отдельный browser frontend на **React + TypeScript** в `frontend/`. Инструменты — **Vite и npm**, lock-файл — `frontend/package-lock.json`. При создании приложения закрепляются совместимые версии Node/npm; прямые npm-зависимости записываются точными версиями, транзитивные — в lock-файле. Конкретные версии выбираются и проверяются при реализации, без предположений о текущих релизах. Воспроизводимая установка — `npm ci`, сборка — `npm run build`.

В B4-1 добавляются строгая проверка TypeScript, линтер, Vitest/React Testing Library и production-сборка в отдельном frontend CI; итоговый `required` учитывает его результат. Покрытие собственного TS/TSX — минимум 80% отдельно от Python, включая неимпортированные исходники; сгенерированные типы исключаются явно. Браузерные сценарии на Playwright проверяются по мере готовности соответствующих экранов.

Python остаётся в backend/data/agent и общем пакете `contracts/`. UI общается с FastAPI только через HTTP API и SSE: загрузка файлов — multipart, данные и каталоги — JSON, прогресс и шаги агента — SSE. Бизнес-расчёты, SQL, выполнение аналитики и перевыполнение виджетов остаются на сервере. В TypeScript выполняются отображение и преобразование `ChartSpec + data → ECharts option`; Python UI и импорт Python-моделей браузером не используются.

Источник схем — Pydantic-модели владельцев контрактов; TypeScript-типы генерируются из опубликованных API/OpenAPI/JSON Schema, включая схемы SSE и блоков, которые не следует считать автоматически покрытыми OpenAPI. В B5-1/B4-1 выбираются и фиксируются генератор и команда обновления; изменения схем сопровождаются регенерацией и проверкой совместимости API-клиента. В `frontend/src/` находятся интерфейс, API-клиент и генерируемые типы; отдельные ручные копии бизнес-контрактов не ведутся.

Зона B4 остаётся за BE с участием MLE по стримингу; смена языка не назначает нового владельца или исполнителя. Этапы CP1/CP2/FINAL и продуктовый объём сохраняются. Упаковка — статическая сборка frontend в локальном Compose (§7.4).

### 6.1 Экраны

1. **Источники данных** — загрузка CSV (drag&drop, несколько файлов), подключение к БД (форма), прогресс профилирования.
2. **Каталог** — таблицы, колонки (оригинальное имя, тип, описание, пропуски), граф связей (визуально), предупреждения и лог трансформаций.
3. **Чат** — сообщения с блоками (текст, график, таблица, уточнение-кнопки, подсказки), стриминг шагов агента («Смотрю структуру…», «Считаю сезонность…»), кнопка **«Как посчитано»** под каждым ответом (SQL/функция + параметры), кнопка «Добавить на дашборд» на графике.
4. **Дашборды** — список, просмотр (сетка виджетов), обновление (перевыполнение), открытие из чата по ссылке.
5. **Регистрация и вход** — формы локального аккаунта, выход, состояние истёкшей сессии и личные ресурсы; при выходе и смене пользователя закрываются потоки и очищается прежнее состояние UI. Полная проверка сессии и изоляции относится к AUTH/CP2; эта функция уже входит в согласованный план.

### 6.2 Контракт: `ChartSpec`

Своя упрощённая схема (не сырой Vega-Lite/ECharts — 27B будет её ломать). React-фронт транслирует её в ECharts на TypeScript, получая данные через `/api/results/{id}/data`; агрегаты и бизнес-значения рассчитываются сервером.

```jsonc
{
  "chart_id": "ch_9",
  "result_id": "r_17",                    // данные берутся GET /results/r_17/data
  "type": "line",                         // bar | line | area | scatter | pie | histogram | heatmap | box | table | kpi
  "title": "Выручка по месяцам",
  "subtitle": "Июльские пики повторяются каждый год",
  "x": { "field": "month", "label": "Месяц", "kind": "time" },   // kind: time | category | number
  "y": [ { "field": "amount", "label": "Выручка, ₽", "format": "money" } ],  // format: number | money | percent | int
  "color": { "field": "region", "label": "Регион" },              // опционально
  "orientation": "vertical",              // для bar
  "stacked": false,
  "sort": { "field": "amount", "order": "desc" },
  "limit": 20,
  "annotations": [ { "x": "2023-07-01", "text": "пик" } ]         // опционально
}
```

Правила выбора типа (дефолт, агент может переопределить по просьбе):
- время по X → `line` (или `bar` при ≤ 12 точках);
- категория + мера → `bar` (горизонтальный при длинных подписях / > 8 категорий);
- доля частей целого ≤ 6 категорий → `pie`;
- распределение одной числовой → `histogram`/`box`;
- две числовые → `scatter`;
- две категории + мера → `heatmap`;
- одно число → `kpi`.

### 7.3 API

| Метод | Путь | Назначение |
|---|---|---|
| POST | `/api/datasets/upload` | multipart, один или несколько CSV → `{dataset_id, status}` |
| POST | `/api/datasets/connect` | `{kind: postgres\|clickhouse, dsn, tables?}` → `{dataset_id}` |
| GET | `/api/datasets` | список |
| GET | `/api/datasets/{id}` | статус + `DatasetCatalog` |
| GET | `/api/datasets/{id}/events` | SSE прогресса профилирования |
| POST | `/api/chats` | `{dataset_id}` → `{chat_id}` |
| GET | `/api/chats?dataset_id=` | список чатов |
| GET | `/api/chats/{id}` | чат + сообщения |
| POST | `/api/chats/{id}/messages` | `{text}` → **SSE**: `status`, `tool_call`, `tool_result`, `block`, `done`, `error` |
| GET | `/api/results/{id}` | метаданные `ToolResult` (без rows) |
| GET | `/api/results/{id}/data` | `{columns, rows}` для рендера |
| GET | `/api/dashboards?dataset_id=` | список |
| POST | `/api/dashboards` | создать/сохранить (из UI «добавить на дашборд») |
| GET | `/api/dashboards/{id}` | `Dashboard` |
| POST | `/api/dashboards/{id}/refresh` | перевыполнить виджеты → новые result_id |
| PATCH | `/api/dashboards/{id}` | переименовать, layout, удалить виджет |

Web-контракт един для browser frontend и backend. В PL-1 согласуются API регистрации/входа/выхода/текущего пользователя и механизм сессии из AUTH-плана, передача сессии обычным запросам, multipart upload и обоим SSE-потокам, ошибки доступа и истечение сессии. Сервер определяет пользователя по проверенной сессии; переданный клиентом `user_id` не является основанием доступа. При выходе/смене пользователя UI закрывает потоки и очищает прежнее состояние и кэш. Эти проверки выполняются к AUTH/CP2; CP1 использует только согласованный режим разработки.

SSE передаётся как `text/event-stream` с полями `event:` и `data:` и пустой строкой между событиями. Примеры ниже показывают логическое содержимое, а не буквальный wire-формат. Для POST сообщения клиент читает поток через `fetch`/ReadableStream: нативный `EventSource` не отправляет POST. Для GET прогресса подходит `EventSource` либо тот же потоковый клиент с учётом выбранного способа сессии. Проверяются разделённые сетевыми чанками события, завершение, ошибка, отмена и разрыв; разрыв не должен автоматически повторять POST и запускать агент второй раз. Proxy не буферизует SSE. Форматы событий и ошибок входят в генерируемые схемы; multipart upload сохраняет контракт нескольких файлов и понятных ошибок.

Формат SSE-события:

```jsonc
{ "event": "status", "data": { "node": "execute", "text": "Считаю сезонность по выручке…" } }
{ "event": "block",  "data": { /* Block из AssistantMessage */ } }
{ "event": "done",   "data": { "message_id": "m_101" } }
```

### 7.4 Инфраструктура

- инференс — внешний OpenAI-совместимый API DeepInfra/Qwen3.6-35B-A3B; отдельный локальный `model-runtime` не требуется;
- `backend` — FastAPI + LangGraph + DuckDB (volume для данных);
- `frontend` — статическая сборка React/Vite из `frontend/`, обслуживаемая nginx; сборочный этап использует закреплённые Node/npm и `npm ci`, затем `npm run build`; `/api` проксируется в FastAPI, включая multipart и небуферизуемый SSE;
- метаданные/пользователи/сессии — SQLite в постоянном volume backend; отдельного `app-db` для локального MVP нет;
- `demo-postgres`, `demo-clickhouse` — профиль `demo`, с тем же датасетом, для показа T1.

Конфиг через `.env`: URL модели, имя модели, ключ, лимиты, белый список доменов. Один `make up` / `docker compose up` поднимает приложение. Внешний endpoint открытой модели до 80B разрешён пользователем 20 октября; выбранный профиль проверен через API, его ограничения и замеры приведены в решении #47. Compose не разворачивает веса провайдера.

## 8. Качество: eval-набор

**Ответственные:** **PM/BA** — golden dataset (вопросы, тестовые CSV, заранее известные правильные ответы), QA-прогоны; **MLE** — прогонщик и отчёт; **DA** — синтетический датасет с заложенными закономерностями.

Файл `eval/questions.yaml`, прогон `make eval` → отчёт (что прошло, время, какие инструменты вызваны).

```yaml
- id: s1_overview_01
  scenario: 1
  question: "Что есть в этих данных?"
  expect:
    tools_any: [describe_dataset]
    must_mention: ["3 таблицы", "2021", "2024"]
- id: s2_topvalues_01
  scenario: 2
  question: "Какие регионы встречаются чаще всего?"
  expect:
    tools_any: [value_counts, run_sql]
    answer_contains_value: { from_result: true }
- id: s8_invalid_01
  scenario: edge
  question: "Покажи прибыль по марсианским колониям"
  expect:
    intent: invalid
    blocks_include: [clarification]
```

Минимум: по 5 вопросов на сценарии 1–6, по 3 на 7–10, 10 «неудобных» (несуществующие поля, двусмысленные, вне темы, попытка `DROP TABLE` через чат, пустой вопрос).

Пока реальных данных нет, работаем на **синтетическом датасете** с заложенными свойствами: сезонность 12 мес., лаг 5 дней между C и D, дубли, аномалии, 3 таблицы со связью через ID. Так проверяем, что функции находят то, что заложено.

## 11. Риски

| Риск | Митигация |
|---|---|
| 27B-модель путается в tool-calling | guided decoding, короткий план (≤ 5 шагов), few-shot, фиксированные функции вместо свободного кода |
| Медленный инференс (> 30 с на ответ) | стриминг статусов, минимум LLM-вызовов на ход, кэш описаний каталога, замер в первый же день |
| Реальные данные сильно отличаются от синтетики | адаптер тестируем на грязных CSV, трансформации логируются и видны |
| Большие таблицы | всё в DuckDB, в Python — только агрегаты, сэмплинг в профайлере |
| LLM выдумывает числа | `facts` + `verify` + «как посчитано» |
| Связи между таблицами находятся ложно | порог overlap, `confidence`, показываем пользователю в каталоге |
| Расхождение контрактов между людьми и языками | один пакет `contracts/`, у каждого контракта один владелец (10.1); TS-типы генерируются из API-схем, при изменениях проверяются регенерация и совместимость клиента, включая SSE |
| Перегрузка BE (API + хранилище + React/TS UI) | распределение страховки в 10.1, ранний React-каркас и API-фикстуры, этапы CP1/CP2/FINAL по issues-plan; при нехватке времени первым упрощается экран каталога согласно 10.1 |
| Ошибки web-интеграции: SSE, сессия, upload | согласовать транспорт в PL-1; проверить поток, разрыв/отмену, multipart и истечение сессии через browser frontend и локальный proxy; не повторять POST автоматически |
