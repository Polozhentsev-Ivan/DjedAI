# Контракты и технические решения — PL-1 / #47

Дата: 20 октября 2026. Этот документ фиксирует решения для параллельной разработки.
Реализация отдельных функций и приёмка чекпоинтов остаются в своих issues.
До закрытия #47 осталось подтвердить условия финального инференса и приложить
замер выбранного профиля (§6). Остальные решения ниже определены.

Итоговые изменения общих форматов принимает Polozhentsev-Ivan. Владелец контракта
проверяет профильную часть; это не назначает его исполнителем всех связанных задач.
Внутренние `Block`/`ComposeResponse` агента — результат модели до преобразования
в `MessageBlock`, не отдельный публичный формат сообщения. В `AgentState.charts`
используется общий `ChartSpec`, без второй сокращённой модели.

График обязательно содержит `chart_id` и `result_id`. Значения для него читаются
через `/api/results/{result_id}/data`. Валюта в каталоге — ISO-код (`RUB`), UI
преобразует его в знак. Кратность связи — `N:M`, не `N:N`. Процент `12,5%` хранится
как `12.5`, не `0.125`. Неоднозначные даты и ID сохраняются по правилам #54/#55.

Общие схемы экспортируются командой
`uv run --locked python scripts/export_frontend_contracts.py` в
`frontend/schema/contracts.json`; `npm run gen:types` создаёт
`frontend/src/api/generated.ts`. Ручные копии общих моделей удалены из снимка UI.
Снимок `frontend/schema/openapi.yaml` фиксирует согласованные wire-форматы
эндпоинтов; реализация отсутствующих обработчиков остаётся в #94/#97/#102.
`DatasetSummary` содержит `source`, `table_count`/`row_count` (null при обработке)
и статус `processing|ready|error`; `DatasetDetail` добавляет каталог и ошибку.
`source.files` — метаданные списка, а не поле DatasetCatalog. DELETE датасета
выбран: только владелец, 204, отмена его выполняющихся задач и удаление
принадлежащих ему связанных объектов; реализация и проверка каскада — #94/#103.
Подробности — [README контрактов](../../src/djedai/contracts/README.md).

## 2. Хранение, идентификаторы и доступ

БД приложения и пользователей — **SQLite** через SQLAlchemy/Alembic, один backend.
DuckDB хранит аналитический контекст CSV; большие результаты — Parquet.
Переход на PostgreSQL нужен при нескольких backend или измеренной конкуренции
записи, с отдельной проверкой переноса данных и миграций. Выбор и основания уже
зафиксированы в [AUTH-1](101-auth-storage.md); PostgreSQL не является вторым
одновременно выбранным вариантом локального хранилища приложения.

Логин — уникальный `username` с учётом регистра. Пароль — Argon2id. Сессия —
непрозрачный случайный токен, в SQLite только SHA-256 verifier; 24 часа без
продления по активности, отзыв на logout. JWT и `SESSION_SECRET` не используются.
Токен однократно возвращается как `TokenResponse`.

Для JSON API, multipart и обоих SSE-потоков выбираем одинаковый транспорт:
`Authorization: Bearer <access_token>`. Браузер хранит токен в памяти и
`sessionStorage` текущей вкладки; в URL, `localStorage` и логи он не попадает.
Это не HttpOnly-cookie: защита от XSS обязательна, чужой JavaScript имеет доступ
к памяти страницы. После обновления вкладки UI проверяет `/auth/me`; после logout,
401 или смены пользователя отменяет потоки и очищает токен, workspace и кэш.
Refresh-token и sliding expiration в текущем протоколе отсутствуют.

Маршруты: `POST /api/auth/register` → 201/UserRead, `POST /api/auth/login` →
TokenResponse, `GET /api/auth/me` → UserRead, `POST /api/auth/logout` → 204 с отзывом
текущей сессии. HTTP-подключение этих правил — #102/#104; текущие AUTH-роутеры
ещё заглушки, закрытие PL-1 не означает их приёмку.

Владелец датасета, подключения, чата, результата и дашборда — `users.id`.
Текущий пользователь определяется проверенной сессией, не клиентским `user_id`.
Связанные ресурсы должны иметь одного владельца; `source_result_id` проверяется
с тем же контекстом. Списки фильтруются по владельцу, чужой ID отвечает 404.
Результат с `owner_id=NULL` не доступен через пользовательский API. Ключ
аналитического контекста — `(owner_id, dataset_id)`, временные представления
результатов ограничены одним выполнением. Применение этих проверок — #103/#105.

## 3. HTTP, поток, версии и публикация

- Префикс API — `/api`. Production UI и API имеют один origin: nginx проксирует
  `/api`, отключает буферизацию SSE, передаёт Authorization и допускает multipart.
  Dev использует Vite proxy; отдельные dev origins перечислены явно в
  `BACKEND_CORS_ORIGINS`, wildcard запрещён.
- Upload — `multipart/form-data`, повторяющееся поле `files`; Content-Type с
  boundary устанавливает браузер. Ответ 202 сообщает `dataset_id` и статус,
  прогресс идёт в `GET /api/datasets/{id}/events`.
- POST сообщения и GET прогресса читаются через `fetch`/ReadableStream, с Bearer
  и AbortSignal. Нативный EventSource не подходит для выбранного заголовка.
  Формат: `event: <имя>`, `data: <JSON>`, пустая строка; UTF-8 и сетевые чанки
  не совпадают с границами событий. Данные кадра — соответствующая модель SSE,
  без дополнительной обёртки `{event,data}` внутри `data:`.
- JSON-ошибка — `ErrorResponse = {"error": ToolError}`: `code`, `message`,
  `suggestion`. HTTP-код сохраняется. Валидация не отражает пароли/DSN из input,
  5xx не возвращает текст внутреннего исключения. После старта SSE ошибка идёт
  событием `error`, затем поток заканчивается без `done`.
- Порядок: инструменты → сохранение ToolResult → `compose` → `verify` →
  сохранение AssistantMessage → `block` → `done`. ToolResult может быть виден
  раньше текста; непроверенный черновик compose не публикуется. Backend учитывает
  замену/отклонение блоков узлом verify. Сам числовой verifier реализуется в #76.
  Разрыв не повторяет POST автоматически; клиент восстанавливает историю GET,
  новый запуск возможен только явным действием пользователя.
- Общая версия API — **0.2.0**: закрепляет обёртку ошибки и канонические типы UI.
  Старую плоскую ErrorResponse нельзя считать тем же wire-форматом. Каталог и
  рецепт содержат собственный `schema_version=1`; несовместимое изменение требует
  новой версии, обновления потребителей и миграции сохранённых объектов.

## 4. Воспроизводимый виджет вне чата

`Dashboard` — сохранённое определение. В виджете ровно одно из `tool_call`
(один независимый вызов) или `recipe` (цепочка). Шаг рецепта хранит `step_id`,
`call` и необязательный `source_step_id`; зависимости могут ссылаться только на
предыдущие уникальные шаги. `output_step_id` выбирает результат для визуализации.
Старые временные UUID `source_result_id` в рецепте запрещены.

Пример и частичный сбой — [component_exchange.json](../../src/djedai/contracts/examples/component_exchange.json).
Его рецепт заново читает ID из таблицы, затем считает строки свежего результата:

```json
{
  "schema_version": 1,
  "steps": [
    {"step_id": "rows", "call": {"tool": "run_sql", "params": {"sql": "SELECT id FROM missing_values"}}},
    {"step_id": "count", "source_step_id": "rows", "call": {"tool": "run_sql", "params": {"sql": "SELECT COUNT(*) AS n FROM source_result"}}}
  ],
  "output_step_id": "count"
}
```

Исполнитель refresh получает владельца и датасет от дашборда, проверяет доступ,
выполняет шаги по порядку и сохраняет каждый новый результат. Для зависимого шага
он подставляет **новый** result_id в `source_result_id`; `run_sql` видит этот
результат как локальное представление `source_result`. Имена/параметры инструментов
валидируются реестром; внешние файлы/сеть через SQL закрыты. Подключение этого
режима `source_result_id` и сам refresh реализуются в #97 с аналитикой, его ещё
нельзя считать работающим по наличию схемы рецепта.

Для этого не нужен активный чат и повторное обращение к LLM. `source_chat_id`
сохраняет происхождение, но не определяет контекст исполнения. Перед сохранением
зависимого виджета в рецепт переносят все необходимые предварительные вычисления;
неполный provenance отклоняют, не используют старый Parquet как исходные данные.
Параметры относительного периода вычисляются заново по данным, абсолютный период
остаётся фиксированным параметром рецепта.

Сохраняем исходную семантику: при открытии UI явно вызывает
`POST /dashboards/{id}/refresh`; GET определения сам не запускает вычисления.
Кнопка обновления вызывает тот же POST. Бюджет по умолчанию — 20 вызовов на весь
refresh, включая предварительные шаги и повторы: четыре виджета по пять шагов.
Это отдельный бюджет, не ограничение чат-плана в пять шагов; сам запрос инструмента
сохраняет лимит строк и таймаут.

Ответ refresh/открытия — `DashboardSnapshot`, содержащий `WidgetSnapshot` для
каждого виджета. Успешный/пустой исход получает свежий result_id, равный
`chart.result_id`. При сбое — `status=error`, `result_id=null`, понятная ошибка;
успешные соседние виджеты доступны. Старые подписи/спека могут остаться для
объяснения виджета, но старые данные не выдаются за свежий расчёт. Повторы и
ошибки относятся только к затронутой цепочке.

## 5. Пороги и лимиты

Единый набор — `djedai.config.LimitSettings`, значения из окружения или `.env`.
Backend Settings наследует эти поля; аналитика и типизация используют тот же
набор через `get_limits()`. Пустое значение означает default; нули, отрицательные
лимиты, бесконечность и доли вне допустимого диапазона отклоняются. После смены
окружения процесс перезапускают.

| Переменная | Значение | Правило |
| --- | --- | --- |
| TYPE_PARSE_THRESHOLD | 0.95 | Доля распознанных среди непустых, включая границу; ID/неоднозначность остаются защитными правилами |
| RELATION_MIN_OVERLAP | 0.5 | `|from ∩ to| / |from|` на различных непустых ID, направление ссылка → ключ |
| RELATION_UNNAMED_MIN_OVERLAP | 0.95 | Более строгая граница без совпадения имён |
| RELATION_MIN_JACCARD | 0.5 | Дополнительная граница без совпадения имён |
| SQL_MAX_ROWS | 5000 | Верхняя граница строк SQL; аргумент max_rows может её только уменьшить |
| TOOL_TIMEOUT_SECONDS | 30 | Таймер выполнения SQL и описательных DuckDB-инструментов |
| DASHBOARD_MAX_TOOL_CALLS | 20 | Весь refresh, включая зависимости и повторы |

Для overlap знаменатель `min(|A|,|B|)` отклонён: вложенные плотные диапазоны
посторонних ID давали ложное 1.0. Правила связей внедряются в #57/PR #140 и должны
читать указанные настройки, а не вводить второй набор констант. Аналогично #97
использует общий бюджет refresh. Их реализация не включается в PL-1 по наличию
решения о формате/значениях.

## 6. Инференс: оставшаяся точка решения

Подтверждённый профиль разработки — DeepInfra,
`Qwen/Qwen3-235B-A22B-Instruct-2507`: реальный SQL-прогон на 500 000 строк описан
в [протоколе CP1](../cp1-smoke-run.md). Это не замер локальной модели и не серия
измерений скорости/стабильности JSON. В #98 зафиксирован комментарий об
OpenRouter/Gemma, но нет численных метрик, ревизии весов или оборудования;
закрытый статус #98 не заменяет этих подтверждений.

На текущем компьютере проверена RTX 4070 Laptop с **8188 MiB VRAM**. Веса 32B
из старого `.env.example` не считаются выбранным профилем для этого устройства.
Отдельный GPU-сервер команды пока не подтверждён.

Предлагаемый локальный профиль для проверки на этом устройстве —
[Qwen/Qwen3-8B-GGUF](https://huggingface.co/Qwen/Qwen3-8B-GGUF), Q4_K_M,
контекст 8192, без thinking, через локальный OpenAI-совместимый runtime.
У официальных весов Apache-2.0; это кандидат для замера, не уже подтверждённый
запуск. Если внешний инференс разрешён для сдачи, используем проверенный
DeepInfra/Qwen без перехода на неподтверждённые free-модели.

В [исходном кейсе](../source/case-2-ai-native-bi.docx) указаны локальный запуск и
отсутствие облачных решений. Фраза §7.4 спецификации о разрешённом внешнем endpoint
не сопровождается подтверждением исключения. Поэтому до выбора финального
профиля нужны фактические условия: разрешён ли внешний инференс при сдаче и
какое оборудование доступно команде. Подтверждение условий нельзя заменить
успешным вызовом API.

После ответа фиксируем один основной профиль: точные веса/revision, runtime,
квантизацию, VRAM, рабочий контекст и параметры. Для управляемого API отдельно
фиксируем недоступные сведения провайдера, не придумывая их. Прикладываем серию
запросов схем Understand/Plan/Compose с временем и долей валидных ответов.
Более 20% некорректных ответов требуют исправления схем и повторного замера.
До этого пункт модели в #47 остаётся незавершённым.

## 7. Доступ к ClickHouse и внешние данные

Выбираем **прямое read-only выполнение в ClickHouse через clickhouse-connect**,
с pushdown фильтров, JOIN внутри источника и агрегатов; целую БД в DuckDB не
копируем. Каталог строится по метаданным и серверным профилям, примеры ограничены.
Локально сохраняются ограниченные ToolResult/Parquet, не скрытая полная выборка.
SQL для этого источника валидируется в диалекте ClickHouse; DuckDB SQL нельзя
просто передавать как будто это тот же диалект.

Доступ — отдельный read-only пользователь к разрешённым таблицам. Серверные
ограничения времени/памяти/чтения и число строк результата задаются адаптером;
превышение даёт ошибку (`overflow_mode=throw`), не частичный агрегат под видом
полного. Настройки и учёт распределённого запроса проверяются при подключении
источника. Это выбор проекта на основе
[ограничений ClickHouse](https://clickhouse.com/docs/operations/settings/query-complexity)
и [read-only доступа](https://clickhouse.com/docs/operations/settings/permissions-for-queries).

Объём реального ClickHouse и доступ к нему не предоставлены: это внешний блокер
проверки #61/#100. Опубликованный CSV и синтетика не заменяют проверку реального
подключения. Стратегия pushdown выбрана независимо от размера, чтобы объём
источника не требовал соответствующего объёма RAM на машине приложения.
