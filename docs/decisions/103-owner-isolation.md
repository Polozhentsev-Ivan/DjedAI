# Владельцы ресурсов и PostgreSQL — AUTH-3 / #103, B1-8 / #60

Дата: 22.10.2026. Основа — сессии #101/#102, хранилище #93 и read-only
PostgreSQL-адаптер #60. Это решение дополняет PL-1, не меняя Bearer-транспорт.

## Граница доступа

Все `/api/datasets`, `/api/chats`, `/api/results` и `/api/dashboards` требуют
проверенной сессии. Владелец берётся из неё, не из клиентского `user_id`, текста
модели или переданного ORM-объекта. Анонимный запрос получает 401. Чужой и
неизвестный ID получают одинаковый 404; списки содержат только свои объекты.
Связанные чат, датасет и результат должны иметь одного владельца. Результаты
с `owner_id=NULL` недоступны пользовательскому API. Ответы и ошибки личных API
не кэшируются (`Cache-Control: no-store`).

В SSE права проверяются до HTTP-заголовков и повторно во время потока, даже
когда источник не выдаёт событий. Отзыв/истечение сессии завершает поток
терминальным `error` с `data.code="unauthorized"`; клиент очищает только токен
этого запроса. Для агентного worker та же проверка служит сигналом отмены до
открытия источника и между шагами. Уже выполняющийся внешний вызов может
закончиться, но его ответ не передаётся отозванной сессии. Принятое профилирование
продолжается с неизменной парой `(owner_id, dataset_id)`: выход не меняет владельца
фоновой задачи и не передаёт её следующему вошедшему пользователю.

## Аналитика и файлы

Runtime повторно читает сохранённый чат и датасет до запуска модели. Контекст
открывается по `(owner_id, dataset_id)`; соединение ограничено выбранными
таблицами каталога. SQL/JOIN/CTE проверяются по этому набору. Сырые, системные и
невыбранные таблицы, пути CSV/Parquet/DuckDB, сетевые функции, `postgres_query`,
`postgres_execute`, динамические table functions и пользовательские macros
недоступны SQL агента. Неизвестная табличная функция отклоняется.

Файл датасета должен находиться в собственном каталоге ID, файл результата —
иметь точную ссылку `parquet://<result_id>.parquet`. Подмена пути и symlink
отклоняются до чтения. Перед выдачей результата проверяется вся цепочка
`source_result_id`, включая владельца и отсутствие циклов. Сохранение не может
перепривязать чужой/бесхозный результат. Табличные/графические блоки ответа
проверяются перед публикацией. Выполнение инструментов поверх `source_result_id`
пока явно отклоняется; будущая реализация обязана использовать этот же контекст.

Перед записью общего Parquet результат закрепляет свой ID и владельца через
уникальный ключ БД (`flush` в ещё не завершённой транзакции). Конкурентный INSERT
с тем же ID отклоняется до изменения файла; транзакция завершается после успешной
атомарной записи. При ошибке записи/commit выполняется rollback. Файл, оставшийся
после сбоя без записи БД, нельзя присвоить простой передачей `data_ref`: новый
результат должен материализовать собственные строки. Для новых результатов
используется полный UUID; безопасность не зависит от отсутствия коллизий.

## PostgreSQL

`POST /api/datasets/connect` принимает `kind="postgres"`, `dsn` и необязательный
список `tables`. Ответ 202, чтение статуса/каталога и progress SSE такие же, как
у CSV. На Python-границе используется `DatasetService.connect_db(...,
kind="postgresql")`. Выбранные таблицы проходят общий профайлер. Данные остаются
в PostgreSQL; локально сохраняются представления и каталог.

DSN и выбор таблиц хранятся в SQLite только как Fernet ciphertext, связанный с
владельцем и ID датасета. API, модель, каталог и сохранённые ошибки DSN не получают.
Сервер повторяет `ATTACH` только после проверки владельца; затем отключает
внешний доступ DuckDB. Применяются read-only ATTACH, read-only транзакции и
права роли PostgreSQL. Подключайте отдельную роль с одним SELECT.

Каждый PostgreSQL-контекст использует отдельный DuckDB instance в памяти:
файл датасета подключается в него read-only, а `pg_src` и временный секрет
принадлежат этому instance. Поэтому одновременно открытые чаты одного датасета
не отключают подключения друг друга. Таблицы PostgreSQL в память не копируются.

Для PostgreSQL задайте в backend `.env` `SOURCE_ENCRYPTION_KEY`. Сгенерировать
ключ можно из корня репозитория:

```sh
uv run --locked python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"
```

Ключ держат вне Git, он не является `VITE_*` и не входит в сборку frontend.
Сохраните его отдельно от резервной копии SQLite/файлов. После восстановления
используйте тот же ключ: потеря или простая замена делает сохранённые DSN
недоступными. Автоматической ротации пока нет. Без корректного ключа создание
подключения возвращает 503; CSV работает. После рестарта незавершённая обработка
CSV/PostgreSQL восстанавливается для прежнего владельца.

## Обновление и следующие задачи

Примените `uv run --locked alembic upgrade head` (Compose делает это сам).
Миграция добавляет nullable `datasets.source_secret` и сохраняет существующих
владельцев. `CP1_LOCAL_MODE` теперь относится только к прежней bootstrap-утилите
и никогда не заменяет Bearer. Compose задаёт false. Старые CP1-данные не удаляются,
но пользователь без пароля не получает сессию. Автоматической передачи этих
данных новому аккаунту нет; административный перенос требует отдельного решения.

Формы регистрации/входа, восстановление workspace и очистка QueryClient при
смене аккаунта — #104; итоговая пользовательская приёмка — #105. До подключения
форм браузерный smoke входит через настоящий auth API. HTTP/SQL двух владельцев
проверяются уже здесь. Дашборды/refresh и ClickHouse пока не реализованы:
их маршруты требуют сессию и проверяют доступные связанные ресурсы, затем
отвечают 501. Их будущая приёмка обязана повторить проверки владения, фоновых
задач, результатов и потоков; этот PR не объявляет эти функции готовыми.

## Воспроизведение проверок

```sh
uv run --locked pytest --strict-markers tests/integration/test_owner_isolation.py
uv run --locked python scripts/test_postgres_isolation.py --output /absolute/outside-repo/postgres-isolation.json
```

Второй сценарий требует Docker, сам создаёт и удаляет отдельный PostgreSQL и
проверяет две БД с одноимёнными таблицами и разными числами. При отсутствии Docker
он завершается ошибкой, а не успешным пропуском. Модель для этих тестов —
управляемая подмена, GPU/веса не нужны. Браузерные команды и smoke с API-входом
описаны в [frontend/README.md](../../frontend/README.md), PostgreSQL runner —
в [scripts/README.md](../../scripts/README.md).
