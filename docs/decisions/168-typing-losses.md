## Проблема

Typed view превращает нераспознанное значение в NULL (B1-2). SUM по такой колонке
молча пропускает значение, и пользователь получает неполную сумму без предупреждения.
Журнал знал число потерь только по всей таблице. Каталог хранил лишь
`parse.success_ratio`, а `ToolResult` никак не связывал качество преобразования с
конкретным расчётом.

## Решения

1. **Контракт `QualityReport`.** Отчёт лежит в `ToolResult.quality`. На каждую
   использованную колонку с ограничениями — `ColumnQuality`:
   - typed view и колонка, `raw_table`, исходное имя;
   - преобразование (действие журнала), целевой тип и формат;
   - использование: `measure`, `filter`, `join_key`, `group`, `output`;
   - знаменатель `rows` и отдельно `source_empty` (исходные NULL и пустые строки),
     `non_empty`, `parse_failed`, `failed_ratio`;
   - примеры нераспознанных значений;
   - ограничения `QualityIssue`: код, серьёзность, текст, варианты уточнения.

   Исходный пропуск — не ошибка разбора и не ограничение.
2. **Lineage через SQL.** `analytics/lineage.py` квалифицирует запрос схемой каталога
   (`sqlglot qualify`: раскрывает `*`, алиасы, `GROUP BY 1`). Для каждой ссылки на колонку
   lineage определяет использование и путь через CTE и подзапросы до таблицы каталога.
   Производное выражение (`amount * qty`) связывается со всеми исходными колонками.
   Всё, что не связалось, попадает в `unresolved`. Тогда `lineage="partial"`, а
   проверяются все колонки упомянутых таблиц по профилю.
3. **Популяция считается, а не берётся из профиля.**
   - Популяция колонки — scope, на строках которого она агрегируется или выводится.
     Колонка CTE без агрегации проходит наружу, и её популяция — строки внешнего
     запроса после его JOIN и WHERE. Агрегат, GROUP BY или DISTINCT в подзапросе
     останавливают проход.
   - `analytics/quality.py` копирует scope популяции без GROUP BY, HAVING, ORDER BY и
     LIMIT. Typed view в копии заменяется подзапросом над `raw_<имя>` с флагами
     «значение было» и «значение не распознано». Флаги проходят через CTE до scope
     популяции.
   - Строки без пары в LEFT JOIN не считаются ни пропусками, ни потерями.
   - Для фильтра считаются строки, которые условие отбросило из-за нераспознанного
     значения: `failed AND условие IS NOT TRUE` на строках без этого условия.
   - Условие `FILTER (WHERE …)` агрегата сужает популяцию меры так же, как WHERE.
     Колонка из самого условия — фильтр.
   - Ключ JOIN точно не посчитать: соединение по нему меняет саму популяцию. Он
     получает профиль таблицы с границей знания.

   SQL view берётся из `duckdb_views()`, а соединение чата открыто только на чтение.
   Поэтому старые датасеты не перестраиваются.
4. **Граница знания вместо выдуманного числа.** Если популяцию не посчитать
   (коррелированный подзапрос, UNION внутри подзапроса, ключ JOIN, ошибка запроса),
   берётся профиль таблицы из журнала. Тогда `scope="table"`, а `boundary` объясняет,
   почему точного числа нет. Контракт не даёт `table` без `boundary`.
5. **Одна колонка в нескольких популяциях.** Показывается популяция с наибольшим
   числом потерь.
6. **Порог сравнивается точно.** Сравнение идёт в `Decimal`. При float `0.55 * 100 =
   55.00000000000001`, и ровно 55 распознанных из 100 отвергались. Ровно на пороге
   колонка типизируется.
7. **Журнал фиксирует неоднозначности, которые раньше разрешались молча.**
   - `parse_date`: `ambiguous_values` и `alternative_formats`, если формат выбран по
     большинству.
   - `parse_percent`: `without_percent_sign`.
   - `keep_text`: `below_threshold` с кандидатом и долей, если подошло больше половины
     значений.
8. **Ограничение в ответе не зависит от модели.** Узел `cite_metrics` добавляет блок
   «Ограничения данных» из `ToolResult.quality`. Модель получает факты `data_quality`.
   Промпт compose запрещает называть неполный результат полным, verify отклоняет такой
   черновик.
9. **Blocking ведёт в уточнение.** Варианты начинаются с «таблица.колонка:». Ответ с
   этой ссылкой снимает блокировку, и в ограничениях отмечается «Выбор уточнён
   пользователем».
   - Чат сворачивает цепочку «вопрос — уточнение — кнопка — уточнение — кнопка» в одно
     сообщение: исходный вопрос и все выборы. Так две неоднозначные даты подряд не
     теряют вопрос и его популяцию.
   - Выбор действует только на вопрос, в котором сделан: агент ищет ответ лишь в текущем
     сообщении. Новый вопрос по той же колонке снова получает уточнение. В журнал
     выбор не сохраняется.
10. **Хранение.**
    - `results.quality` — миграция `f168qual0001`; отчёт отдаёт `GET /api/results/{id}`.
    - Блок ограничений хранится в блоках ответа.
    - После перезапуска ответ и «Как посчитано» показывают те же ограничения.

## Правила

| Код | Когда | Серьёзность |
| --- | --- | --- |
| `parse_losses` | в популяции есть нераспознанные значения меры, вывода или группировки | warning |
| `parse_losses` | фильтр отбросил строки с нераспознанным значением | warning |
| `parse_losses` | ключ JOIN с нераспознанными значениями (профиль таблицы, граница знания) | warning |
| `kept_as_text` | колонка ниже порога участвует в расчёте, фильтре или группировке | warning |
| `ambiguous_date` | день и месяц не различить, колонка в расчёте, фильтре или группировке | blocking |
| `ambiguous_date` | то же, колонка только выводится; или формат выбран большинством | warning |
| `mixed_currency` | колонка с несколькими валютами агрегируется | blocking |
| `mixed_currency` | деньги разных валют в одном выражении агрегата | blocking |
| `mixed_currency` | то же вне агрегата; колонка валют в фильтре или группировке | warning |
| `ambiguous_separator` | одиночный разделитель (`1,234`) принят за десятичный | warning |
| `percent_scale` | в процентной колонке есть значения без знака % | warning |
| `percent_sum` | проценты сложены | warning |

Любая потеря в популяции — warning, независимо от доли: неполная сумма не называется
полной. Единица и валюта, которых нет в каталоге, в ответ не добавляются. Живые
источники (PostgreSQL) не проверяются: типы задала БД, разбора не было.

## Вне задачи

- курсы валют и пересчёт;
- сохранение выбранного формата даты или валюты в каталог;
- раскладка потерь по группам GROUP BY: число дано на популяцию целиком;
- примеры нераспознанных значений именно из популяции: показываются примеры таблицы;
- переделка raw-таблиц и журнала.
