# 173. Единая политика передачи данных внешней модели

**Статус:** принято. **Задача:** #173 (TASK 11). **Связано:** #47, #159.

## Контекст

Аудит «Project Vulnerability Analysis» показал, что `ALLOW_DATA_SHARING` управлял
только примерами в описаниях каталога, а узлы compose/verify отдельно отправляли
факты и строки результатов. При этом внешний инференс уже согласован в
[#47](47-contracts-and-runtime.md#6-согласованный-внешний-инференс): backend,
SQLite, DuckDB и UI остаются локальными, а модель получает каталог и ограниченный
контекст. Эта задача не вводит новый запрет на DeepInfra и не добавляет отдельное
согласие пользователя. Она фиксирует, **какой именно контекст** попадает во
внешнюю модель, и делает это правило единым для всех стадий.

## Решение

Одна политика `DataTransferPolicy` живёт в `src/djedai/agent/data_policy.py`.
Экземпляр создаётся при построении `BIModelClient` и передаётся всем узлам через
`configurable["client"]`; `policy_for_client()` возвращает политику клиента, а при
её отсутствии — безопасный режим из окружения. Узлы не создают отдельный HTTP-клиент
и не обходят политику: итоговая проверка выполняется в
`BIModelClient.generate_typed_response()` непосредственно перед сетевым вызовом.

### Режимы

| Режим | `ALLOW_DATA_SHARING` | Что дополнительно разрешено |
| --- | --- | --- |
| Безопасный (по умолчанию) | `false` | Метаданные, текст пользователя и история, факты, агрегаты, значения и свободный текст **текущего** результата |
| Полный | `true` | Все несекретные категории, включая выборки каталога (`sample_values`, `top_values`) и сырые строки прошлых результатов |

`ALLOW_DATA_SHARING=false` — не глобальный запрет на передачу данных и не запрет
внешнего инференса. Это ограничение дополнительной экспозиции: без примеров
каталога и строк прошлых ходов модель всё равно получает каталог, вопрос, историю
диалога, факты, агрегаты и данные текущего расчёта, необходимые для ответа.
Секреты, DSN, пароли, ключи и токены запрещены в обоих режимах.

### Категории и контексты

| Категория | Безопасный режим | Полный режим |
| --- | --- | --- |
| `METADATA` — имена, типы, роли, статистика, описания, связи, summary | разрешена | разрешена |
| `USER_TEXT` — вопрос и текст сообщений истории | разрешена | разрешена |
| `FACT` — структурированные факты инструментов | разрешена | разрешена |
| `AGGREGATE` — счётчики, суммы, min/max и другие агрегаты | разрешена | разрешена |
| `CELL_VALUE` — значения ячеек | только `CURRENT_RESULT` | разрешена |
| `FREE_TEXT` — свободный текст результата | только `CURRENT_RESULT` | разрешена |
| `SECRET` — секреты, DSN, учётные данные | запрещена | запрещена |

Контекст `CATALOG` относится к выборкам каталога (`sample_values`, `top_values`),
`HISTORY` — к сохранённым результатам прошлых ходов. Текущий результат — это
результат, посчитанный в этом ходе; он нужен, чтобы ответить на текущий вопрос.
Исторические агрегаты передаются через `FACT`, а не через сырые строки. Свободный
текст в строках результата проходит по тому же правилу, что `CELL_VALUE`: в
restricted-режиме он разрешён только для текущего результата.

## Как это применяется

- `memory_context()` передаёт политику в `conversation_context()`. В безопасном
  режиме строки прошлых результатов заменяются меткой
  `sample_rows=omitted_by_data_policy`; метаданные, факты и текст истории остаются.
- `_answer_payload()` в графе собирает для compose/verify только разрешённые факты
  и данные. Если после фильтрации не осталось ни фактов, ни разрешённых строк,
  модель не вызывается: возвращается понятное ограничение
  «Недостаточно данных, разрешённых к передаче модели…». Выдуманный ответ не
  публикуется.
- `visualize` получает `chart_result()`: колонки, `row_count`, `chart_hint`,
  факты и `sample_rows` только для текущего результата. Для истории остаётся
  `sample_rows_omitted`.
- `execute` очищает ошибки, факты, SQL и параметры инструмента до сохранения в
  состоянии; `plan` дополнительно очищает текст ошибки перед отправкой.
- `clarify` не вызывает модель, но очищает вопрос, варианты и сообщения решений
  перед публикацией.
- `describe_catalog()` использует `policy_for_client(client)`. Выборки каталога
  передаются только при `policy.allows(CELL_VALUE, CATALOG)`; явный
  `share_values=False` остаётся запретом и в полном режиме.
- Повторы и ремонт (retry/repair) повторно используют уже очищенные промпты.
  `guard()` вызывается один раз перед первой сетевой попыткой; если в промпте
  остался секрет, клиент возвращает `POLICY_RESTRICTED` без сети.

## Секреты и ошибки

`DataTransferPolicy` рекурсивно очищает строки, словари, списки и Pydantic-модели.
Распознаются приватные ключи PEM, URL/DSN с учётными данными, ключи `sk-…`,
`Bearer …` и присваивания `password=…`, `api_key=…`, `token=…`. Секретные имена
полей (`password`, `token`, `api_key`, `dsn`, `authorization` и т. п.) заменяют
значение на `[REDACTED]`, даже если оно вложено в список или словарь. Имя поля
может остаться, но его значение — нет.

Для описаний каталога этого недостаточно: обычный пароль может не совпадать ни с
одним шаблоном секрета. Поэтому перед сериализацией `sample_values`, `top_values`
и `stats.min/max` колонки, у которой `name` или `original_name` распознано как
чувствительное, заменяются на `[REDACTED]` в обоих режимах — так же, как значения
таких колонок в строках результатов. Имя колонки остаётся метаданными и не
скрывается.

Сообщения об ошибках модели не содержат тела ответа провайдера, prompt, DSN или
строк. `BIModelClient` возвращает стабильные тексты для `INVALID_JSON`,
`SCHEMA_MISMATCH`, `OUTPUT_LIMIT`, `TIMEOUT`, `SERVER_ERROR`, `UNKNOWN_ERROR` и
`POLICY_RESTRICTED`; HTTP-статус и тип ошибки сохраняются для диагностики.
Диагностика по-прежнему пишет только стадию, тип, длительность и usage — без
prompt, ответа, DSN и примеров строк.

## Разрешённые примеры payload по стадиям

Ниже — форма, а не реальные данные. Маркеры показывают, какие категории допустимы
в безопасном режиме.

### understand

```json
{
  "system": "Каталог: <METADATA>; история: <USER_TEXT>; факты прошлых ходов: <FACT>",
  "user": "<USER_TEXT: вопрос пользователя>"
}
```

### plan

```json
{
  "catalog": "<METADATA>",
  "tools_registry": "<METADATA: имена и JSON Schema инструментов>",
  "results": "Tool run_sql: error - <очищенный текст ошибки>",
  "history": "<USER_TEXT, FACT, метаданные; sample_rows=omitted_by_data_policy>"
}
```

### visualize

```json
{
  "result_id": "r_17",
  "tool": "run_sql",
  "columns": ["<METADATA: имя колонки>"],
  "row_count": 2,
  "sample_rows": [["<CELL_VALUE текущего результата>", 10]],
  "facts": ["<FACT: агрегат>"],
  "chart_hint": {"type": "bar", "x": "category", "y": ["amount"]}
}
```

Для исторического результата вместо `sample_rows`:
`"sample_rows_omitted": "data_policy"`.

### compose

```json
[
  {
    "result_id": "r_17",
    "tool": "run_sql",
    "facts": [{"text": "<FACT>", "kind": "summary", "values": {"total": 30}}],
    "data": {
      "columns": ["<METADATA>"],
      "row_count": 2,
      "rows": [["<CELL_VALUE текущего результата>", 10]]
    }
  }
]
```

При пропущенных исторических строках добавляется пояснение политики: использовать
только факты, агрегаты и метаданные и не выдумывать значения.

### verify

Тот же payload, что у compose, плюс черновик ответа:

```json
{
  "facts": "<разрешённые FACT/AGGREGATE/CELL_VALUE текущего результата>",
  "draft": "<текст черновика>"
}
```

### clarify

Сетевого вызова нет. В ответ попадают очищенные вопрос и варианты уточнения из
`Understanding` и решения по метрике/качеству из результатов инструментов. Секреты
в них заменяются на `[REDACTED]`.

### descriptions

```json
{
  "table": "orders",
  "original_name": "<METADATA>",
  "row_count": 125430,
  "primary_key_candidates": ["order_id"],
  "time_columns": ["created_at"],
  "columns": [
    {
      "name": "order_id",
      "original_name": "<METADATA>",
      "semantic_type": "id",
      "role": "id",
      "null_ratio": 0.0,
      "distinct_count": 125430,
      "is_unique": true,
      "sample_values": ["<CELL_VALUE каталога: только ALLOW_DATA_SHARING=true>"],
      "top_values": [{"value": "<CELL_VALUE каталога>", "count": 1}],
      "stats": {"min": "<AGGREGATE>", "max": "<AGGREGATE>"}
    }
  ]
}
```

В безопасном режиме поля `sample_values` и `top_values` отсутствуют; остаются
имена, типы, роли, статистика и агрегаты.

## Безопасная конфигурация

В `.env.example`:

```dotenv
# false — безопасный режим: без выборок каталога и сырых строк истории.
# true — полный режим для доверенного endpoint.
ALLOW_DATA_SHARING=false
```

Значение читается из окружения, затем из `.env`. Окружение процесса при чтении не
меняется. Переключение в `true` — осознанное решение оператора для конкретного
endpoint, а не новое согласие пользователя в UI.

## Ограничения

- В безопасном режиме исторические строки не передаются, даже если они являются
  агрегатами. Агрегаты должны быть оформлены инструментом как `Fact`; это
  сохраняет ответ на follow-up без раскрытия сырых строк.
- Без примеров каталога описания колонок могут быть менее точными. Это ожидаемая
  плата за безопасный режим; полный режим включает примеры.
- Политика очищает секреты, но не заменяет сетевую авторизацию, изоляцию данных и
  проверку прав доступа.
