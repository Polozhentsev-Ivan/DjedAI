Дата: 24.10.2026. Основа — интерфейс данных [#62](62-data-interface.md), проверка

## Способ доступа: материализация с порогом

**Выбрано:** выбранные таблицы ClickHouse копируются в файл DuckDB датасета при
подключении, если их суммарный объём не больше порога. Источник больше порога
отклоняется понятной ошибкой. Запросы агента выполняются в DuckDB, не в ClickHouse.

Объём, по которому принято решение. Это демо-датасет #100
(`eval/demo_db_expectations.json`), он же единственный доступный ClickHouse проекта;
реальный объём заказчика так и не предоставлен (см. §7 PL-1):

| Таблица | Строк | Байт на диске ClickHouse |
| --- | ---: | ---: |
| `sales` | 4 376 | 69 395 |
| `campaigns` | 365 | 1 026 |
| `products` | 50 | 1 388 |
| `stores` | 10 | 562 |
| **Итого** | **4 801** | **≈72 КБ** |

Сравнение вариантов для такого объёма:

| | Материализация в DuckDB | Проксирование (pushdown) |
| --- | --- | --- |
| Каталог, профайлер, поиск связей | общие, без изменений | нужна серверная реализация профиля и связей |
| `run_sql`, `describe_*`, `value_counts`, инструменты #66/#67 | работают как есть | каждый инструмент — второй вариант в диалекте ClickHouse |
| Проверка SQL агента (`analytics/scope.py`) | та же AST-проверка DuckDB | новая проверка в диалекте ClickHouse и её собственная приёмка #103 |
| Граница владельца после сборки | как у CSV: read-only файл, без секрета | секрет и сетевой доступ при каждом запросе |
| Свежесть данных | снимок на момент подключения | живые данные |
| Объём | ограничен порогом и диском приложения | не ограничен ресурсами приложения |

Для тысяч строк выигрыш pushdown — живые данные и объём — не нужен, а его цена —
второй путь выполнения для всех инструментов и вторая модель проверки прав. Решение
§7 PL-1 принималось без известного объёма; теперь он известен, и §7 уточняется.
Pushdown остаётся путём для источников больше порога: при появлении такого
источника понадобится отдельная задача с собственной приёмкой изоляции.

## Порог

| Параметр | По умолчанию | Смысл |
| --- | --- | --- |
| `CLICKHOUSE_MAX_ROWS` | 10 000 000 | сумма строк выбранных таблиц |
| `CLICKHOUSE_MAX_BYTES` | 1 000 000 000 | сумма байт на диске ClickHouse; потолок размера выгрузки |
| `CLICKHOUSE_QUERY_TIMEOUT_SECONDS` | 300 | `max_execution_time` и таймаут HTTP-чтения |

Значения по умолчанию сначала были взяты с запасом в три порядка над демо: 5 млн строк.
Опубликованный датасет организаторов больше: 9 таблиц HK_Datasets — 5 376 000 строк и
289 МиБ в ClickHouse. С порогом 5 млн подключение всех таблиц отказывало. С порогом
6 млн на тех же данных копирование, профиль и связи заняли 22,5 с при пике памяти
процесса 1,17 ГБ, файл датасета — 168 МБ ([прогон PL-3](../pl3-hk-datasets-run.md)).
Поэтому порог строк поднят до 10 млн: почти двойной запас над данными кейса при том же
порядке памяти. Порог байт не менялся. Порог — общий на все выбранные таблицы,
и проверяется он трижды:

1. **До чтения строк** — по `system.tables.total_rows/total_bytes`. Для
   представлений и таблиц без статистики выполняется `count()`.
2. **Во время выгрузки** — каждая таблица получает от сервера не больше *остатка*
   общего порога: `max_result_rows/bytes` уменьшаются на уже загруженное, режимы
   `*_overflow_mode=throw`. Клиент обрывает поток больше остатка байт.
3. **После выгрузки** — строки пересчитываются в DuckDB и вычитаются из остатка.
   Это нужно, когда источник вырос между подсчётом и выгрузкой, и для пользователя
   с `readonly=1`, которому сервер не даёт задать лимиты.

Превышение — ошибка сборки, а не усечённая копия под видом полной.

## Полнота выгрузки

ClickHouse при `*_overflow_mode=break`, а также при `limit`/`offset` в профиле
отдаёт часть строк обычным успешным ответом. Поэтому:

- для `readonly=2` адаптер сам задаёт `result_overflow_mode`, `read_overflow_mode`,
  `read_overflow_mode_leaf`, `timeout_overflow_mode` = `throw` и `limit`/`offset` = 0;
- после подключения действующие настройки читаются из `system.settings`. Если
  `limit`/`offset` не 0 или у заданного лимита режим не `throw`, подключение
  отклоняется. Для `readonly=1`, который настройки не меняет, это единственная защита
  на стороне профиля;
- если загружено меньше строк, чем было в источнике до выгрузки и остаётся после
  неё, сборка падает: «выгрузка неполная: получено N строк из M». Уменьшение
  источника во время выгрузки ошибкой не считается.

Оба случая найдены на ревью #61 и закреплены тестами в `tests/unit/data/test_clickhouse.py`.

Сообщение о превышении показывается пользователю: «источник слишком велик для
загрузки: N строк > M; выберите меньше таблиц». Остальные ошибки источника, как у
PostgreSQL, остаются обобщёнными.

## Подключение

- Протокол — HTTP-интерфейс ClickHouse (порт 8123/8443), клиент на stdlib
  (`djedai.data.clickhouse.ClickHouseHttp`). Он же используется в скриптах
  seed/verify. Зависимость `clickhouse-connect`, упомянутая в §7, не понадобилась:
  выгрузка идёт в Parquet, который читает DuckDB.
- DSN: `http(s)://user:password@host:port/database` или `clickhouse://…`
  (`?secure=1` — HTTPS). Пользователь и пароль обязательны. Из параметров разрешены
  только `secure` и `connect_timeout`. Без базы в адресе используется `default`.
- Каждый запрос идёт с `readonly=2`. Пользователю с `readonly=1` сервер не даёт
  менять настройки — тогда настройки не передаются, и объём ограничивают
  предварительный подсчёт и размер выгрузки. После подключения проверяется, что
  `getSetting('readonly')` равен 1 или 2; иначе подключение отклоняется.
  Гарантию даёт роль на стороне БД (`infra/clickhouse/roles.sql`: `readonly = 2 CONST`).
- Таблицы выбираются в базе подключения: `имя` или `база.имя`; без списка берутся все.
- Типы: Parquet сохраняет `Decimal`, `Date/Date32`, `DateTime64`, `Nullable`,
  `LowCardinality`, `Bool`, `UUID`. `DateTime` с зоной переводится в UTC без зоны, как у
  PostgreSQL. `Int128/256` и `IPv4/6` приводятся к тексту на сервере. Массивы и map
  остаются текстом с записью в журнале преобразований.

В файле DuckDB есть «сырые» таблицы `ch_<база>_<таблица>` и типизированные
представления `<таблица>`. Каталог (`source.kind="clickhouse"`,
`table.source.relation="база.таблица"`) строится общим профайлером и поиском связей.
SQL агента видит только представления каталога.

## Владелец и изоляция

- DSN и выбор таблиц хранятся как Fernet ciphertext, привязанный к владельцу,
  датасету **и виду источника**. Шифротекст PostgreSQL нельзя расшифровать как
  ClickHouse и наоборот.
- Секрет нужен только при сборке и при восстановлении прерванной сборки. После
  этого `get_context` открывает файл только для чтения, как у CSV, с
  `enable_external_access=false`, без секрета и без обращений к ClickHouse. Отзыв
  ключа или недоступность сервера не влияют на анализ готового датасета.
- Все проверки [#103](103-owner-isolation.md) общие: `(owner_id, dataset_id)` для
  чтения, каталога, SSE, контекста, чатов и результатов. Чужой ID получает 404. Фоновая
  сборка сохраняет владельца, с которым была принята.
- Пароль не попадает в URL запроса, `repr`, сообщения об ошибках, каталог, файл
  DuckDB, ответы API и логи. Временный Parquet создаётся в каталоге датасета и
  удаляется в любом случае.

## Ограничения

- Данные — снимок на момент подключения. Обновление снимка относится к задаче
  refresh дашбордов и должно повторить проверки владельца при пересборке.
- Форма подключения в UI пока отправляет фиксированный (макетный) список таблиц
  и не умеет «проверить соединение» — это отдельная UI-задача. API и Python-фасад
  принимают реальный список или `null` (все таблицы).
