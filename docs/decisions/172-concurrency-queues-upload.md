# Ограничение параллельных вычислений, очередей и загрузки — B5-11 / #172

Дата: 26.10.2026. Основа — #94, #103, #158 и аудит архитектурной безопасности. Зона ответственности — Backend (`ya-Bell`).

## 1. Архитектурная модель исполнения (Single-Process Model)

Сервис DjedAI архитектурно спроектирован для работы с локальной базой данных SQLite (`app.db`) и локальными файлами аналитических датасетов DuckDB. Запуск нескольких воркеров Uvicorn в одном контейнере запрещён из-за несовместимости файловых блокировок SQLite с конкурентной многопроцессной записью. 

Сервис запускается строго в **один процесс** (`uvicorn djedai.backend.app:app --host 0.0.0.0 --port 8000`). Все механизмы ограничения очередей, семафоров и учета квот реализованы внутри процесса на базе потокобезопасных примитивов (`asyncio.Lock`, `threading.Lock`, `Permit`).

## 2. Управление допуском чата (Chat Admission) и жизненный цикл CPU-слотов

1. **Запрет параллельных ходов в одном чате**:
   - Пока последний ход чата имеет состояние `running`, входящий запрос немедленно отклоняется с кодом **HTTP 409 Conflict**:
     `{"error": {"code": "conflict", "message": "В этом чате уже выполняется генерация ответа. Дождитесь завершения или отмените текущий запрос."}}`
   - После сохранения терминального исхода (`success`, `error`, `timeout`, `cancelled`, `interrupted`) следующий явно отправленный вопрос может ждать завершения cleanup предыдущего worker. Сохранённый `run_id` должен совпадать с активным worker этого чата. Его physical permit остаётся занят до выхода потока; новый worker до этого не запускается.
   - В очереди допускается только один следующий вопрос этого чата. Повторные запросы получают 409; ожидание подчиняется общим лимитам очереди, deadline и отключению клиента. Старый вопрос автоматически не повторяется.

2. **Двухуровневые лимиты и очередь**:
   - Глобальный лимит активных воркеров: `MAX_CONCURRENT_CHATS` (дефолт `4`).
   - Лимит активных воркеров на пользователя: `MAX_CONCURRENT_CHATS_PER_OWNER` (дефолт `1`).
   - Лимиты очередей: `MAX_QUEUED_CHATS` (дефолт `10`), `MAX_QUEUED_CHATS_PER_OWNER` (дефолт `2`).
   - При переполнении очереди возвращается **HTTP 429 Too Many Requests**:
     `{"error": {"code": "rate_limit", "message": "Превышен лимит параллельных запросов пользователя..."}}`

3. **Ожидание слота и отмена**:
   - Запрос ожидает освобождения слота с дедлайном `CHAT_ADMISSION_TIMEOUT_SECONDS` (дефолт `10.0` с). При истечении — **HTTP 429** (`code="admission_timeout"`).
   - Если клиент закрыл вкладку во время ожидания (`request.is_disconnected()`), ожидание мгновенно отменяется, заявка удаляется из очереди, воркер не создаётся.

4. **Жизненный цикл слота CPU (Permit)**:
   - Слот удерживается **до фактического завершения потока ОС** (`threading.Thread`).
   - `permit.release()` вызывается исключительно в блоке `finally:` функции воркера.
   - Если клиент оборвал SSE-поток во время вычислений, соединение закрывается, выставляется флаг кооперативной отмены `cancel_event.set()`, но **слот остаётся занятым** до тех пор, пока поток реально не выйдет из выполнения. Это исключает каскадную перегрузку CPU при повторных запросах отключившихся клиентов.

5. **Справедливость (Fair Queueing)**:
   - Очередь ожидания диспетчеризуется по схеме **Round-Robin** между владельцами (`owner_id`), предотвращая монополизацию сервера одним пользователем.

## 3. Ограниченная модель исполнения (Bounded Execution Model)

В Python принудительное завершение потока (`pthread_kill` / `PyThreadState_SetAsyncExc`) небезопасно и вызывает аварийное падение C-расширений (DuckDB, OpenSSL). Для ограничения вычислений принята модель:

- **Кооперативная отмена**: перед каждым узлом графа LangGraph (`understand`, `plan`, `execute`, `compose`, `verify`) проверяется флаг `is_cancelled()`.
- **Прерывание DuckDB**: в `run_sql` таймер `con.interrupt()` прерывает аналитические запросы по истечении `TOOL_TIMEOUT_SECONDS` (30 с).
- **Сетевой таймаут LLM**: клиент `BIModelClient` использует сокетный таймаут `MODEL_TIMEOUT_SECONDS` (60 с).
- **Защита слотом**: даже при выполнении некооперативного C-кода слот остаётся занят, не позволяя параллельным запросам перегрузить процессор.

## 4. Потоковый контроль загрузки и дисковые квоты

1. **Периметр сети (Nginx)**:
   - В `infra/nginx.conf` задана директива `client_max_body_size 2100m;`, отсекающая аномальные тела до бэкенда.

2. **Защита от DoS на уровне ASGI (`StreamingUploadLimitMiddleware`)**:
   - Проверяет входящий поток байтов **до** парсера `python-multipart`.
   - Если `Content-Length` или сумма фактических потоковых чанков превышает `MAX_UPLOAD_REQUEST_BYTES` (2 ГБ) + 64 КБ (запас на multipart-границы), запрос немедленно прерывается с **HTTP 413 Payload Too Large** без сохранения временных файлов в `/tmp`.

3. **Лимит на запрос**:
   - `MAX_UPLOAD_REQUEST_BYTES` (2 ГБ) — максимальный суммарный размер файлов в запросе. Отдельного лимита на файл нет: первоначальные 50 МБ на файл и 100 МБ на запрос отклоняли все CSV организаторов (98–223 МБ), поэтому #229 убрал первый и поднял второй.
   - Потоковое копирование чанками по 64 КБ с немедленным удалением созданного каталога датасета при ошибке (`shutil.rmtree`).
   - Явное закрытие `UploadFile.close()` в блоке `finally` роутера для удаления файлов из `/tmp`.

4. **Атомарный менеджер дисковой квоты (`StorageQuotaManager`)**:
   - `MAX_OWNER_STORAGE_BYTES` (5 ГБ) — дисковая квота владельца в `DATASETS_DATA_DIR`.
   - Атомарное in-flight резервирование байтов под блокировкой (`threading.Lock`). Если `used_disk + reserved + incoming > quota` — отказ **HTTP 413**.
   - Резерв освобождается в `finally`. При успешной записи файлы учитываются на диске, при ошибке каталог удаляется. Исключена гонка (TOCTOU) при двух одновременных загрузках одного пользователя.

## 5. Очередь задач датасетов и Fair Recovery

1. **`DatasetJobQueue`**:
   - Параллельные задачи: `MAX_CONCURRENT_DATASET_JOBS` (дефолт `2`), `MAX_CONCURRENT_DATASET_JOBS_PER_OWNER` (дефолт `1`).
   - Ёмкость очереди: `MAX_QUEUED_DATASET_JOBS` (дефолт `10`), `MAX_QUEUED_DATASET_JOBS_PER_OWNER` (дефолт `2`).
   - При переполнении — отказ **HTTP 429**.
   - Справедливое чередование активных пользователей по Round-Robin.

2. **Безопасное восстановление (Recovery)**:
   - При рестарте `recover_interrupted()` считывает незавершённые задачи из SQLite, сортирует по `created_at ASC` и помещает их в `DatasetJobQueue` с соблюдением общих и пользовательских лимитов.
   - Задачи, превысившие ёмкость очереди при рестарте, атомарно переводятся в статус `error` с понятным сообщением («Сервер был перезагружен; очередь задач переполнена»). Сервер защищён от лавинообразной нагрузки (thundering herd).

## 6. Безопасная диагностика (Safe Diagnostics)

- Контроллеры допуска предоставляют методы `snapshot()` для мониторинга активных и ожидающих задач.
- События допуска журналируются в `agent.jsonl`:
  - `admission_acquired`: время ожидания `wait_ms`.
  - `admission_rejected`: причина отказа (`same_chat_conflict`, `owner_queue_full`, `global_queue_full`, `timeout`).
  - `admission_released`: длительность вычислений `duration_ms`.
- В журнал не попадают промпты, токены, пароли или пути к файлам.
- Локальная утилита оператора поддерживает фильтрацию: `python -m djedai.diagnostics --type admission_rejected`.

## 8. Проверка и воспроизведение

Импорт, перепрофилирование готовых датасетов и восстановление обоих видов задач
используют одну очередь и одни global/per-owner лимиты. При переполнении очередь
refresh не меняет опубликованный каталог; восстановленный refresh получает явную
ошибку, а новый запрос — 429. Нулевой размер очереди допускает работу в свободном
слоте, но запрещает ожидание. Остановка дожидается также задач, запущенных из очереди.

1. **Тесты допуска и очередей**:
   `uv run pytest tests/unit/backend/test_admission.py`
2. **Тесты очередей датасетов, загрузок и квот**:
   `uv run pytest tests/unit/backend/test_dataset_concurrency.py`
3. **Тесты валидации лимитов**:
   `uv run pytest tests/unit/test_limits.py`
