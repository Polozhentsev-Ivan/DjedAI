## 1. Основание и согласованные условия

Источники: `AI-Native-BI_spec (2).md` и `План AI-Native BI.html`. Коды B1–B5 сохраняются для сверки со спецификацией. Совместные строки HTML превращаются в одну задачу, а не в отдельную задачу для каждого участника.

Подтверждено пользователем:

- Чекпоинты — **19 и 26 октября 2026**, финал — **30 октября 2026**.
- Дневные интервалы HTML — ориентиры последовательности и параллельной работы. У отдельных задач не будет жёстких дат начала и окончания.
- PM не участвует и не фигурирует как роль, исполнитель или согласующий.
- Владелец зоны ответственности и фактический исполнитель — разные понятия. Любую задачу может взять любой участник.
- Авторизация включает **самостоятельную регистрацию, вход/выход и личные данные каждого пользователя**. БД пользователей оформляется отдельной задачей.
- Основной UI — **React + TypeScript** в отдельном `frontend/`, сборка Vite, пакетный менеджер npm и `package-lock.json`. Python остаётся backend/data/agent; продуктовый объём, зоны владельцев и CP1/CP2/FINAL сохраняются.
- Сначала согласуется этот план; создание issues и изменение GitHub — только после одобрения.

Текущие описания и состояния задач — в [GitHub Issues](https://github.com/Polozhentsev-Ivan/DjedAI/issues). Исторические решения подготовки ниже применяются с учётом опубликованных задач и последующих согласованных изменений.

## 3. Вехи и приёмка

Предлагаются три GitHub milestones. Валидация 26–28 октября и фриз 29 октября — контрольные пункты финального milestone, как в HTML.

| Milestone | Дата | Проверяемый результат |
|---|---|---|
| CP1 — Сквозной сценарий | 19.10.2026 | Локальный запуск → загрузка CSV → минимальный каталог → вопрос → `run_sql`/базовый инструмент → сохранённый результат → текстовый ответ в чате. API, хранилище, модель и UI соединены. |
| CP2 — Качество и контекст | 26.10.2026 | Сценарии 1–2 качественно; подключение PostgreSQL; связи и описания данных; уточнения; проверка чисел; память; «Как посчитано»; полный каталог; eval v1. В предложенный объём CP2 также входит регистрация и личное пространство. |
| FINAL — Финальная сдача | 30.10.2026 | Визуализации, контекст и живые дашборды; сценарии 3–10 по приоритетам спецификации; ClickHouse; итоговые проверки, документация и показ. Валидация 26–28.10, 29.10 — фриз, далее исправления дефектов. |

**Регистрацию, вход и изоляцию всех доступных на CP2 функций предлагается завершить к CP2**, чтобы оставалось время проверить личные данные на финальных функциях. Это предложение плана, а не срок из исходных файлов. К CP1 нужны согласованная модель владения и схема БД пользователей; готовность входа не должна блокировать разработку компонентов на тестовых пользователях. Такой режим относится только к разработке: при приёмке AUTH обязательна реальная проверка сессии и прав. Защита новых функций после CP2 входит в критерии самих B1-9/B5-6/B4-7 и итоговую PL-5; закрытие AUTH не освобождает их от этой проверки.

Официальные критерии CP1 в предоставленных MD/HTML отсутствуют. До их появления используется внутренний сценарий из §10.2 MD. Для CP2 сохраняется формулировка о подключении предоставленного датасета; готовность этого пункта подтверждается фактическим прогоном, а не только синтетикой.

### Как согласовать ранние и полные этапы

| Расхождение источников | Предлагаемое решение |
|---|---|
| В MD к CP1 нужен каталог, в HTML полный B4-3 позже | Минимальный просмотр структуры входит в B4-2/приёмку CP1; полноценный B4-3 — CP2. |
| MD требует `understand` на CP1, HTML ставит B3-3 после него | В B3-2/4 — минимальная маршрутизация простого вопроса; полный B3-3 с неоднозначностями и уточнениями — CP2. |
| `compose` в HTML включён в B3-4, в MD — в B3-6 | Минимальный ответ из `facts/data` — B3-4/CP1; полный `compose + verify` — B3-6/CP2. Отсутствие полного verify на CP1 прямо предусмотрено §10.2 MD. |
| B5-5 стоит после CP1, но сохранять надо каждый вызов | Запись результатов, включая `error/empty`, `result_id`, SQL и параметры — в B5-2/CP1; чтение полного реестра и данных через API — B5-5/CP2. |
| Обзорная архитектура ставит verify перед compose | Зафиксировать порядок подробного §5.1: `compose → verify → публикация`. |
| Исходные материалы предполагали Python UI, а §7.4 — nginx со статикой | Утверждён React + TypeScript: Vite собирает статику, nginx обслуживает frontend и проксирует `/api` в FastAPI, включая upload и SSE. Исходный HTML не изменяется. |
| Виджет хранит один вызов, но аналитика поддерживает `source_result_id` | В PL-1 согласовать воспроизводимый рецепт зависимых вычислений. B5-6 должен обновлять JOIN/предварительный расчёт, а не зависеть от старого временного результата. |

У задачи, проходящей несколько этапов, **milestone обозначает полную готовность**. Более ранний результат отмечается явным чекбоксом в её описании и в issue чекпоинта. Частичная готовность не закрывает всю задачу. Это особенно относится к B1-10, B4-2/4/6, B5-3/8/9.

## 4. Формат и правила будущих issues

- Заголовок: `[B1-1] Загрузить сырые CSV в DuckDB` или `[AUTH-1] Создать БД пользователей и миграции`.
- В описании: результат, источник, зона ответственности, milestone, ранние этапы, зависимости, объём, критерии приёмки и способ проверки.
- Метки зон: `area:data`, `area:analytics`, `area:agent`, `area:ui`, `area:backend`, `area:infra`, `area:auth`, `area:quality`.
- Метки типа: `type:task`, `type:decision`, `type:checkpoint`. Метка `stretch` — только для необязательного расширения `what_if`.
- Приоритеты: `priority:critical` — блокирует ближайшую веху; `priority:high` — основные пользовательские сценарии; `priority:normal` — остальной согласованный объём. Низкий приоритет не означает исключение из плана.
- Для финала сохраняется порядок MD: визуализация/контекст/дашборды → аномалии/сегменты/сезонность → лаги/прогноз. PostgreSQL и ClickHouse остаются в плане; ClickHouse не превращается в необязательную задачу.
- После создания зависимости получают реальные ссылки `#issue`. До этого используются стабильные коды. На этапе реализации можно опираться на согласованные контракты и заглушки; полная приёмка требует работающих зависимостей. Ссылка на ранний этап другой задачи не превращается в требование закрыть всю эту задачу: готовность раннего этапа отмечается отдельным чекбоксом.
- Изменение кода связано с issue через PR; закрытие — после проверки критериев и ревью. Чекпоинт содержит ссылки на результаты, а не только список закрытых тикетов.

5. **Собрать финал:** `ChartSpec + results API` → Dashboard API с рецептами → ветка агента → экран и «На дашборд»; ClickHouse; прогноз; прогон реальных данных и расширенных сценариев. Проверить права и на новых функциях.

## 8. Решения PL-1

Актуальный реестр — [Контракты и технические решения #47](../decisions/47-contracts-and-runtime.md).
Там зафиксированы SQLite для приложения, Pydantic/OpenAPI как источник общих
типов Python/TS, Bearer-сессия браузера, multipart/SSE, версии и ошибки API,
публикация после verify, рецепт зависимого виджета и отдельный бюджет refresh,
конфигурируемые пороги и прямой read-only доступ к ClickHouse.

Внешний инференс разрешён пользователем для открытых весов до 80B суммарных
параметров. Выбран DeepInfra/Qwen3.6-35B-A3B (35B, FP8); [протокол замеров](model-profile-pl1.md)
фиксирует скорость, JSON/SQL и ограничения управляемого runtime. На нём повторён
CP1 smoke на 500 000 строк. Полная реализация функций и внешний доступ к данным
проверяются в соответствующих issues.
