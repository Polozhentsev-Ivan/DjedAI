# CP1: минимальный сквозной прогон без интерфейса

Актуальный разрешённый профиль до 80B проверен повторно:
[Qwen3.6-35B-A3B](#повтор-на-модели-до-80b). Ниже сохранён протокол исходного
прогона на 235B как историческое свидетельство.

**Дата: 20 октября 2026 года. Результат: `passed`.**

На полном CSV из HK_Datasets проверен путь загрузки данных, построения каталога,
вызова настоящей модели DeepInfra, выполнения SQL и сохранения ответа.
Независимый CSV-парсер, SQL агента и текстовый ответ дали **500 000 строк**.
Отдельный Python-процесс повторно прочитал каталог, сообщения, результат Parquet
и таблицу DuckDB; проверки прошли.

Сценарий выполняется [скриптом smoke_cp1.py](../scripts/smoke_cp1.py).
Он вызывает `stream_chat_turn()` напрямую, без HTTP-сервера и браузера.
Это проверка ядра сценария [#106](https://github.com/Polozhentsev-Ivan/DjedAI/issues/106).
Полная приёмка чекпоинта с UI и Compose остаётся отдельной работой.

## Что и как проверяется

| Шаг | Действие | Условие успеха |
| --- | --- | --- |
| 1. Загрузка | Штатный загрузчик читает CSV в сырую таблицу файловой DuckDB | Файл прочитан, данные доступны для дальнейшей обработки |
| 2. Структура | Строятся typed view, профиль и `DatasetCatalog` с исходными именами, типами и журналом преобразований | Каталог проходит валидацию общего контракта и сохраняется в SQLite |
| 3. Независимый эталон | Стандартный Python `csv.reader` считает записи исходного файла после заголовка | Число положительное и совпадает с числом строк профиля; эталон считается вне SQL агента |
| 4. Контекст агента | Граф получает сохранённый каталог через `catalog_loader` и `to_prompt()` | Модель работает со схемой выбранного датасета |
| 5. Модель и SQL | Настоящая модель строит план; инструменты получают read-only подключение к DuckDB датасета с отключённым внешним доступом | Есть успешный `run_sql` с прямым `COUNT(*)` всей таблицы датасета, без CTE, фильтров и JOIN, результат равен `[[500000]]` |
| 6. Текстовый ответ | Модель формирует ответ из результата инструмента | Только текстовые блоки; их содержимое разбирается как одно целое число и равно эталону |
| 7. Завершение и запись | Собираются события хода чата, сохраняются сообщения и `ToolResult` | Последнее событие — `done`, нет события `error`, есть ссылки ответа на сохранённые результаты |
| 8. Новый процесс | Скрипт запускает отдельный интерпретатор с `--verify-only` | Совпадают каталог, вопрос, ID и текст ответа, ссылки и содержимое `ToolResult`; существует Parquet и сохраняется число строк DuckDB |

Событие `tool_result` с `ok: false` допускается: граф может исправить SQL и повторить
попытку. Это отличается от события `error`, которым завершается неуспешный ход чата.
Глобальный статус `passed` устанавливается только после проверки в новом процессе.
Режим `--prepare-only` возвращает `prepared` и не подтверждает работу модели.

## Что произошло в проверенном запуске

Вопрос:

> Сколько всего строк в таблице "08_fonovye_zadaniya"? Посчитай через run_sql,
> включая дубли. Ответь только одним целым числом, без пояснений и других блоков.

Первая попытка SQL не содержала кавычек вокруг имени, начинающегося с цифры:

```sql
SELECT COUNT(*) FROM 08_fonovye_zadaniya
```

Парсер вернул синтаксическую ошибку. Граф передал её в повторное планирование,
и модель сформировала рабочий запрос:

```sql
SELECT COUNT(*) FROM "08_fonovye_zadaniya"
```

Он вернул одну строку результата со значением `500000`. Поле
`ToolResult.data.row_count = 1` означает число строк агрегированного результата;
число записей исходного датасета находится в `data.rows = [[500000]]`.
Текстовый ответ модели — `500000`.

Всего зафиксировано четыре успешных структурированных ответа API:
`Understanding`, два `PlanResponse` и `ComposeResponse`.

| Объект | Значение |
| --- | --- |
| Датасет | `ds_smoke` |
| Чат | `c_smoke` |
| Сообщение пользователя | `m_0f70d8779f17` |
| Ответ ассистента | `m_add90ff830dc` |
| Успешный результат | `r_b11de959` |
| Ссылка на данные | `parquet://r_b11de959.parquet` |
| Результат первой, ошибочной попытки | `9d2fcb54-59b1-439c-abd4-85eede5008b7` |

В SQLite сохранены два сообщения и оба вызова SQL, включая ошибочный.
Ответ ссылается на один успешный результат. Поэтому повторная проверка сообщает:

```json
{"status": "passed", "messages": 2, "results": 1}
```

Для этого пути подключены инструменты к реальной DuckDB и каталог к графу.
Также уточнён compose-промпт: текст должен находиться в непустом поле `markdown`;
при использовании переформулированного вопроса сохраняются исходные требования
к формату ответа. На предварительном запуске пустой ответ был отклонён проверкой.

## Как повторить

Из рабочей папки `smoke-cp1`, используя уже настроенный ключ в соседнем `repo/.env`:

```powershell
cd C:\Users\ivpol\DjedAI\smoke-cp1
uv run --locked python scripts/smoke_cp1.py --env-file ..\repo\.env
```

В обычном checkout с ключом в корневом `.env` достаточно:

```sh
uv run --locked python scripts/smoke_cp1.py
```

Поддерживаются имена ключа `DEEPINFRA_API_KEY` и `MODEL_API_KEY`.
Адрес и модель задаются параметрами `--base-url` и `--model`; их значения по
умолчанию приведены выше. Каждый запуск создаёт новый каталог результатов.
Код выхода 0 и `report.json: status = passed` означают успех.

Проверить уже сохранённый запуск без нового обращения к модели:

```sh
uv run --locked python scripts/smoke_cp1.py --verify-only artifacts/cp1-smoke/hk-live/report.json
```

## Границы результата

Подтверждён один вопрос к одному полному датасету и чтение сохранённых данных
новым процессом. Проверки точности текста выполняет smoke-скрипт;

само по себе не подтверждает полноценную проверку чисел агентом.

PostgreSQL/ClickHouse и качество на наборе разных вопросов. Повторное чтение
артефактов не является проверкой продолжения диалога после перезапуска.
Серия замеров устойчивости, стоимости и производительности модели не проводилась.
