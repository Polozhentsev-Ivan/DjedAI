# CSV-датасеты в локальном режиме CP1

Однопользовательский режим включается явно: `CP1_LOCAL_MODE=true`.
`CP1_LOCAL_USER_ID` (по умолчанию `cp1-local-user`) задаёт владельца на сервере;
HTTP-клиент не выбирает владельца. Это временный режим локального CP1: сессии,
Bearer-транспорт и полноценная регистрация/авторизация остаются в #102–#105.

Команды выполняются из корня репозитория. Проект использует `package=false`,
поэтому для локального Python задайте `PYTHONPATH=src` (в Docker это уже настроено).
В Bash:

```bash
export PYTHONPATH=src
export CP1_LOCAL_MODE=true
uv run --locked alembic upgrade head
uv run --locked python -m djedai.backend.bootstrap_local_user
```

В PowerShell:

```powershell
$env:PYTHONPATH = "src"
$env:CP1_LOCAL_MODE = "true"
uv run --locked alembic upgrade head
uv run --locked python -m djedai.backend.bootstrap_local_user
```

Команда создаёт обычную строку пользователя без пароля, повторный запуск сохраняет
пользователя и его ресурсы. При необходимости имя при первом создании задаётся
`--username имя`. Конфликт имени с другим ID и неактивный настроенный пользователь
отклоняются. Подготовленные тестовые пользователи/CSV для запуска не требуются.
Если режим выключен либо пользователь не подготовлен, CSV API возвращает 503.

`POST /api/datasets/upload` принимает `multipart/form-data` с повторяющимся полем
`files`; каждый файл должен иметь расширение `.csv`. Ответ 202 содержит
`dataset_id` и `status=processing`. Исходные файлы сохраняются потоково; загрузка,
типизация и профилирование выполняются в рабочем потоке вне цикла HTTP-сервера.
Все файлы образуют один датасет с несколькими таблицами. Ошибка любого файла
переводит весь датасет в `error`, частичный каталог не публикуется.

`GET /api/datasets` возвращает список владельца; `GET /api/datasets/{id}` —
статус, сводку, каталог либо сохранённую понятную ошибку. Отдельный каталог доступен
в `GET /api/datasets/{id}/catalog` после готовности (до неё — 409).
Чужие и неизвестные ID, включая SSE, отвечают 404.

`GET /api/datasets/{id}/events` передаёт SSE `progress`, затем ровно одно
терминальное событие `done` либо `error`. Поле `data` содержит контракт события
без вложенной обёртки `event/data`. Новое подключение к завершённому датасету
сразу получает его терминальное событие. Отключение браузера не отменяет
профилирование; после него можно повторно прочитать состояние или подключить SSE.

SQLite хранит владельца, статус, каталог, текущий прогресс, ошибку, манифест исходных
файлов и относительный путь DuckDB. `DATASETS_DATA_DIR` по умолчанию равен
`./var/data/datasets`; внутри каждого UUID-каталога находятся `raw/0000.csv` и
`dataset.duckdb`. Имена загружаемых файлов служат только метаданными и не задают
пути. Публикация DuckDB происходит после закрытия успешно построенной временной
базы. При перезапуске незавершённые CSV-датасеты заново строятся из сохранённых
исходников; недоступный исходник становится сохранённой ошибкой.

Для восстановления нужно переносить **SQLite и весь `DATASETS_DATA_DIR` вместе**.
Готовый CSV-контекст открывается по паре `(owner_id, dataset_id)` из сохранённого
каталога и отдельного файла DuckDB; тестовая база аналитики здесь не используется.
Один backend обслуживает эти файлы. Внешние подключения PostgreSQL/ClickHouse
(#62 и последующие этапы) и общий жизненный цикл хранения/удаления (#94) этим
адаптером не реализуются.

Рабочий CSV-фасад B1-10 находится в
`djedai.backend.dataset_service.DatasetService(factory, data_dir)`:

- `await ingest_csv(owner_id, sources)` принимает `Sequence[CsvSource]`
  (`djedai.data.service.CsvSource(path, original_name)`) без HTTP и `UploadFile`.
  До возврата `DatasetUploadAccepted(dataset_id, status="processing")` фасад
  сохраняет собственные копии файлов; исходники вызывающего кода после этого
  можно закрыть, переместить или удалить. Типизация/профилирование идут в фоне.
- `get_catalog(owner_id, dataset_id)` читает сохранённый `DatasetCatalog`:
  чужой/неизвестный ID — 404, неготовый каталог — 409.
- `get_detail` даёт статус и ошибку; `get_context` — доверенный каталог и путь
  DuckDB для аналитики; `recover_interrupted` и `close` управляют запуском и
  завершением фоновой обработки.

HTTP-адаптер `ingest_uploads` копирует multipart-потоки через ту же процедуру
хранения и постановки в обработку. `djedai.data.service.ingest_csv_dataset`
выполняет общий pipeline сырых таблиц, типов, профилей и полного каталога.
`connect_db`, PostgreSQL/ClickHouse-адаптеры и полный жизненный цикл источников
остаются следующими этапами #62; текущие CSV-фасад и HTTP-контракты уже работают.
