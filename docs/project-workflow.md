# GitHub и рабочий процесс

Основной репозиторий — [Polozhentsev-Ivan/DjedAI](https://github.com/Polozhentsev-Ivan/DjedAI), default branch — `main`. Это единый монорепозиторий приложения: Python/backend, frontend, contracts, prompts, fixtures, CI и инфраструктура версионируются совместно.

Текущие статусы карточек/PR и настройки GitHub смотрятся в сервисе. Эта глава описывает устройство процесса, а не поддерживает второй постоянно устаревающий счётчик задач.

## Задачи и ответственность

У задачи есть GitHub-номер и код направления: например `B1` — данные, `B2` — аналитика, `B3` — агент, `B4` — UI, `B5` — backend/инфраструктура. `PL` обозначает сквозную работу, `AUTH` — сессии/личные данные, `CP` — приёмки, `CD` — поставку.

| Зона | Ответственность |
| --- | --- |
| Тимлид | Приоритеты, общие решения, итоговая связность и приёмка |
| DE | Источники, типизация, профиль и DatasetCatalog |
| DA | Смысл метрик, аналитические инструменты, независимые ожидания |
| MLE | Модель, граф, prompts, память и оценка агента |
| Backend/UI | HTTP/SSE, хранение, интерфейс, графики, сборка и интеграция |

Зона помогает выбрать профильного проверяющего, но не запрещает другому участнику взять issue. Фактический исполнитель определяется assignee. Отдельная PM-роль не требуется для выполнения описанных функций.

Карточка задаёт результат, критерии, зависимости, ранние этапы и milestone полной готовности. Ранний работающий этап может быть частью более широкой открытой задачи. Ссылка `Refs #…` отмечает такой этап; `Closes #…` применяется после выполнения всего заявленного объёма.

В [GitHub Labels](https://github.com/Polozhentsev-Ivan/DjedAI/labels) направления обозначены `area:data`, `area:analytics`, `area:agent`, `area:ui`, `area:backend`, `area:infra`, `area:contracts`, `area:auth`, `area:quality`. Например, UI-задачи ищутся по `area:ui`. Тип работы задают `type:feature`, `type:task`, `type:bug`, `type:docs`, `type:decision`, `type:checkpoint`; приоритет — семейство `priority:*`. Также остаются стандартные GitHub labels (`bug`, `documentation` и другие), поэтому один фильтр по типу не обязательно охватывает всю историческую работу.

[Milestones](https://github.com/Polozhentsev-Ivan/DjedAI/milestones) группируют приёмки: **CP1 — Сквозной сценарий**, **CP2 — Качество и контекст**, **FINAL — Финальная сдача**. Они отвечают на вопрос об общем результате этапа, labels — о зоне/типе/приоритете отдельной карточки. Текущая открытость milestone и процентовка issues читаются в GitHub, а не выводятся из документации или факта наличия экрана.

## Цикл изменения

```text
issue → исполнитель → актуальная main → тематическая ветка
      → код/контракты/docs + проверки → PR → ревью
      → исправления → squash merge → проверка общего результата
```

Автор просматривает diff, описывает наблюдаемое поведение и фактически выполненные проверки. PR оформляется по [.github/pull_request_template.md](../.github/pull_request_template.md). Сообщения коммитов/заголовки — Conventional Commits; развёрнутое описание — по-русски.

Автор не принимает собственный PR. Изменения итогового ревьюера проверяет другой знакомый с зоной участник. Общий контракт согласуется с владельцем и потребителями. Командное правило squash и агрегирующий check не следует путать с конкретными настройками branch protection; техническое enforcement проверяется отдельно в GitHub.

## Что находится в `.github`

```text
.github/
  pull_request_template.md
  workflows/ci.yml
```

В базовой версии документации нет отдельного release/deploy workflow. CI проверяет изменение; выкладка на сервер и публикация выпуска — отдельные процедуры. Все пять CI jobs назначены локальному Linux runner с метками `self-hosted`, `linux`, `x64`, `djedai-ci`.

## CI

События: PR в main, push в main/`ci/**`, ручной запуск. Workflow имеет read-only contents permissions, checkout не сохраняет credentials, actions закреплены SHA, устаревший run того же ref/PR отменяется.

Runner работает в отдельном WSL 2 дистрибутиве `DjedAI-CI` на Ubuntu 24.04 со своим Docker Engine. Один runner выполняет jobs последовательно. Его служба запускается внутри WSL, а задача Windows `DjedAI CI Runner` удерживает окружение после входа пользователя. При выключении или сне компьютера задания ожидают доступного runner; назначение в workflow само по себе не доказывает, что машина сейчас online. Установка, проверка службы и ограничения описаны в [infra/ci.md](../infra/ci.md). Регистрационные скрипты — [PowerShell](../scripts/setup-local-runner.ps1) и [Linux](../scripts/setup-local-runner.sh).

Browser smoke в конце удаляет собственные тестовые Compose-тома и orphan-контейнеры, чтобы постоянный runner не переносил аккаунты/данные между прогонами. Эту очистку тестового окружения нельзя переносить в процедуру обновления пользовательской установки.

Для зависших заданий и прерываний подготовлено обслуживание локального runner: watchdog и очистка принадлежащих тестовому запуску контейнеров. Команды состояния и границы автоматического восстановления описаны в [инструкции CI](../infra/ci.md); скрипт — [local-runner-maintenance.sh](../scripts/local-runner-maintenance.sh).

| Job | Назначение |
| --- | --- |
| repository | Проверки checker/выбора CI, tracked structure/UTF-8/ссылок и запрещённых outputs |
| python | Locked dependencies, Ruff, contracts, unit/coverage, migrations, integrations, PG/CH, защищённые tools/eval |
| frontend | npm ci, generated TS, typecheck, lint, coverage и production build |
| browser | Настоящий auth/API/UI с управляемой моделью, Compose/nginx/restart |
| required | Итог применимых jobs с учётом разрешённых пропусков |

Python/frontend/browser выполняются при изменении приложения/конфигурации. Для docs-only PR/push они могут быть пропущены: `scripts/check-ci-changes.mjs` сравнивает полный диапазон изменения. Файлы `prompts/` считаются runtime, несмотря на `.md`; неизвестный путь также запускает полный набор. Ручной workflow dispatch выполняет все application checks.

Поэтому зелёный docs-only `required` подтверждает проверку документационного изменения, а не новый полный runtime/eval. Перед выпуском нужен полный прогон выбранной версии. Спецификация workflow и локальный повтор — [infra/ci.md](../infra/ci.md), [качество](quality.md).

## Документация и выпуск

Пользовательское поведение, настройки, API и процедуры меняются вместе со своей документацией. Проверяются реальные команды, соответствие UI и локальные ссылки. Генерируемые схемы/типы не редактируются вручную.

Выпуск должен связывать версию кода, конфигурацию/модель, миграции, инструкции и результаты проверки. Плавающий текущий README и протокол старого SHA не являются доказательством новой версии. Перенос/rollback базы требует совместимости миграций и данных; это описано в [эксплуатации](operations.md).

Исторические требования и решения сохраняются в [спецификации](specification.md), [плане issues](issues-plan.md) и `docs/decisions/`. Актуальный маршрут читателя начинается с [оглавления](README.md), а не с последовательного чтения всех карточек.
