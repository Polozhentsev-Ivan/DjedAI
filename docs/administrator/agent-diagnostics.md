# Диагностика ответа агента

Каждый авторизованный ход реального чата получает `run_id`, связанный с
`owner_id`, `dataset_id`, `chat_id` и `user_message_id`. Диагностика записывается
по мере работы, поэтому не зависит от успешного сохранения AssistantMessage.
Существующая trace успешного ответа и формат API/SSE сохраняются.

## Где читать

В Compose журнал находится в `/app/var/diagnostics/agent.jsonl` в том же
постоянном томе `app-data`, что и данные приложения. Пересоздание контейнера
без удаления тома сохраняет журнал. Локально путь задаётся `DIAGNOSTICS_DIR`
(по умолчанию `./var/diagnostics`).

Команды для оператора сервера:

```sh
docker compose exec backend /app/.venv/bin/python -m djedai.diagnostics
docker compose exec backend /app/.venv/bin/python -m djedai.diagnostics --run run_ID
# Запуск вне Docker:
uv run --locked python -m djedai.diagnostics --run run_ID
```

Команда читает текущий файл и сохранённые архивы в хронологическом порядке.
Это локальный административный доступ к файлам сервера: HTTP API для журнала
нет, браузер пользователя получить его не может. Права на каталог/файлы нужно
сохранять только у оператора; новые файлы на POSIX создаются с режимом 0600,
каталог — 0700. На Windows доступ определяется также ACL каталога.

## События и интерпретация

- `run_started`: идентификаторы хода и вопроса, время UTC.
- `stage_started` / `stage_finished`: узел графа и длительность в мс. Событие
  начала записывается до входа в узел, включая узел, который впоследствии упал.
  У быстрого маршрута это `fast_route`, `execute` и `fast_compose`; вызовов
  модели на нём нет. `run_finished.duration_ms` — общее время хода, поэтому
  быстрый и обычный маршруты сравниваются по нему и по сумме стадий.
- `fast_path_selected`: выбран быстрый маршрут; содержит только `kind`
  (`row_count` или `structure`) и `table_id`, без текста вопроса.
- `model_call_started` / `model_call_finished`: `call_id`, модель, имя схемы,
  стадия (`stage`), фактически отправленный `reasoning_effort`, исходная
  настройка `reasoning_setting`, исход валидации, общее время вызова с
  паузами/повторами и доступный usage.
- `model_attempt_started` / `model_attempt_finished`: номер каждой фактической
  сетевой попытки, HTTP status при наличии, длительность отправки и чтения
  ответа, нормализованный тип ошибки. Тела HTTP-ошибок не читаются; их статус
  и заголовки сразу используются политикой повторов. Паузы видны в общем
  времени model_call. [Общий бюджет и повторы](../developer/agent-deadlines.md) задаются #158;
  внутренние повторы SDK отключены.
- `run_finished`: success, error, timeout или cancelled, нормализованная причина,
  `error_node`, последняя стадия и trace пройденных узлов. Результаты инструментов
  и сами ответы по-прежнему хранятся штатно в БД приложения.
- `model_retry_wait` / `model_retry_started`: начало разрешённой паузы и новой
  попытки в том же узле. `delay_ms` — выбранная длительность паузы, а не ETA
  ответа. Эти события и `stage_started` питают статусы чата (#161).

В истории вопроса хранится безопасный [ChatTurnState](../developer/chat-turns.md): его
`run_id` позволяет оператору найти тот же ход в журнале. Браузеру передаются
код исхода и последний этап, без тел ошибок провайдера и содержимого журнала.

`null` в токенах означает, что провайдер не сообщил usage. Это не ноль.
Reasoning-токены записываются только из специального поля usage провайдера;
текст рассуждения не сохраняется в журнале. Ошибка JSON/schema или лимита
ответа не удаляет уже полученный usage.

`stage` — одна из стадий `understand`, `plan`, `visualize`, `compose`, `verify`;
`null` означает вспомогательный вызов вне этих стадий (например, описание
каталога). `reasoning_effort` — значение, фактически переданное провайдеру;
`null` означает, что параметр не отправлялся (настройка `provider_default`).
`reasoning_setting` сохраняет исходное значение конфигурации, поэтому по журналу
видно, был ли режим задан явно. Отказ провайдера на `reasoning_effort`
записывается как ошибка вызова; подмена на `provider_default` не выполняется.

Если у `run_started` нет `run_finished`, ход незавершён либо процесс был
прерван: такой ход нельзя считать успешным. После обычной отмены/исключения
записывается финальный исход; аварийное завершение процесса оставляет последние
уже записанные события. Причину аварии следует сопоставить с журналом контейнера.
Модельный запрос отменяется вместе с потоком в пределах допуска на очистку,
описанного в [#158](../developer/agent-deadlines.md). Состояние ошибок в UI относится к #161.

## Стоимость

По умолчанию расчётная и фактическая цена неизвестны. Для оценки укажите вместе:

```dotenv
MODEL_INPUT_PRICE_PER_MILLION_USD=0.10
MODEL_OUTPUT_PRICE_PER_MILLION_USD=0.95
MODEL_PRICE_REFERENCE=2026-10-23 DeepInfra Qwen/Qwen3.6-35B-A3B standard https://deepinfra.com/Qwen/Qwen3.6-35B-A3B/api
```

Это пример явного снимка тарифа, а не автоматический тариф для любого endpoint.
Перед использованием проверьте действующие ставки. При смене модели, провайдера
или service tier обновите все три значения. Неполная, отрицательная или
нечисловая конфигурация отклоняется при запуске. Значения можно оставить пустыми.

`estimated_cost_usd` считается по входным и выходным токенам одного model_call;
reasoning обычно уже входит в выходные токены и повторно не прибавляется.
Оценка использует стандартные ставки без скидок за кэш. Она содержит ссылку на
снимок тарифа и не является подтверждением списания. `actual_charge_usd` остаётся
`null`. Попытки с ошибкой без usage могут тарифицироваться провайдером, поэтому
сумма известных оценок не является полной стоимостью всех попыток.

## Хранение и сбои записи

`DIAGNOSTICS_MAX_BYTES=10000000` и `DIAGNOSTICS_BACKUPS=5` ограничивают журнал
текущим файлом и пятью архивами. Ротация выполняется перед новой записью;
одна запись может быть больше установленного размера. Самые старые архивы
заменяются, так что длительность хранения зависит от нагрузки. Для долгого
аудита оператор выгружает файлы до ротации. Часть хода может оказаться за границей
хранения; отсутствие событий не доказывает отсутствие вызовов.

Запись защищена блокировкой потоков одного backend-процесса. Текущий Compose
запускает один процесс Uvicorn; для нескольких процессов/реплик нужны отдельные
каталоги или централизованный сборщик. Повреждённая последняя JSONL-строка
после аварии не скрывает предыдущие и новые завершённые события.

Ошибка диска выдаёт безопасное сообщение `Agent diagnostics unavailable` в
stderr и не подменяет ответ агента. В таком случае журнал неполон; нужно
восстановить доступ/свободное место. В диагностике нет промптов, текста вопросов,
ответов/рассуждений, содержимого ячеек, URL запроса, заголовков, ключей или сырых
сообщений исключений провайдера. Идентификаторы ресурсов остаются служебными
данными и защищаются доступом к каталогу сервера.

## Проверка

```sh
uv run --locked pytest tests/unit/backend/test_diagnostics.py -q
```

Управляемый HTTP-сервер проверяет реальные SDK-повторы 429/5xx/timeout,
ошибки формата с usage и реальный граф с остановкой на understand/plan/verify.
Также проверяются отмена, изоляция параллельных контекстов, ротация, повторное
чтение после завершения приложения и отсутствие контрольных секретов в журнале.
Отдельные тесты сверяют `stage`, фактический `reasoning_effort` и
`reasoning_setting` для явного режима и для `provider_default`.

### Контрольный Compose-прогон — 23.10.2026

В отдельном проекте с отдельным томом и управляемым совместимым endpoint
проверен настоящий backend-образ: регистрация, загрузка трёхстрочного CSV,
чат, реальный SQL COUNT и успешное завершение. Для understand задан один 429
перед успешным ответом; журнал содержит обе попытки. Для второго вопроса
endpoint постоянно возвращал 503 на verify: зафиксированы три попытки,
ошибка хода и `error_node=verify`, неподтверждённый текст не опубликован.

CLI прочитал тот же набор событий после перезапуска backend. Второй аккаунт
получил 404 при чтении и отправке в чужой чат; новых событий от запрещённой
отправки не появилось. Контрольные строки из вопроса/ключа/ошибки провайдера
в журнале отсутствовали. Журнал не доступен через `/api/diagnostics`.
Прогон подтверждает интеграцию и хранение; качество и задержку внешней модели
на искусственном endpoint он не измеряет.
