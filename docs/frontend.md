# Frontend: устройство и разработка

Frontend DjedAI — React-приложение в [frontend/](../frontend/). Оно работает с реальным авторизованным API, наблюдает обработку датасетов и ответы агента через SSE, показывает сохранённые результаты и визуализирует спецификации графиков. Бизнес-расчёты, права доступа, история, определения метрик и рецепты дашбордов принадлежат backend.

Документ описывает код на 30 октября 2026 года, включая агентное создание дашборда. Пользовательские шаги находятся в [user-guide.md](user-guide.md), запуск всей системы — в [local-build.md](local-build.md), HTTP-контракты — в [api.md](api.md), общие правила разработки и проверки — в [development.md](development.md) и [quality.md](quality.md).

## Где хранится состояние

Не добавляйте второй независимый источник уже существующего состояния. В приложении нет отдельного Redux/Zustand store; ответственность распределена следующим образом.

| Состояние | Владелец | Срок жизни / восстановление |
| --- | --- | --- |
| Bearer-токен и версия сессии | [api/session.ts](../frontend/src/api/session.ts) | Память и `sessionStorage` текущей вкладки; смена версии отменяет старые запросы |
| Проверенный пользователь | [app/auth.tsx](../frontend/src/app/auth.tsx) | Результат `/auth/me` для текущей версии сессии |
| Активный датасет | [app/workspace.tsx](../frontend/src/app/workspace.tsx) | React state и `localStorage`; проверяется по списку доступных `ready` |
| Датасеты, каталоги, чаты, дашборды, результаты | [api/queries.ts](../frontend/src/api/queries.ts) | Query cache, источник истины — сервер |
| Ещё не восстановленный из истории вопрос, поток блоков, выполняющийся запрос | [api/useChatConversation.ts](../frontend/src/api/useChatConversation.ts) | Локально, с привязкой к чату, датасету и сессии |
| DSN, выбранные таблицы, новый ключ модели, текст вопроса | Соответствующая форма | До очистки формы/размонтирования; секреты не сохраняются в browser storage |
| Светлая/тёмная тема | [lib/theme.ts](../frontend/src/lib/theme.ts) | `localStorage` и класс `.dark`; при отсутствии выбора — системная тема |

`WorkspaceProvider` использует список из API. Если сохранённый ID не относится к доступному готовому датасету, выбирается первый готовый или `null`. При смене сессии выбор и Query cache очищаются. Факт наличия ID в browser storage не даёт права доступа: право всегда проверяет backend.

## Авторизация и изоляция сессий

[LoginPage](../frontend/src/pages/LoginPage.tsx) использует настоящее `register`/`login` из [api/auth.ts](../frontend/src/api/auth.ts). Регистрация создаёт пользователя, затем UI отдельно выполняет вход. Публичные запросы не несут прежний Bearer. Пользовательское имя не заменяется email. Страница ограничивает повторную отправку формы, очищает пароль после ошибки, а при размонтировании отменяет запрос.

Токен хранится под `djedai.access_token` в `sessionStorage`, а не в cookie и не в `localStorage`. Если browser storage недоступно, текущая страница продолжает работать с токеном в памяти. Обновление страницы сначала вызывает `/auth/me`; личные queries монтируются только после успешной проверки. При сетевой ошибке проверки показывается ошибка с повтором, а не предполагаемый вход.

Каждая сессия имеет собственный `AbortController` и номер версии. `sessionSnapshot()` фиксирует токен и lifetime для исходящего запроса; `sessionSignal()` объединяет его с сигналом вызывающего кода. Замена или очистка токена отменяет предыдущий lifetime. Поэтому старый ответ, SSE-событие или поздний 401 не должен попадать в новую сессию. `clearSessionIfCurrent` очищает только ту сессию, которой принадлежит ошибка.

`AuthProvider` при изменении сессии отменяет queries, очищает весь Query cache и удаляет `djedai.activeDataset`. `AuthGate` использует версию для размонтирования старого workspace. Дополнительно `useChatConversation` подписан на сессию и сбрасывает собственные вопросы, блоки и stream. Это существенно для переключения аккаунтов в одной вкладке: очистки одного токена недостаточно.

Выход захватывает старый Bearer для `/auth/logout`, сразу очищает локальную сессию и отправляет отзыв с отдельным lifetime и таймаутом. Запоздалый logout не должен отменить новый вход. Ошибки 401 и 403 рабочего API переводят UI к повторному входу с соответствующим уведомлением.

Query keys не содержат `owner_id`: изоляция в пределах вкладки обеспечивается полным сбросом cache при смене сессии, а между пользователями — backend. Не вводите долговременный persisted cache личных ресурсов без изменения этой модели.

## HTTP, ошибки и контракт схем

### Общий клиент

[api/client.ts](../frontend/src/api/client.ts) содержит `API_BASE`, `apiUrl`, `send`, `request` и `ApiError`.

- Базовый адрес — `VITE_API_BASE_URL`, по умолчанию `/api`; завершающие слеши удаляются.
- Bearer берётся из текущей сессии; переданный вызывающим кодом `Authorization`, включая другое написание регистра, отбрасывается.
- JSON получает `Content-Type: application/json`; для `FormData` заголовок multipart вручную не задаётся.
- Неуспешный ответ нормализуется из `{ error: { code, message, suggestion } }`, строкового FastAPI `detail` либо HTTP-статуса.
- Сетевая ошибка становится `ApiError` с кодом `network`; намеренное прерывание остаётся `AbortError`.
- После получения JSON проверяется актуальность сессии и caller signal, прежде чем результат попадёт в UI.

TypeScript описывает ожидаемый JSON, но общий `request<T>()` не является runtime-валидатором произвольного ответа. Для небезопасных границ есть отдельные проверки: JSON SSE, формы блоков и совместимость данных графика. Если меняете контракт, исправляйте обе стороны и тесты, а не обходите проблему cast к более удобному типу.

### Генерация типов

Цепочка общих схем:

```text
Python contracts и backend OpenAPI
    → scripts/export_frontend_contracts.py
    → frontend/schema/contracts.json
    + frontend/schema/openapi.yaml (описание HTTP/SSE snapshot)
    → npm run gen:types
    → frontend/src/api/generated.ts
```

`Schemas` — alias `components['schemas']` из сгенерированного файла. Общие модели, в том числе каталог, результат, блоки чата, состояние хода, метрики, качество, происхождение чтения и дашборд, экспортируются из Python. [openapi.yaml](../frontend/schema/openapi.yaml) описывает frontend snapshot путей и ссылается на этот экспорт. Это не автоматически обновляемая копия всех существующих backend endpoints: при изменении HTTP-пути или формы запроса проверяйте snapshot отдельно.

При изменении общего контракта из корня репозитория:

```powershell
uv run --locked python scripts/export_frontend_contracts.py
npm --prefix frontend run gen:types
```

Просмотрите diff обоих snapshot-файлов и `generated.ts`. Сам `generated.ts` вручную не редактируется. В CI Python проверяет актуальность экспорта через `--check`; frontend заново генерирует TypeScript и требует пустого diff. `--default-non-nullable false` сохраняет согласованную трактовку default/nullable, поэтому поля с backend default нельзя самовольно сделать обязательными только в UI. Регрессии контрактов находятся в [api/contracts.test.tsx](../frontend/src/api/contracts.test.tsx).

## Query cache и мутации

Ключи централизованы в `keys` в [queries.ts](../frontend/src/api/queries.ts). Для разных датасетов раздельны списки чатов/дашбордов; детали индексируются серверным ID. Вложенный ключ `['result', id, 'data']` позволяет инвалидировать метаданные и данные результата общим префиксом.

По умолчанию данные считаются свежими 30 секунд, автоматического refetch при фокусе окна нет. Сеть и 5xx получают один дополнительный GET; ошибки 4xx не повторяются. Мутации не повторяются автоматически. Отдельные настройки:

| Данные | Особенность |
| --- | --- |
| Список датасетов | Polling каждые 2 секунды, пока есть `processing` |
| Detail датасета | Polling каждые 2 секунды при `refresh.status=processing`; сам датасет остаётся `ready` |
| История чата | `staleTime: 0`; polling каждую секунду, пока есть сохранённый `running` |
| Результат и данные результата | `staleTime: Infinity`: сохранённые результаты неизменяемы |
| Дашборд | GET возвращает сохранённое состояние, refresh — отдельная POST-мутация |

Upload/connect инвалидируют список датасетов; завершение наблюдения за профилированием инвалидирует список и detail. Перепрофилирование сразу кладёт принятый detail в cache. Refresh дашборда сохраняет полученный dashboard и инвалидирует результаты; удаление виджета заменяет detail ответом PATCH. Настройки модели заменяют соответствующий query результатом PUT.

DSN и ключ модели могут находиться в аргументах мутаций. Для таких мутаций установлен `gcTime: 0`, а формы вызывают `reset()` после использования. В `SourcesPage` DSN и результаты проверки очищаются после принятого подключения, а изменение DSN/типа сбрасывает старую проверку. Счётчик версии формы отбрасывает ответ проверки уже изменённого адреса. В `SettingsPage` из cache удаляются аргументы законченной мутации; после сохранения очищается поле ключа даже при неизменившихся публичных настройках. Не записывайте тела этих запросов в консоль, devtools storage или общий telemetry.

## SSE и жизненный цикл вопроса

### Транспорт

[api/sse.ts](../frontend/src/api/sse.ts) использует `fetch`, поскольку чат требует POST и Bearer-заголовок; нативный `EventSource` эти условия не закрывает. `SseParser` инкрементально декодирует UTF-8, учитывает разрывы строки/события между чанками, LF/CRLF, комментарии и многострочный `data`.

Для агента определены `status`, `tool_call`, `tool_result`, `block`, `done`, `error`; для профилирования — `progress`, `done`, `error`. Payload каждого события — JSON соответствующего контракта. Некорректный JSON даёт `bad_event`. Завершение тела без терминального `done`/`error` даёт `stream_interrupted`. Stream закрывает reader при терминальном событии или abort и проверяет lifetime перед callback.

Нет автоматического reconnect/replay POST, `Last-Event-ID` или повторного запуска агента после обрыва. Возврат в чат восстанавливает сохранённое состояние через GET. Повтор наблюдения за профилированием — новый GET на события той же задачи, а не повтор upload/connect.

### Идентичность, состояние и отмена

[useChatConversation.ts](../frontend/src/api/useChatConversation.ts) связывает оптимистический вопрос с серверной историей по ID. Для каждого явного отправления создаются UUIDv4 `request_id` и ожидаемый `message_id = m_` + UUID без дефисов. Одинаковый текст, отправленный дважды, — два вопроса. Не дедуплицируйте сообщения по тексту или времени.

Серверное `ChatMessage.turn` хранит `run_id`, состояние, этап/фазу, сообщение, сроки, ошибку и ссылку на успешный ответ. Терминальные исходы: `success`, `error`, `timeout`, `cancelled`, `interrupted`. История — источник истины: сохранённый конечный исход закрывает старый stream и освобождает локальное состояние даже при задержавшемся SSE. Ошибка вопроса не должна превращаться в успешное сообщение ассистента.

При новом чате hook сначала создаёт чат, затем навигирует на его ID и отправляет вопрос. `Run` хранит контекст, controller, принадлежность сессии, принятие вопроса и запрос остановки. Входящие события применяются только к актуальному контексту. При смене чата, датасета, сессии или размонтировании старый stream отменяется. Поздняя очистка старого run не снимает busy нового.

Кнопка **Остановить** вызывает серверный cancel принятого вопроса. Если первое подтверждение ещё не пришло, остановка ожидает его ограниченное время; для запроса отмены используется короткий timeout. После reload можно отменить сохранённый `running`. Успех, успевший сохраниться до cancel, остаётся успехом. Неподтверждённая отмена показывается как отдельная ошибка; один `AbortController.abort()` не выдаётся за подтверждённый серверный исход.

При обрыве hook очищает черновые блоки неуспешного хода и запрашивает историю. Периодическое восстановление не отправляет вопрос повторно. **Повторить вопрос**, кнопка уточнения и suggestion — новые явные отправления. Ограничение параллельных ходов и очереди обеспечивает backend; UI не имеет счётчика позиции в очереди и не вычисляет ETA. Подробности: [chat-turns.md](chat-turns.md), [agent-deadlines.md](agent-deadlines.md), [решение об очередях](decisions/172-concurrency-queues-upload.md).

## Страницы и формы

### Источники

[SourcesPage](../frontend/src/pages/SourcesPage.tsx) объединяет CSV upload, проверку/подключение PostgreSQL и ClickHouse, прогресс текущего наблюдения и список серверных датасетов. Выбор нескольких CSV отправляется одним multipart. После принятия upload/connect UI знает `dataset_id` и подключает profiling SSE.

Для БД есть переключатель типа, DSN, **Проверить соединение**, выбор найденных таблиц и **Подключить**. Проверка не создаёт источник. Пустой набор выбранных таблиц означает все доступные таблицы, а не «не подключать ничего». ClickHouse DSN — HTTP(S), PostgreSQL — PostgreSQL URI. Секрет не хранится в browser storage, но остаётся в поле/памяти во время редактирования: это не password mask.

Строки `ready` доступны для выбора/каталога; `processing` — для повторного наблюдения. **Скрыть прогресс** закрывает GET и UI, не отменяя серверную задачу. **Повторить получение прогресса** используется при транспортном сбое. **Загрузить заново** у ошибочного датасета открывает CSV picker, а не отдельную форму повторного DB connect. Новые размеры/квоты и HTTP 429/413 приходят из backend; frontend не измеряет дисковую квоту и не предоставляет управление очередью.

### Каталог

[CatalogPage](../frontend/src/pages/CatalogPage.tsx) показывает summary, таблицы, original/system names, типы, описания, пропуски, примечания, журнал и найденные связи. [api/view.ts](../frontend/src/api/view.ts) переводит контракт в подписи, объединяет предупреждения и строит раскладку графа. [RelationGraph](../frontend/src/components/RelationGraph.tsx) — отдельный SVG с доступными с клавиатуры узлами, направлением/типом связей и горизонтальной прокруткой больших схем.

Ревизия/время/свежесть читаются из detail; **Перепрофилировать** запускает background refresh. Во время него прежний каталог остаётся доступным. Ошибка новой сборки показывается отдельно. Нет форм редактирования типов, описаний или отношений и нет отдельного UI реестра метрик. Свежесть отражает последнюю проверку, а не live subscription к схеме базы. Различия PostgreSQL live и CSV/ClickHouse snapshot описаны в [data-and-catalog.md](data-and-catalog.md) и [решении #169](decisions/169-catalog-revision.md).

### Настройки модели

[SettingsPage](../frontend/src/pages/SettingsPage.tsx) работает с общими на установку настройками. `editable_connection=false` скрывает ключ/адрес и оставляет select по `allowed_models`. При разрешённом редактировании модель — input с datalist, адрес — URL input, новый ключ — password input. Запросы отправляют только изменённые поля. Защита полей также есть на backend: UI не является границей разрешения.

Кнопка **Проверить** использует редактируемые значения, но не сохраняет их. **Сохранить** применяет изменения со следующего вопроса. **Удалить** у заданного через UI ключа отправляет `api_key: ''`: это удаление override с возвратом к серверной конфигурации, а не гарантированное отключение ключа. Сохранённый ключ в read response отсутствует. Профиль `matches_env=false` сопровождается уведомлением об отключённых reasoning, оценке стоимости и передаче значений ячеек. Форм управления температурой, стоимостью, лимитами и data-sharing нет.

Источник серверной семантики — [model_settings.py](../src/djedai/backend/model_settings.py). Особенность для поддержки: настройки общие, а Query cache каждого браузера локален и не рассылает изменение остальным пользователям в реальном времени.

## Блоки ответа, результаты и ограничения

[ChatBlocks](../frontend/src/components/ChatBlocks.tsx) отображает согласованный discriminated union блоков:

| Блок | Реализация |
| --- | --- |
| `text` | Ограниченный Markdown через React text nodes |
| `chart` | `ChartAnswer` + `ChartCard`/`ResultChart`, данные и объяснение по `result_id`, сохранение через `SaveToDashboard` |
| `table` | Данные результата, проекция колонок, ограниченный preview |
| `clarification` | Кнопки вариантов, отправляющие текст следующего вопроса |
| `suggestions` | Кнопки предлагаемых вопросов |
| `dashboard_link` | Внутренняя ссылка на `/dashboards/{id}` |
| Неизвестный/несовместимый | Видимое объяснение вместо падения всего ответа |

Текст модели недоверенный. [Markdown](../frontend/src/components/Markdown.tsx) поддерживает абзацы, заголовки, списки, bold/italic и inline code; не использует HTML-инъекцию. Это не полноценный GitHub Markdown: сырые HTML, произвольные ссылки, таблицы и fenced code blocks не получают автоматически полный Markdown-rendering. HTML в tooltip ECharts отдельно экранируется функциями форматирования.

Только последний ответ разрешает нажать уточнение/suggestion; во время следующего запроса они отключены. Иначе выбор мог бы подтвердить не последний вопрос. Текст кнопки сразу отправляется, а не копируется в draft.

[SavedResult](../frontend/src/components/SavedResult.tsx) по ID читает метаданные и данные сохранённого расчёта. [HowCalculated](../frontend/src/components/HowCalculated.tsx) показывает инструмент/параметры, колонки, SQL, строковый объём, происхождение чтения и ограничения. `calculation()` в `view.ts` собирает сведения из `quality` и `read`; сравнение с текущей ревизией позволяет отметить старый расчёт после перепрофилирования. Не пытайтесь реконструировать результат из прозы модели или повторно вычислять его на frontend.

Определения метрик и проверки качества — backend-функции, но их последствия видны в уточнениях, ответе и сохранённом результате. `calculation()` явно отображает `quality`/`read`; полный `MetricProvenance` отдельной структурированной формой в панели не развёрнут. Пояснение метрики может присутствовать в тексте ответа, а полные сведения доступны в метаданных API. При изменении mapping не теряйте потери распознавания, неполный lineage и режим чтения. Правила: [#166](decisions/166-metric-semantics.md), [#168](decisions/168-typing-losses.md), [#169](decisions/169-catalog-revision.md).

Есть известная граница текущего интерфейса: ссылки **Метаданные JSON**, **Данные JSON** и исходного результата — обычные `<a>` на защищённый endpoint. Они не проходят через общий клиент и не добавляют Bearer. Встроенное чтение авторизовано, переход по ссылке может вернуть 401. Для исправления нужен авторизованный fetch/download либо внутренний экран, с сохранением lifetime сессии; передавать токен query-параметром не следует. Не описывайте эти ссылки как готовый надёжный экспорт.

## Renderer графиков

Путь данных:

```text
chart block / Widget.chart
    → ResultChart или DashboardWidget
    → GET /results/{id}/data
    → SpecChart (проверка формы и пустых состояний)
    → React ResultTable/KPI либо ECharts option
```

[spec.ts](../frontend/src/charts/spec.ts) поддерживает `line`, `area`, `bar`, `pie`, `scatter`, `histogram`, `heatmap`, `box`, `table`, `kpi`. Основные оси/серии находятся там; [special.ts](../frontend/src/charts/special.ts) отвечает за scatter, histogram, heatmap и box. [echarts.ts](../frontend/src/charts/echarts.ts) регистрирует только нужные series/components и SVG renderer. [Chart](../frontend/src/charts/Chart.tsx) создаёт instance один раз, меняет option при изменении данных/темы, использует `ResizeObserver` и освобождает instance при unmount. Комментарий «canvas» в файле не меняет фактический `renderer: 'svg'`.

`ChartTemplate` описывает представление; `ChartSpec` добавляет `result_id` для блока чата. Браузер применяет только сортировку и limit к полученным строкам через `displayData()`. Значение по умолчанию — 20 строк. Бизнес-агрегация, SQL, интервалы гистограммы, квартили и итоговый KPI должны быть подготовлены сервером. Сортировка/limit frontend не являются топом по не полученной части базы.

Перед отрисовкой [data.ts](../frontend/src/charts/data.ts) проверяет:

- наличие полей осей, мер, цвета и сортировки в данных;
- конечные числовые значения или NULL, без скрытого превращения строк в числа;
- полный однострочный результат с одной мерой для KPI;
- неотрицательные значения pie и готовых частот histogram;
- две категории и одну меру для heatmap;
- пять полных упорядоченных статистик одинакового формата для box plot;
- допустимость цветовой группировки и отсутствие нескольких строк одной пары категорий там, где нужен готовый агрегат.

Пустые данные, отсутствие числовых значений, неизвестный тип, несовместимая форма и ошибка GET имеют разные состояния. Сетевое повторение повторяет GET данных результата. Усечение сервером или ограничение отображения сопровождается пояснением. Не заменяйте отсутствующие значения нулями ради появления графика.

[ResultTable](../frontend/src/charts/ResultTable.tsx) использует порядок и labels спецификации либо явную проекцию table block, пропускает неизвестные поля и показывает NULL прочерком. Временная точность ISO-колонки сохраняется по наиболее подробному значению; время выводится как записано, без сдвига в зону браузера, а явное смещение указывается. [format.ts](../frontend/src/charts/format.ts) и `lib/format.ts` задают числовые, процентные, денежные и временные подписи. Обычный числовой `measureLabel` сохраняет дробную часть, проценты ожидаются уже в масштабе 0–100. Денежный формат пока жёстко использует ₽ и округляет до целых; он не выбирает валюту по `MetricProvenance`. Отдельный `formatMeasure` в общем SavedResult preview и dashboard KPI также округляет числовой формат по умолчанию до целых. Это ограничения отображения, а не изменение сохранённых JSON/Parquet; не обещайте пользователю точность предпросмотра дробных чисел или универсальную валютную поддержку.

Pie использует отдельную HTML-легенду, чтобы она не перекрывала кольцо. У scatter идентичность категории отделена от текстовой подписи: NULL и строка «Нет значения» не должны стать одной переключаемой серией. Chart tests и browser tests закрепляют эти случаи.

## Дашборды: сохранённый снимок и пересчёт

Создание теперь выполняет отдельная агентная ветка `understand → plan_dashboard → execute_dashboard → save_dashboard`, описанная в [решении #78](decisions/78-dashboard-branch.md). Frontend отправляет обычный вопрос и отображает полученные превью и `dashboard_link`. Планирование 3–8 виджетов, сохранение рецептов, повтор планирования и частичные ошибки находятся на сервере. Отдельный экран builder или мутация из кнопки графика для этого не нужны.

[DashboardsPage](../frontend/src/pages/DashboardsPage.tsx) получает список и выбирает явный ID либо первый dashboard. GET возвращает сохранённый snapshot и **не запускает refresh**. **Новый** — ссылка в чат. **Обновить данные** — POST refresh, который перевыполняет сохранённые рецепты без нового LLM-плана. У каждого виджета загружаются метаданные/строки результата; KPI использует отдельный `kpiView`, остальные типы — `SpecChart`. `kpiView` берёт первую строку и может показать дополнительные меры/факты; все проверки полноты KPI из `SpecChart` в этом пути не переиспользуются. При развитии renderer учитывайте эту разницу.

`widget.status=error`, пустой `result_id` или ошибка загрузки конкретного результата дают локальную ошибку виджета; успешные соседи остаются видимыми. Кнопка **Повторить** виджета сейчас вызывает общую refresh-мутацию всего дашборда. **Как посчитано** временно заменяет график панелью, **Удалить** отправляет PATCH с ID виджета. Форм rename/delete всего dashboard и drag-and-drop layout нет; добавление отдельного графика выполняется из чата.

В чате [ChartAnswer](../frontend/src/components/ChartAnswer.tsx) лениво читает метаданные при раскрытии **Как посчитано**. [SaveToDashboard](../frontend/src/components/SaveToDashboard.tsx) при открытии меню получает список дашбордов текущего датасета и сохраняет `dataset_id`, `result_id`, `chart` и optional `dashboard_id`. Рецепт восстанавливает backend; клиент не конструирует его из графика. После успеха ChatPage на 6 секунд показывает уведомление со ссылкой. Ошибки списка/сохранения доступны для повторения. Форматы и проверки — [решение #88](decisions/88-how-calculated-save-to-dashboard.md), [семантика рецептов и snapshot](decisions/97-dashboard-api-refresh.md). Optional Export в компоненте не является реализованным экспортом приложения.

## Стили, адаптация и доступность

[styles/tokens.css](../frontend/src/styles/tokens.css) содержит реальные frontend-токены; [globals.css](../frontend/src/styles/globals.css) сопоставляет их Tailwind и задаёт общие правила. Дизайн-источник и макеты находятся в [ui-design/](ui-design/), но при расхождении работающий экран определяется исходниками страниц. Не добавляйте случайные дубли цветов, шрифтов и размеров, если есть подходящий token. Шрифты bundled локально, внешняя font CDN не нужна.

`useCompactLayout` переключает боковую панель при ширине меньше 1024 px. Каталог располагает журнал и связи рядом от 1180 px; большие графы получают полную строку. Таблицы имеют минимальную ширину и прокрутку, pie меняет расположение легенды, дашборды используют grid с минимальной шириной виджета 360 px. Это реализованная адаптация desktop/tablet; полноценный отдельный мобильный сценарий этим не доказывается.

Общие компоненты имеют labels, focus-visible, статусы и ошибки, `aria-busy`, `aria-current`, `aria-live`; Radix обеспечивает поведение dropdown/collapsible. Узлы графа доступны по Tab и Enter/Space; у ECharts-контейнера есть `role=img` и label, а табличный результат даёт текстовую альтернативу числам. Наличие этих механизмов не является сертификатом полной доступности. При изменении формы проверяйте label, доступное имя, порядок фокуса, disabled, контраст и работу с клавиатуры; jsdom не проверяет фактическую раскладку.

## Локальная разработка и dev mock

Из `frontend/` после установки закреплённых версий:

```powershell
npm ci
npm run dev
```

По умолчанию это **реальный API**. Vite proxy отправляет `/api` на `http://localhost:8000`; backend должен быть отдельно запущен по [local-build.md](local-build.md). Изменить target можно переменной **процесса Vite** `DJEDAI_API_PROXY`:

```powershell
$env:DJEDAI_API_PROXY = 'http://127.0.0.1:8001'
npm run dev
```

`VITE_API_BASE_URL` меняет browser base URL и встраивается при сборке. Обычно относительный `/api` позволяет сохранить одну схему с dev proxy и nginx. `DJEDAI_API_PROXY` читает `vite.config.ts` из process environment: не ожидайте, что произвольная запись в frontend `.env.local` автоматически изменит эту переменную конфигурационного процесса. В production Vite dev proxy не обслуживает приложение; маршрутизацию задаёт сервер/nginx.

Для визуальной работы без backend явно включите `VITE_API_MOCKS=true` в окружении Vite либо в локальной конфигурации frontend и перезапустите dev server. [mocks/browser.ts](../frontend/src/mocks/browser.ts) использует MSW 3 `virtual:msw`; query-параметр `?mock=normal|empty|slow|error` выбирает сценарий и сохраняет выбор в пределах вкладки. Вернуться к обычному mock можно `?mock=normal`.

Mock запускается только при `import.meta.env.DEV && VITE_API_MOCKS === 'true'`. Production build не импортирует эту bootstrap-ветку. Сценарии MSW подходят для состояний страниц и контрактов компонентов; они не подтверждают read-only подключение, настоящее шифрование, владение, DuckDB SQL, очереди или качество ответа модели. Не помещайте ключ API, пароль и DSN в `VITE_*`: эти значения предназначены для публичного browser bundle. Для backend используются его собственные настройки.

Часть chart/block browser tests намеренно управляет ответами API для проверки renderer: это не оценка качества LLM. CP1 использует реальный HTTP model client с детерминированным тестовым OpenAI-совместимым сервером, а не внешний платный провайдер. ClickHouse в форме браузерного сценария обслуживается тестовым HTTP-сервером; настоящая серверная изоляция БД проверяется отдельными Python integration runners. Smoke живой установки требует `DJEDAI_SMOKE_USERNAME`/`DJEDAI_SMOKE_PASSWORD`; с настоящей моделью он может совершать внешние вызовы. Не подменяйте факт детерминированного прохождения заявлением об успешной проверке оплачиваемой модели.

[CI workflow](../.github/workflows/ci.yml) запускает repository checks, frontend contracts/typecheck/lint/coverage/build, Python checks и отдельный browser job. Browser job также проверяет Compose/nginx/persistent volumes и повторное чтение после рестарта; evidence сохраняется artifact. [check-ci-changes.mjs](../scripts/check-ci-changes.mjs) пропускает application suites для изменений только документации, но Markdown в `prompts/` считается runtime. `required` проверяет ожидаемые исходы jobs. Документационный PR не обязан показывать новые application test counts; реальные результаты и ограничение конкретного прогона фиксируйте по его протоколу, не по одному наличию тестового файла.

## Границы текущего UI, важные при изменениях

- Авторизация, реальные источники, сохранённая история, состояния хода, каталог и renderer уже подключены к API; dev mock — отдельный явный режим.
- Редактирования metric definitions, типов/связей каталога, удаления датасета, управления очередью/квотой и паролем аккаунта в UI нет.
- Агент создаёт дашборд по вопросу; отдельный график сохраняется кнопкой **В дашборд**. Optional Export в `ChartCard` не означает наличия экспорта в интерфейсе.
- GET dashboard показывает snapshot; POST refresh пересчитывает все виджеты, в том числе из кнопки повтора одного ошибочного виджета.
- JSON anchors обходят общий Bearer transport и остаются ограничением интерфейса.
- Настройки модели общие на установку; разрешённый select не даёт пользователю право изменить скрытый адрес или ключ.
- Клиентские сортировка, форматирование и limit не заменяют серверный расчёт, полный результат и проверку качества.

Перед добавлением действия проследите полный путь: доступный control → hook/transport → согласованный контракт → backend-проверка → invalidation → загрузка/ошибка/повтор → тест нужного уровня. Это позволяет развивать экран, сохраняя идентичность вопросов, изоляцию сессии и происхождение чисел.
