# PL-3: прогон данных организаторов HK_Datasets

**Дата: 26–27 октября 2026 года. Результат:** платформа загружает все девять CSV организаторов:
- **штатная загрузка CSV:** работает;
- **прямое подключение PostgreSQL:** работает;
- **ClickHouse:** подключается без предварительной обработки данных после исправления порога.

Типы всех 145 колонок совпали с README организаторов. Все 66 сверяемых ключевых запросов на каждом из трёх источников совпали с независимым эталоном.

Прогон выявил пять дефектов. Четыре исправлены в этой задаче и подтверждены повторным прогоном. Ещё три требуют отдельных задач, тексты для них подготовлены ниже.

Прогон сделан без LLM. Сценарии с моделью проверит MLE. Ниже приведена теоретическая оценка, какие из них закрываются инструментами платформы.

Повторяет прогон скрипт [check_hk_datasets.py](../scripts/check_hk_datasets.py), эталонные типы лежат в манифесте [hk_datasets_manifest.json](../eval/hk_datasets_manifest.json). Синтетика в прогоне не используется: все цифры ниже получены на опубликованных файлах.

## Как проверялось

| Шаг | Что делается | Эталон |
| --- | --- | --- |
| download | Девять файлов закреплённой ревизии; докачка по HTTP Range с повтором при обрыве | Размер и Git blob из манифеста |
| reference | `csv.reader` считает записи и пустые значения. Отдельная DuckDB читает файлы с типами из README | Код платформы не используется |
| csv | `ingest_csv_dataset` — тот же путь, что `POST /datasets/upload`: все 9 файлов одним датасетом | — |
| types / profile | Типы, доля нераспознанных, строки, ключи, временные колонки, связи, размер каталога в промпте | README и `csv.reader` |
| queries | 13–14 вызовов инструментов на таблицу (120 всего), по 3 повтора: холодный и медиана повторных | SQL на эталонной DuckDB для 66 вызовов |
| postgres | Таблицы с типами README загружаются в демо-PostgreSQL, затем `connect_postgres_dataset` и те же запросы | Тот же эталон |
| clickhouse | То же для демо-ClickHouse, `connect_clickhouse_dataset` | Тот же эталон |
| API | Бэкенд uvicorn, `POST /api/datasets/upload` девяти файлов одним запросом, опрос статуса | Число таблиц и строк |

Пары «запрос — эталон» по сценариям кейса:
- **«Сколько записей», «за какой период»:** `run_sql`;
- **«Какие значения чаще»:** `value_counts`;
- **«Динамика по месяцам», «сумма по кварталам»:** `time_aggregate`;
- **«Есть ли повторы»:** `find_duplicates` по ключу и по строкам целиком;
- **«Что связывает записи»:** JOIN самоссылки в 01 и 02;
- **корреляция:** «Показы»/«Клики» в 06.

Инструменты `describe_dataset`, `describe_column`, `detect_anomalies`, `seasonality`, `segment_profile` и `compare_segments` сверяются только по статусу и времени: для них нет одного числового ответа.

Среда:
- **Железо и ОС:** Fedora 44, 12 CPU, 15 ГБ ОЗУ, NVMe.
- **Python и DuckDB:** Python 3.13.16, DuckDB 1.5.6, зависимости из `uv.lock`.
- **Демо-БД:** образы PostgreSQL и ClickHouse из `compose.yaml` (те же digest) в podman, одноразовые контейнеры.

### Типы и профиль

Типизация совпала с README для всех 145 колонок девяти таблиц:
- нераспознанных значений 0;
- даты и время, десятичная запятая и разреженные колонки дат распознаны без потерь. В разреженных колонках («Возвращено отправителю (МСК)», «Отклонена (МСК)») пустоты остаются пропусками.

Отдельно о колонках, которые README велит считать категориями:
- `ID_Аптеки` и `ID_Лекарства` — числовые коды, распознаны как `id`, а не как числа;
- `Версия приложения` (`2.0.1`) осталась текстом.

Уникальный ключ найден у 8 таблиц из 9. У 09 ключ составной (`Дата`, `ID_Аптеки`, `ID_Лекарства`): профайлер ищет только одноколоночные ключи. Дублей по составному ключу нет, и это совпадает с эталоном.

Полных дублей строк нет ни в одной таблице. Связей между файлами не найдено, и это верно: общих идентификаторов у файлов нет.

Каталог в промпте агента (`to_prompt()`) занимает 12 037 символов, около 4–5 тыс. токенов на все девять таблиц.

## Сценарии кейса: что закрывают инструменты

Оценка теоретическая: с моделью сценарии не прогонялись. «Детерминированно проверено» значит, что инструмент вернул верный результат на HK_Datasets без LLM. Остальное зависит от того, выберет ли модель нужный инструмент и параметры. Это проверяет MLE.

| Сценарий | Инструменты | Проверено без LLM | Оценка |
| --- | --- | --- | --- |
| 1. «Что передо мной?», «за какой период и сколько?» | Каталог в промпте, `describe_dataset`, `run_sql` | Да: строки, период, состав таблиц | Должно работать. Каталог на 12 тыс. символов помещается в контекст; описания таблиц на русском пишет LLM при загрузке, если модель подключена (`describe_dataset` в `data/service.py`) |
| 2. «Что означает поле?», «какие значения чаще?» | `describe_column`, `value_counts`, README-подобные описания от LLM | Да | Должно работать. Смысл поля модель выводит из исходного имени: имена в HK содержательные |
| 2. «Что связывает записи с одинаковым Y?» | `segment_profile`, `find_duplicates`, `run_sql` | Частично: JOIN самоссылок верен | Работает через SQL. Каталог не подсказывает самоссылки (дефект 6) |
| 3. «Что происходит с X каждый июль?», «есть ли повторы?» | `time_aggregate`, `seasonality`, `find_duplicates`, `detect_anomalies` | Да | Должно работать. Два года данных дают ровно 24 месяца, минимум для сезонности с периодом 12 |
| 4. Визуализация и смена вида | `chart_hint` в `ToolResult`, `ChartSpec` | Нет: нужен агент и UI | Зависит от модели. Без роли `dimension` (дефект 7) подсказка оси категорий слабее |
| 5. Дашборд «ежеквартальная статистика» | `time_aggregate(freq=quarter)`, рецепты виджетов, `/api/dashboards` | Расчёт — да | Расчёт верен. Сборку дашборда проверяет MLE и UI |
| 6. Диалог с контекстом | `agent/memory.py`: окно истории и фокус на прошлых результатах | Нет | Зависит от модели |
| доп. Повторяющийся паттерн 12 месяцев, сезонные пики | `seasonality` | Да: пики найдены | Должно работать |
| доп. Сегменты «тип + роль», «чем X отличается от Y» | `segment_profile`, `compare_segments` | Да | Должно работать |
| доп. Корреляции, лаг «C предшествует D на 5 дней» | `run_sql` (`corr`, сдвиг по датам) | Корреляция — да | Корреляция работает. Отдельного инструмента для лагов нет, модель должна написать SQL с `lag`/сдвигом сама: риск ошибки |
| доп. Экстраполяция, «что если изменить цену» | — | — | Не покрыто: прогноза и сценарного моделирования нет. Модель должна отказать или предложить тренд по `time_aggregate`. Возможный пробел для финала |

Что стоит проверить MLE на этих данных в первую очередь:
1. сценарии 1–2 по каждому файлу (критерий CP2);
2. вопрос про возвраты в 01: самоссылки нет в каталоге;
3. вопрос о прогнозе, чтобы проверить, что модель честно сообщает об ограничении;
4. имя таблицы с цифрой в начале (`01_prodazhi`): по протоколу CP1 модель сначала забывает кавычки, и граф исправляет запрос со второй попытки.

### Issue 1: связи внутри одной таблицы

**Название:** `feat(data): находить связи внутри одной таблицы (ссылки на ключ той же таблицы)`

**Что происходит.** В README организаторов описаны две самоссылки:
- в 01: `Код исходной позиции` → `Код позиции`;
- в 02: `Код предыдущего обращения` → `Код обращения`.

`find_relations` пропускает пары колонок одной таблицы (`relations.py`, проверка `a.table.view_name == b.table.view_name`). Снять проверку недостаточно: без совпадения имён связь принимается только при `jaccard ≥ 0,5`, а у ссылки на ключ он мал: 5 819 из 500 000.

**Как воспроизвести:**

```sh
uv run --locked python scripts/check_hk_datasets.py --tables 01,02 --stages download,reference,csv
```

В `report.md` у обеих самоссылок стоит «НЕ найдена».

- **Ожидается:** в `relations` есть связи N:1, в промпте у колонки пометка `FK → …`.
- **Фактически:** связей 0.

**Замеры.** JOIN самоссылки верен и совпал с эталоном: 5 819 строк в 01 и 199 439 в 02.

**Влияние.** Сценарий 2 («что связывает записи») и анализ возвратов и цепочек обращений идут без подсказки каталога.

**Решение и приёмка:**
- рассматривать пары внутри таблицы, если одна сторона — кандидат в PK;
- принимать N:1 при `overlap ≥ 0,95` без условия на jaccard;
- проверка JOIN и предупреждения как у межтабличных связей;
- тест на фикстуре, ложных связей на синтетике PL-2 нет;
- в HK обе связи найдены.

### Issue 2: тип category и роль dimension

**Название:** `fix(data): назначать тип category и роль dimension текстовым колонкам с малым числом значений`

**Что происходит.** Спецификация §B1-2 п. 4 задаёт вывод типа «… → category (низкая кардинальность) → text». В коде `category` не назначается нигде, а роль `dimension` получают только `bool`.

В HK все 88 текстовых колонок стали `text`/`text`, хотя у 61 из них не больше 50 значений: «Канал продажи» — 3, «Тип операции» — 2, «Статус» — 3–6. Коды вида `ПР-ЗК-0000001` тоже остаются `text`, а не `id`.

**Как воспроизвести.** Запустить `check_hk_datasets.py --stages download,reference,csv` и посмотреть роли в `csv-catalog.json`.

**Замеры.** Распределение ролей в каталоге HK: `id` — 2, `dimension` — 0.

**Влияние:**
- сценарии 3–5: группировки, оси категорий графиков, дашборды;
- агент выбирает измерения только по числу уникальных в промпте;
- UI показывает «текст» вместо «категория».

**Решение и приёмка:**
- текстовой колонке с малым числом значений назначать `category` (порог в `LimitSettings`, согласовать);
- текстовым кодам с ID-подобным именем — `id`;
- тесты на фикстурах. В HK «Канал продажи», «Статус», «Город» получают `dimension`, «Код заказа» — `id`; инструменты и связи не меняют поведение.

Refs #49

### Issue 3: загрузка при нехватке временного места

**Название:** `fix(backend): понятная ошибка и освобождение временных файлов при загрузке больших CSV`

**Что происходит.** Starlette пишет multipart во временный каталог (`TMPDIR`, по умолчанию `/tmp`), затем сервис копирует файлы в `raw/`. При загрузке девяти файлов HK (1,48 ГБ) с `/tmp` на tmpfs 1,6 ГБ:
- ответ `400` за 1,3 с без причины;
- `/tmp` заполнен на 100 %;
- uvicorn держал 8 удалённых временных файлов до перезапуска, и другие процессы на машине получали «No space left on device».

С `TMPDIR` на диске та же загрузка проходит: `202` за 4,7 с, обработка 123,7 с, пик RSS 1,4 ГБ.

- **Ожидается:** ответ с текстом «недостаточно места для загрузки», временные файлы удалены.
- **Фактически:** `400`, место занято до перезапуска.

**Замеры.** На диске нужно около двух объёмов загрузки (временные файлы и `raw/`) плюс DuckDB: для HK это примерно 3,1 ГБ.

**Влияние.** В Compose `/tmp` контейнера лежит на диске, и проблема не видна. На машине с маленьким `/tmp` загрузка всего датасета падает без объяснения.

**Решение и приёмка:**
- обрабатывать `OSError` при разборе multipart, закрывать и удалять временные файлы, отвечать понятным текстом;
- описать требование к месту и `TMPDIR` в `infra/README.md`;
- рассмотреть потоковую запись сразу в `raw/`;
- тест: при нехватке места не остаётся открытых файлов.

Refs #49

## Как повторить

Из корня репозитория. Данные кэшируются в `artifacts/hk-datasets/`, отчёты пишутся в `artifacts/hk-check/<UTC>-<суффикс>/` (`report.json`, `report.md`, каталоги и файлы DuckDB).

```sh
# Скачать данные (около 1,5 ГБ), построить эталон, загрузить CSV и выполнить запросы.
uv run --locked python scripts/check_hk_datasets.py

# Демо-БД: docker compose --profile demo up -d --wait (infra/README.md), затем переменные
# DJEDAI_DEMO_{PG_LOADER_DSN,PG_READER_DSN,CH_LOADER_URL,CH_READER_URL} из .env.
# OPENSSL_CONF=/dev/null нужен только в песочнице Flatpak, где postgres_scanner падает.
uv run --locked python scripts/check_hk_datasets.py --stages postgres,clickhouse \
  --reference artifacts/hk-check/<run>/reference.duckdb

# Сравнить прогоны до и после изменения.
uv run --locked python scripts/check_hk_datasets.py --compare <before>/report.json <after>/report.json
```

Код выхода 0 и `status: finished` значат, что все этапы выполнены. Расхождения с эталоном видны в `report.md` (колонка «Эталон») и в `report.json` (`match: false`, `type_mismatches`).

Чтобы получить прогон «до», запустите скрипт текущей ветки на коде коммита `2ad05a4`. Пример — через `git worktree add <dir> 2ad05a4`:

```sh
uv run --locked python <dir>/scripts/check_hk_datasets.py --cache artifacts/hk-datasets
```

Загрузка через API:
1. `uv run --locked alembic upgrade head`;
2. `uv run --locked uvicorn --app-dir src djedai.backend.app:app`, переменная `TMPDIR` должна указывать на раздел, где свободно не меньше 1,5 ГБ;
3. регистрация и вход через `/api/auth/register` и `/api/auth/login`;
4. `POST /api/datasets/upload` с девятью полями `files`;
5. опрос `GET /api/datasets/{id}` до статуса `ready`.
