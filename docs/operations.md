# Эксплуатация и восстановление

Глава рассчитана на локальную поставку из [`compose.yaml`](../compose.yaml): один backend-процесс, nginx/frontend и постоянный том `app-data`. Первичная установка описана в [local-build.md](local-build.md), параметры — в [configuration.md](configuration.md). Команды выполняются из корня того же checkout с тем же Compose project name, что использовался при запуске.

## Что работает и что сохраняется

Backend запускает Alembic-миграции, необязательный legacy bootstrap и один Uvicorn-процесс. SQLite содержит пользователей, непрозрачные сессии, ownership ресурсов, каталоги и ревизии, состояния фоновых задач и ходов, историю чатов, метрики, дашборды и настройки модели. CSV/DuckDB и Parquet находятся на диске. Процесс запускается от UID/GID `10001:10001`.

В Compose весь рабочий каталог `/app/var` смонтирован в именованный том:

| Путь в контейнере | Содержимое |
| --- | --- |
| `/app/var/app.db` | БД приложения и метаданные |
| `/app/var/data/datasets` | Сохранённые источники, DuckDB и ревизии |
| `/app/var/data/results` | Parquet сохранённых вычислений |
| `/app/var/diagnostics` | Текущий JSONL и архивы диагностики |

Резервировать нужно весь `/app/var`, а не только `app.db`. Ссылки SQLite на результаты/датасеты без соответствующих файлов не восстанавливают содержимое. Пароли источников и ключ модели из UI зашифрованы `SOURCE_ENCRYPTION_KEY`; этот ключ и серверная конфигурация хранятся отдельно в защищённом месте. Сам том не зашифрован приложением целиком.

Внешний PostgreSQL не является частью тома приложения. Его резервирует владелец БД отдельно. Снимок ClickHouse в DuckDB также не заменяет резервную копию исходного ClickHouse. Сервисы профиля `demo` имеют отдельные тома `demo-pg-data` и `demo-ch-data`.

## Обычный запуск, остановка и изменение конфигурации

```sh
docker compose up -d --wait --wait-timeout 180
docker compose ps
docker compose logs --tail 100 backend frontend
```

Проверить API через общий nginx:

```powershell
Invoke-RestMethod http://localhost:8080/api/health
```

```sh
curl --fail http://localhost:8080/api/health
```

Health подтверждает ответ процесса и маршрутизацию через nginx. Он не обращается к модели, не проверяет внешние БД и не доказывает корректность аналитики. После изменений выполните пользовательский сценарий с известным CSV и ожидаемым ответом.

Остановить и снова запустить существующие контейнеры:

```sh
docker compose stop
docker compose up -d --wait --wait-timeout 180
```

`docker compose down` удаляет контейнеры и сеть, сохраняя именованные тома. `docker compose down -v` удаляет и данные приложения; это не команда обычной остановки, обновления или резервирования. Изменение `-p`/project name подключает другой том — пустая установка после такой смены не означает потерю старого тома.

После правки `.env`:

```sh
docker compose config --quiet
docker compose up -d --force-recreate --wait --wait-timeout 180 backend
```

После изменения исходников/зависимостей соберите образы:

```sh
docker compose up --build -d --wait --wait-timeout 180
```

В отличие от `.env`, изменение модели через UI применяется со следующего хода без перезапуска. Оно общее на установку. Режим доступа к таким настройкам и ограничения endpoint описаны в [configuration.md](configuration.md#модель-и-настройки-интерфейса).

## Нагрузка и ожидание

Действующая топология — один backend-процесс. Нельзя увеличивать `--workers` или масштабировать backend на одном томе: счётчики допуска, очереди, резервы диска и блокировки находятся в памяти процесса; файловая организация DuckDB и SQLite тоже рассчитана на эту поставку.

По умолчанию одновременно работают четыре чата всего и один чат владельца; в очереди — десять запросов всего и два владельца, ожидание допуска — 10 с. Для фоновых задач датасетов лимиты — два одновременно всего, один владельца и очередь 10/2. Владельцы обслуживаются по кругу. Заполненная очередь возвращает 429; повторная генерация в том же работающем чате — 409. Это штатный отказ в допуске, а не рекомендация многократно повторять POST.

Один принятый ход имеет общий бюджет 120 с, одна попытка модели — 60 с, дополнительная попытка по умолчанию одна. Отмена и timeout закрывают SSE и не публикуют непроверенный черновик. Слот остаётся занятым до фактического выхода worker: стороннее синхронное вычисление может завершаться позднее клиентского ответа. Следующий явно отправленный вопрос того же чата может ждать cleanup предыдущего worker, но не запускается параллельно с ним. Подробности — [agent-deadlines.md](agent-deadlines.md), [chat-turns.md](chat-turns.md) и [решение об очередях](decisions/172-concurrency-queues-upload.md).

После перезапуска незавершённые задачи датасетов перечитываются из SQLite и допускаются через ограниченную очередь. Если все восстановленные задачи не помещаются в её ёмкость, лишние получают понятный `error`, а не запускаются одновременно. Вопросы чата не повторяются автоматически: состояние и историю нужно прочитать и при необходимости явно отправить новый вопрос. Восстановление сохранённого состояния не означает продолжение оборванного HTTP-потока.

## Свободное место и квоты

CSV ограничен 2 000 000 000 байт на запрос; отдельный лимит файла удалён. Для владельца при приёме проверяются текущие файлы датасетов и резервируемые CSV-байты в пределах 5 000 000 000 байт. Квота не охватывает все данные тома: Parquet и диагностика лежат отдельно, дальнейший рост DuckDB и импорт ClickHouse не являются атомарной частью резервирования CSV. Дополнительный nginx-порог тела запроса — `2100m`.

Multipart сначала пишет во временный каталог, затем сервис сохраняет копии CSV в каталоге датасета. Поэтому свободное место требуется на обоих этапах; для девяти файлов HK_Datasets нужно около 3,1 ГБ на временные и исходные копии, плюс дальнейший рост DuckDB. При 507 `insufficient_storage` проверьте Docker storage, том и `TMPDIR`; при необходимости перенесите временный каталог на раздел с запасом. Временные файлы и неполный датасет освобождаются обработчиком ошибки. Подробнее — [место для загрузок](../infra/README.md#место-на-диске-для-загрузки-csv).

Следите за свободным местом хоста/Docker и размером тома независимо от пользовательских квот:

```sh
docker system df
docker compose exec backend /bin/sh -c 'df -h /app/var; du -sh /app/var/data/datasets /app/var/data/results /app/var/diagnostics'
```

Команды только читают объём. Не удаляйте произвольные `dataset*.duckdb`, Parquet или записи SQLite вручную: они связаны ID и ревизиями. Универсального API удаления датасета и политики автоматического хранения всех пользовательских результатов в текущей поставке нет. Очистку данных планируйте как отдельную операцию с резервной копией и проверкой связности; ротация диагностики не очищает вычисления.

## Диагностика ошибок и задержек

Вопрос имеет `run_id`, видимый в сохранённом `ChatTurnState` и событиях `status`. Он связывает историю с локальным журналом оператора. Читать журнал можно из контейнера:

```sh
docker compose exec backend /app/.venv/bin/python -m djedai.diagnostics --run run_ID
docker compose exec backend /app/.venv/bin/python -m djedai.diagnostics --type admission_rejected
```

Без фильтров CLI читает текущий файл и архивы по порядку. HTTP-маршрута диагностики нет. Доступ к контейнеру/тому — административный доступ к данным установки; не выдавайте его пользователям ради просмотра одного run.

Журнал содержит начало/конец хода, стадии, модельные вызовы и сетевые попытки, паузы повторов, допуск/отказы, длительность, нормализованные ошибки и доступный usage. Промпты, вопросы, ответы, рассуждения, ячейки, ключи, DSN и сырые provider errors в этот журнал не записываются. Служебные ID всё равно требуют защиты. На POSIX новые файлы создаются с режимом 0600, каталог — 0700; на Windows дополнительно проверяйте ACL хоста.

По умолчанию текущий JSONL ротируется около 10 000 000 байт, хранится пять архивов. Это ограничение объёма, а не срока хранения; часть событий старого run может уже отсутствовать. Сбой записи диагностики не подменяет ответ агента, но делает журнал неполным. Ошибка диска отмечается безопасным `Agent diagnostics unavailable` в stderr. Детали полей и проверенные сценарии — [agent-diagnostics.md](agent-diagnostics.md).

| Наблюдение | Что проверить |
| --- | --- |
| 401 / `unauthorized` в SSE | Срок/отзыв сессии; войти снова. Logout отзывает конкретную сессию |
| 404 для существующего ID другого аккаунта | Штатная owner-изоляция; войти владельцем ресурса |
| 409 при вопросе | В этом чате ещё выполняется ход либо повторно использован `request_id`; прочитать историю |
| 429 при входе | Лимит попыток, заголовок `Retry-After`; после окна попробовать один раз |
| 429 при вопросе/датасете | Заполненная очередь или timeout допуска; найти admission-событие |
| 413 при CSV | Размер файла, сумма файлов, дисковая квота либо внешний nginx-порог |
| Каталог готов с предупреждением описания | Данные профилированы, но модельное описание не удалось; проверить модель отдельно |
| `turn_timeout` | Найти последнюю стадию/попытку run; не увеличивать лимиты без оценки источника задержки |
| Сохранённый источник/модель перестали открываться | Вернулся ли прежний `SOURCE_ENCRYPTION_KEY`, доступен ли источник, не менялись ли права/сеть |
| Данные пропали после смены каталога запуска | Compose project name, подключённый том и исходный аккаунт |

Ошибки в HTTP и SSE очищены намеренно. Для диагностики сети используйте статус/тип ошибки, доступ к самому сервису и контейнерные журналы, не включая в публикуемые материалы `.env`, Authorization, provider key и строки подключений. Расчётная стоимость в JSONL при заданном тарифе не равна счёту провайдера; `null` usage не означает нулевой расход.

## Резервная копия

Ниже — холодная файловая копия стандартной Compose-установки. На время копирования останавливается **только backend** — единственный писатель `/app/var`; frontend и демо-БД можно оставить работающими. Пользовательские операции в этот период недоступны. Не выполняйте `down`, не удаляйте том и не копируйте один открытый `app.db`.

Перед началом сохраните текущий SHA (`git rev-parse HEAD`), дату, Compose project name и версию образов. Убедитесь, что резервная папка находится вне Git и имеет достаточно места. Команды создания уникальной папки:

PowerShell:

```powershell
$backupRoot = Join-Path (Get-Location) '..\djedai-backups'
$backupDir = Join-Path $backupRoot (Get-Date -Format 'yyyyMMdd-HHmmss')
New-Item -ItemType Directory -Path $backupDir -ErrorAction Stop | Out-Null
```

Bash:

```sh
backup_dir="../djedai-backups/$(date +%Y%m%d-%H%M%S)"
mkdir -p "$backup_dir"
```

Остановите backend с запасом для завершения. После команды проверьте, что контейнер действительно остановлен:

```sh
docker compose stop -t 600 backend
docker compose ps -a backend
```

Скопируйте весь каталог из **остановленного** контейнера. `compose cp` не требует запуска приложения.

PowerShell:

```powershell
docker compose cp backend:/app/var "$backupDir/app-var"
if ($LASTEXITCODE -ne 0) { throw 'Копирование не завершено; резервная копия неполна' }
Get-Item -LiteralPath (Join-Path $backupDir 'app-var/app.db')
Get-ChildItem -LiteralPath (Join-Path $backupDir 'app-var')
```

Bash:

```sh
docker compose cp backend:/app/var "$backup_dir/app-var"
test -f "$backup_dir/app-var/app.db"
ls -la "$backup_dir/app-var"
```

При ошибке копирования копия считается неполной; сохраните сообщение и повторите в новую папку, пока backend остановлен. Копируются и возможные вспомогательные файлы SQLite/DuckDB — не исключайте их вручную. После успешного копирования запустите приложение:

```sh
docker compose up -d --wait --wait-timeout 180 backend
```

Проверьте health и существующий чат/каталог. Отдельно сохраните `.env`/секреты, особенно `SOURCE_ENCRYPTION_KEY`, в защищённом хранилище; не публикуйте их рядом с техническим отчётом. Копия всего тома включает пользовательские данные и живые серверные сессии: ограничьте доступ, шифруйте резервный носитель по правилам организации и задайте срок хранения. Проверка существования `app.db` подтверждает только наличие файла; пригодность резервной копии доказывается восстановлением.

## Проверка восстановления в отдельную установку

Предпочтительно восстановить копию в **новый** Compose project/пустой том, не перезаписывая действующий. Это позволяет проверить данные и оставить исходную установку для отката. Возьмите тот же commit/образы, которыми создана копия. Подготовьте локальную конфигурацию с исходным ключом шифрования и допустимыми адресами источников/модели. Восстановленная установка имеет те же аккаунты и сессии; проверяйте её в изолированном окружении.

В примере project name — `djedai-restore`, frontend-порт — 8081. Сначала убедитесь, что и контейнеров, и тома с этим именем ещё нет:

```sh
docker compose -p djedai-restore ps -a
docker volume inspect djedai-restore_app-data
```

Ожидается отсутствие сервисов и ошибка `no such volume` у второй команды. Если том существует, выберите новое имя и замените его во всех командах; не удаляйте неизвестный том.

Выберите отдельный порт через переменную окружения текущего терминала.

PowerShell:

```powershell
$env:DJEDAI_PORT = '8081'
$restoreBackup = 'C:\путь\к\копии\20261029-120000'
```

Bash:

```sh
export DJEDAI_PORT=8081
restore_backup='/путь/к/копии/20261029-120000'
```

Создайте backend и новый том, **не запуская штатный entrypoint**:

```sh
docker compose -p djedai-restore create --build backend
```

Скопируйте содержимое `app-var` в новый том через остановленный контейнер.

PowerShell:

```powershell
docker compose -p djedai-restore cp "$restoreBackup/app-var/." backend:/app/var
if ($LASTEXITCODE -ne 0) { throw 'Восстановление файлов не завершено' }
```

Bash:

```sh
docker compose -p djedai-restore cp "$restore_backup/app-var/." backend:/app/var
```

Верните владельца файлов непривилегированному пользователю образа. Следующая одноразовая команда меняет права только в новом томе; приложение и миграции она не запускает:

```sh
docker compose -p djedai-restore run --rm --no-deps --user root --entrypoint /bin/sh backend -c 'chown -R 10001:10001 /app/var'
docker compose -p djedai-restore up --build -d --wait --wait-timeout 180
```

Откройте `http://localhost:8081`, войдите исходным аккаунтом и проверьте список датасетов, каталог, старый чат, открытие строк результата и сохранённый дашборд. Проверка подключённой БД требует доступного исходного сервиса и прежнего Fernet-ключа. Новая задача/вопрос проверяется отдельно; открытие старого результата не проверяет внешнюю модель.

Восстановленные незавершённые задачи могут быть обработаны механизмом recovery при старте. Поэтому доступ к внешним источникам и модели для проверки задавайте осознанно. Для возврата к исходной установке используйте её прежний project name и порт; не запускайте два backend на одном и том же томе. Не выполняйте поверх старого непустого тома простое копирование файлов: оно оставляет лишние результаты/ревизии и не является воспроизводимым восстановлением.

Этот порядок — операторская процедура, а не автоматизированный backup/restore-сервис. Восстановление на целевой ОС, Docker storage driver и версии приложения нужно регулярно проверять на отдельной копии. Не считайте инструкцию свидетельством уже проведённого disaster-recovery прогона вашей установки.

## Обновление и откат

Перед обновлением запишите SHA и сделайте холодную копию. Просмотрите изменения миграций и lock-файлов; выберите конкретную версию в чистом checkout. `backend-entrypoint.sh` выполняет `alembic upgrade head` автоматически. После сборки проверьте healthy, вход, известный CSV/чат, сохранённые результаты и настройки модели.

Откат образа не откатывает схему SQLite. Для гарантированного возврата к прежней версии используйте её резервную копию данных и сохранённый ключ; произвольный `alembic downgrade` не является универсальным безопасным откатом. Новые данные после точки резервирования в такую копию не попадут.

## Границы текущей поставки

Compose публикует приложение только на loopback и не настраивает TLS, публичный доступ, SSO, администраторские роли, централизованные метрики или кластерную очередь. Приложение имеет локальные аккаунты и owner-изоляцию ресурсов, но настройки модели общие. `ALLOWED_OUTBOUND_HOSTS` не реализует firewall. Для сетевой установки нужны отдельное эксплуатационное решение и сохранение границ доверия reverse proxy.

Автотесты и управляемая модель подтверждают контракты и интеграционные сценарии, но не качество всех ответов реального endpoint и не производительность на произвольном объёме данных. План проверок — [quality.md](quality.md); архитектурные границы — [architecture.md](architecture.md).
